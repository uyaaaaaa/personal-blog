# レビュー観点の台帳を main の外の orphan ブランチに持つ

PR で受けた指摘を、追記専用の `harness/journal` と、観点ごとに畳んだ `harness/ledger` の2本の orphan ブランチに置く。
main には置かない。読み書きは `scripts/harness-journal.mjs` を通し、形はスクリプトが持つ。

同じ指摘を2回受けたかどうかは、**実行しても分からず、issue にもならない**。1回目の観点は issue の完了条件を書けるほど固まっていない。
[ADR 11](./11-no-enforcement-inventory.md) が文書から追い出したのは「実行すれば分かること」で、回数と判定はそれに当たらない。

- **検討した案**
  - **main のファイルに持つ**: 記事や実装の PR に台帳の差分が混ざり、レビューと CI の対象になる。`.claude/rules/docs.md` の「書かないもの」（既知の課題や TODO の一覧）にも当たる。
  - **持たず、毎回 GitHub のレビューコメントを読み直す**: 追記専用の台帳としては GitHub で足りるが、「同じ観点の2回目」を判定するには毎回全コメントを正規化し直すことになり、回数が実行のたびにぶれる。
  - **orphan ブランチ2本（採用）**: journal は追記専用でファイル名が衝突しないため、複数のセッションが同時に書いても失われない。ledger は畳み直すので書き手を `codify` の1つに限る。どちらも main の履歴・CI・レビューに乗らない。
- **対価**: `git log` にも作業ツリーにも出ないため、台帳の存在はスクリプトと ADR を読まないと分からない。ブランチを消すと回数が失われ、すべての観点が1回目に戻る。
- **戻す条件**: 指摘が減って回数を数える必要がなくなったとき。または、観点の集計を GitHub 側が持つようになったとき。
