# ドキュメントは原則持たず、思想が反映され簡単に変えられない判断だけを ADR に残す

「実装を読んでも分からない理由」を網羅的に集める方針（旧 `docs/decisions/` の画面・機能ごとの制約 約270項目と、コンポーネント内の設計を扱う ADR 9本）をやめる。
残すのは、アーキテクチャ設計・アーキテクチャ規約・テスト設計・デザインの大方針やガードレールに当たり、かつ覆すと複数ファイル・公開 URL・ビルド設定・テストの走らせ方が変わる判断だけ。基準は `.claude/rules/docs.md`。

- **検討した案**
  - **コンポーネントの仕様書を持つ**: 「実装が正」と宣言した以上、写した文書は遅れたコピーにしかならず、変更のたびに二重更新を強いる。旧 `COMPONENT_SPEC.md` が918行まで育った主因だった。
  - **実装から読み取れない理由を全部集める**: 仕様書の写しは消えたが、コンポーネント1つに閉じる制約まで文書に残るため、1つの UI 変更で実装と文書の両方を直す手間が残った。「消したら壊れる指定」の理由を文書で守ろうとすると、守る範囲が実装の細部まで際限なく広がる。
  - **理由をコードのコメントに置く**: コメントを書かない方針（`.claude/rules/comment.md`）と衝突する。
  - **思想が反映され簡単に変えられない判断だけを残す（採用）**: 文書が守るのは方針転換の経緯だけにし、細部の制約は lint / build / テスト / 目視で受ける。
- **対価**: 「消したら壊れる指定」の再発見が、文書ではなく lint / build / テストと `verify` の目視に依存する。機械的に縛れていない箇所（`<style>` の直値、プラットフォーム系の禁止事項など）は、壊してから気づく。静的解析を厚くする方向で受ける。
- **戻す条件**: 保守する人が複数になり、目視で受けられない制約が増えたとき。そのときも仕様書ではなく、ADR の基準を緩める（「影響範囲が限られる」を外す）形で戻す。
