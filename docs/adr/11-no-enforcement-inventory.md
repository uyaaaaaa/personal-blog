# 効いている検査の一覧を文書に持たない

`docs/ARCHITECTURE.md` の「強制手段の現状」の表（何を・どの設定のどのルールが・どのコマンドで落とすか）を廃止する。
文書に残すのは、次の検査をどのツールに置くかの基準だけにする。効いていない検査は GitHub の issue が持つ。

効いている検査は、破れば `npm run lint` / `npm run build` / `npm test` / Git フックが止める。**読まれなくても効くものを文書に写すと、追従の手間だけが残る。**
実際、`CLAUDE.md` の「テストがあるのは `app/utils/` の純粋関数だけ」はコンポーネントのテストが5本入った時点で嘘になっていた。

- **検討した案**
  - **表を維持し、検査を足すたびに実装と同じコミットで直す**: 設定と表の2箇所を直すことになり、片方が漏れれば嘘になる。上記の乖離が現に起きた。
  - **効いていない検査（「未導入」「無し」）だけ表に残す**: 実行しても分からない情報ではあるが、3行とも issue が既に持っており（[#121](https://github.com/uyaaaaaa/personal-blog/issues/121) / [#156](https://github.com/uyaaaaaa/personal-blog/issues/156) / [#159](https://github.com/uyaaaaaa/personal-blog/issues/159)）、文書と issue の二重管理になる。
  - **一覧を持たない（採用）**: 効いている検査は破れば止まるので文書が要らず、効いていない検査は issue が持つ。文書には、実行しても分からないもの（置き場の基準と、検査が届かない範囲の申し送り）だけを残す。
- **対価**: どのツールがどの違反を見るかを知るには、`eslint.config.mjs`・`.dependency-cruiser.cjs`・`.prettierrc`・`package.json` を読むことになる。表を引くより遅い。効いていない範囲もローカルからは見えず、issue を引く必要がある。
- **戻す条件**: 検査が増えて、設定を読んでも全体像が掴めなくなったとき。そのときも手で書く表ではなく、設定から機械が出す一覧にする。
