# エージェントの Git の経路は、散文ではなくツール呼び出しの入口で塞ぐ

`.githooks/` の commit-msg と pre-commit を通らずに変更が入る経路と、書き手に属する判断（マージ）を、`.claude/hooks/` の PreToolUse で落とす。セッションの頭で依存と `core.hooksPath` を揃え、最初のコミットから両フックが走る状態にする。

フックを有効にするのは `npm install` の `prepare` なので、install 前のセッションでは件名の検査も lint も1つも走らない。GitHub の API でコミットを作るツールは、そもそもローカルのフックを経由しない。**規約を散文でしか持たないと、守るかどうかがその回の読みに依る。** 検査を足しても、迂回路が開いたままなら効いている保証は無い。

- **検討した案**
  - **散文のまま skills に書く**: 現にそう書いてあった「rebase と force push はしない」「マージしない」は、フック自体が走っていないセッションでも読み手に気付かれずに済んでいた。守れたかどうかを後から判定する手段も無い。
  - **ツール名だけを許可設定で塞ぐ**: `mcp__github__*` は名前で切れるが、Bash は中身を見ないと `git commit` と `git commit --no-verify` を分けられない。`git` ごと塞ぐと状態も読めなくなる。
  - **引数を読んで落とす（採用）**: `git` の綴りと GitHub のツール名の両方を1つの判定で見る。落とすときに理由と代わりの手段を1行返せる。
- **対価**
  - **セッションの起動が遅くなる**: 依存の無いコンテナでは頭で `npm ci` を通すぶん待つ。代わりに `verify` の「1 を飛ばすと別のものを測る」が起きなくなる。
  - **hook が git を読む**: マージ済みのブランチを `main` から作り直す経路だけは force push を通すため、remote の位置を判定に要る。
  - **綴りを追うことになる**: `git` のオプションと GitHub のツール名が変われば、判定の側を直す。
- **戻す条件**: ハーネスの許可設定がツールの引数まで見て書けるようになったとき。そのときは判定を設定に移し、hook を畳む。
