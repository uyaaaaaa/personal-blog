# 柱C：コンポーネントとスタイル

> 移植可能なものと不可能なものを分離する。

親ドキュメント：[../ARCHITECTURE.md](../ARCHITECTURE.md)

振る舞い・アクセシビリティ・状態機械はプロジェクトを跨いで不変。
見た目・DOM 構造・語彙はプロジェクト固有。この非対称性が柱C全体の根拠です。

---

## 分類と分割

### C-1. コンポーネントは「所有と依存」で分類する。粒度では分類しない

| 種別 | 依存してよいもの | 依存してはいけないもの |
| :--- | :--- | :--- |
| `ui/`（プリミティブ） | デザイントークンのみ | ドメイン型、ストア、ルータ、API |
| `layout/` | `ui/`、トークン | ドメイン型、API |
| `features/<name>/ui/` | `ui/`、`layout/`、自機能のドメイン | **他 feature の内部** |
| `pages` / `routes` | すべて | — |

- **強制**：`eslint-plugin-boundaries`（`A-5` と同じ機構）
- **根拠**：atoms / molecules / organisms のような粒度分類は、「product card は molecule か organism か」
  という分類論争のコストが便益を上回る。**強制できない分類は規約に書かない**
- **対価**：`ui/` が肥大化しやすい。`ui/` 内での再分割は許容するが、**それは整理であり依存ルールは付けない**

### C-2. `XxxContainer` を作らない

コンポーネントを分割してよい理由は次の3つだけです。

1. 別の場所で再利用する
2. レンダリング境界／バンドル境界を切る
3. 1ファイルが読めない大きさになった

**「ロジックがあるから分ける」は理由になりません。**

- **強制**：`no-restricted-syntax` でファイル名／識別子の `Container` サフィックスを禁止
- **根拠**：Container / Presentational の原典は著者自身が撤回済み。
  分離したかったのは「ロジックと描画」であって「コンポーネントを2つに割ること」ではなく、
  hooks / composables がその手段を提供した時点でラッパー層は不要になった
- **対価**：純粋関数的なコンポーネントの利点（テスト・story・視覚回帰）は意識的に維持する必要がある

## コンポーネント API

### C-3. 相互排他の選択肢に boolean を並べない

必ず文字列 union の1 prop にします。

boolean が許されるのは「真に二値で、直交していて、false が自明なデフォルト」の場合のみ
（`disabled`、`loading`、`required`）。

- **強制**：なし（ガイドライン）。`ui/` のレビューで厳格に、`features/` では緩く適用する
- **根拠**：boolean は1つ増えるごとに状態空間が2倍。6個で64通りで、その大半はドキュメント化もテストもされていない。
  `isPrimary` と `isSecondary` のような相互排他 boolean は**型で不正状態を防げない**
- **対価**：`features/` 固有のコンポーネントでは、呼び出し元が少数なので実害が小さい。過剰適用しない

### C-4. 直交する軸を1つの enum に押し込まない

`variant` が肥大化する原因は、1つの prop が2つの独立した軸を運んでいることです。
典型は「視覚的な強さ（primary / secondary / ghost）」と「意味（danger / success / info）」の混在。

prop を追加する前に **「これは直交する軸か？」** を問います。
既存 enum の値を増やす形になり、かつ他の軸との組み合わせが必要なら、それは新しい prop です。

- **根拠**：直交する軸を1つに押し込むと `primary-danger` `ghost-danger` … と組み合わせ数だけ値が増える。
  boolean 爆発を文字列爆発に置き換えただけになる
- **注意**：variant 合成ツールは型安全に扱えるが、**API 設計の失敗を隠す**副作用がある
  （組み合わせ爆発が快適に書けてしまう）

**1コンポーネントの prop が8個を超えたら設計の警告**とみなし、合成への分解を検討します（禁止線ではなく目安）。

### C-5. 合成（children / slot）を第一のエスケープハッチとする

prop drilling が2階層を超えたら、まず合成に書き換えます。それでも解けない場合のみ Context / provide-inject（`S-18`）。

**props は「設定」、slot は「内容」。**値を渡すなら props、構造を渡すなら slot。

- **根拠**：JSX / slot を渡すと中間コンポーネントは中身を知らずに済み、prop drilling が消える
- **対価**：呼び出し側が組み立てを知ることになり、**デザインシステムとしては一貫性が落ちる**

実務的な落とし所は **「configuration-first + escape hatch」**：
props で構成された既定形を提供し、逸脱用に slot を開ける。全部 slot にはしません。
props と slot を両方持つ場合は、**同じものを2通りで指定できる状態を避け**、優先順位を明文化します。

### C-6. 内部 DOM 構造を props で公開しない

`titleClassName` `wrapperClass` `innerStyle` `renderFooter` `iconName` のような
「中身のカスタマイズ用 props」はアンチパターンです。

- **根拠**：内部 DOM 構造を API として公開してしまい、リファクタ不能にする
- **代替**：構造は slot / children で、スタイルフックは **component トークン（CSS custom property）** で公開する（`C-14`）

### C-7. ネイティブ属性を塞がない

`ui/` のコンポーネントは基底要素の props 型を extend し、rest を基底要素に spread します。
`class` / `className` はマージ（上書きしない）、`ref` は必ず基底要素に届くこと。

- **根拠**：`aria-*` `data-*` `id` `type` `form` `onFocus` が渡せないと、
  呼び出し側は必ず回避策（DOM 直接操作、ライブラリ直 import）に走り、二重管理になる
- **対価**：無制限の spread は「デザインシステムの制約が効かない」ことでもある。
  厳格にするなら**何を許すかを明示的に列挙**する

**イベント名は「起きたこと」を表します**（`change` / `select` / `submit`）。
「何をすべきか」（`doSave` `handleClick`）は禁止。

**親コンポーネントの外では意味をなさない子は、親名を接頭辞にします**（`TodoList` / `TodoListItem`）。
名前は一般 → 具体の順（`SearchButtonClear`、`ClearSearchButton` ではない）。

### C-8. `as` prop / polymorphic を新規に作らない

要素種別を変えたい実需は、次の順で解決します。

1. **別コンポーネントを作る**（`Button` と `LinkButton`）— 大半のケースはこれで足りる
2. `asChild` / Slot 相当で合成する
3. どうしてもの場合のみ polymorphic（**オーバーロードで型を書く。**条件型による制約は避ける）

- **根拠**：polymorphic は TypeScript の型解決コストを実測可能なレベルで払う。
  コンポーネントライブラリ規模では IDE の応答性が落ちる
- **対価**：`Button` / `LinkButton` の分割はスタイルの重複を生む。variant のスタイル定義を1箇所に切り出して両者が参照する
- **注意**：**社内アプリでは polymorphic はほぼ常に過剰**

### C-9. 複数の子が状態を共有する UI は compound components にする

tabs、accordion、select、disclosure、form field。
子を props の配列（`items={[...]}`）で受け取る設計は**最終手段**（データ駆動が本当に必要な場合のみ）。

compound の子は、親の Context がないとき明示的にエラーを投げます（`S-20`）。

- **対価**：呼び出し側のコードが冗長になる。単純なユースケース向けに薄いラッパを併設するのは正当

### C-10. `ui/` の状態を持つコンポーネントは uncontrolled を既定、controlled を opt-in とする

命名は `value` / `onValueChange` / `defaultValue` で統一し、
**両方同時に渡された場合は開発ビルドで警告**を出します。

- **対価**：両対応は実装コストが実質2倍で、「controlled にしたのに state を更新しない」バグの温床。
  **アプリ内部のコンポーネントには不要**で、`ui/` の再利用プリミティブに限定する

### C-11. 複雑なインタラクションは自作しない

dialog、combobox、menu、tabs、tooltip、disclosure は headless プリミティブを採用し、
その上に自社の見た目を載せた薄い wrapper を `ui/` に1つだけ置きます。
**アプリコードは headless ライブラリを直接 import しません**（差し替え可能性の確保）。

自作する場合は「状態と ARIA と keyboard を返す composable」＋「markup だけの component」に分けます。
composable は DOM を作りません。

- **根拠**：headless が切り出しているのは**プロジェクトを跨いでも変わらない部分**
  （キーボード操作、フォーカス管理、ARIA、レイヤリング、controlled/uncontrolled の状態機械、RTL、i18n）
- **対価**：headless は**コストを移すだけで消さない。**スタイルと markup の全責任が自分に来る。
  v0 を早く出す局面では既製の見た目付きライブラリが正解のことは多い
- **注意**：**「headless を入れた ＝ アクセシブル」ではない。**wrapper で ARIA を壊すのは容易

## composable / hook

### C-12. フレームワークの reactive / lifecycle を必要としないなら、それは composable ではない

**判定手順**

1. reactive / lifecycle を使わない → `utils/` の**純粋関数**（テストが最も安く、依存ゼロ）
2. 使う、かつコンポーネント固有 → **コンポーネント内に置く**（早すぎる抽出をしない）
3. 使う、かつ2箇所以上で使う → composable

- **根拠**：純粋関数はテストにフレームワーク環境が要らず、コストが桁違いに安い
- **対価**：抽出のタイミングを判断する必要がある

### C-13. composable の命名と制約

- 命名は `use` ＋ **返すものを表す名詞または動詞句**（`useUserProfile`、`useIntersectionObserver`）。
  **`useUtils` `useHelpers` `useCommon` は禁止**（単一責務違反のシグナル）
- **DOM を生成しない／テンプレートを持たない。**返すのは state と関数のみ
- **トップレベルでのみ呼ぶ。**条件分岐・ループ・非同期の後で呼ばない
- 返り値は名前付きの ref / computed を持つ**プレーンオブジェクト**（分割代入で反応性を失わないため）
- **1回しか使わないロジックを composable に出さない。**抽出は2回目の使用時

### C-14. モジュールスコープの可変値を composable に持たせない

- **根拠**：SSR で**リクエスト間の状態汚染**を起こす。フレームワークが提供する SSR 安全な状態機構を使う

## デザイントークンとスタイル

### C-15. トークンは3層とし、参照方向を一方通行にする

```
component → semantic → primitive
```

| 層 | 例 | 規定 |
| :--- | :--- | :--- |
| primitive | `--blue-500`、`--space-4` | 生の値。**コンポーネントから直接参照禁止** |
| semantic | `--color-text-default`、`--color-bg-danger` | 用途。**コンポーネントが参照するのは原則ここだけ** |
| component | `--button-bg-hover` | 必要な場合のみ。semantic を参照する。**追加は例外扱いとし、理由を書く** |

- **強制**：Stylelint のカスタムプロパティ命名規則、または生成スクリプトによる検証
- **根拠**：命名は**値ではなく用途**で行う（`color.action.primary`、`blue-500` ではない）。
  値で命名すると、ダークモードやリブランドのたびに全参照箇所の手動移行が発生する
- **対価**：3層は小規模にはオーバーヘッド。**primitive + semantic の2層で足りるプロジェクトは多い。**
  component 層は「マルチブランド／深いカスタマイズを外部に提供する」場合の装置

**付随ルール**

- **トークンは単一情報源のファイルで定義し、そこから CSS custom properties を生成する。**手書きの重複定義を作らない
- **テーマで変わりうる値は必ず semantic を経由する。**
  ダークモードは semantic の再定義だけで成立させ、**コンポーネント側にテーマ分岐を書かない状態を目標にする**
- ランタイム境界は CSS custom properties（ビルド時に消える変数はテーマ切替を担えない）
- semantic の命名は難しく、機械的に「用途で命名」すると
  `color-text-default-secondary-subtle-hover` のような名前が生えます。**層の数より命名の粒度設計が実質的な問題**

### C-16. カスケードレイヤーの順序を1回だけ宣言する

```css
@layer reset, tokens, base, layout, components, utilities;
```

以降このリストを変更するのは**設計変更**として扱います。

- **強制**：Stylelint。層外への記述を禁止する
- **根拠**：カスケードに詳細度より先に評価される段を追加することで、
  「詳細度を詳細度で殴る」「`!important` で押し切る」という CSS 最大の負債クラスが構造的に消える
- **対価**：**DevTools で「なぜこのルールが負けたか」が詳細度から読めなくなる。**
  チーム全員が層構成を理解していないと逆効果

**`!important` を禁止します**（第三者ライブラリの上書きを除き、その場合は専用の最上位層を用意する）。
**層外に書かれた CSS は全層に勝つ**ため、層外への記述も禁止します。
**レイヤー内の `!important` は優先順が逆転する**（レイヤー順が逆になる）ので、これを規約に明記します。

### C-17. `ui/` のレスポンシブはコンテナクエリを既定とする

メディアクエリはページ骨格（`layout/`）でのみ使います。
**`ui/` のコンポーネントにビューポートブレークポイントを書きません。**

- **根拠**：コンポーネントが「自分がどのページのどこに置かれたか」を知る必要をなくす。
  ビューポート基準だと、サイドバーの Card とメイン領域の Card を区別できず、
  **同じコンポーネントのレイアウト違いバリアントを量産する**
- **対価**：コンテナ要素が必要になり、**追加の DOM ラッパーを強いることがある。**
  コンテナ自身にはスタイルを当てられない（自己参照不可）

### C-18. 方向を持つプロパティは論理プロパティで書く

`margin-inline`、`padding-block`、`inset-inline-start`、`text-align: start`。
物理プロパティは「物理的にそこでなければならない」場合のみ。

- **対価**：RTL 対応の予定が全くないプロジェクトでは純粋に認知コスト。
  縦書きや将来の i18n を考えるなら安い保険

### C-19. ランタイム CSS-in-JS を新規採用しない

- **根拠**：サーバコンポーネントはブラウザコンテキストを持たないため、
  レンダリング中にスタイルを収集・注入する方式は**構造的に動かない**
- **代替**：ユーティリティファースト、CSS Modules、ゼロランタイム CSS-in-JS

ユーティリティファーストを使う場合、**色・余白・フォントの生値をクラスに直書きしません**
（`text-[#333]`、`mt-[13px]`）。トークン由来のクラスのみ許可し、任意値は lint で禁止します。

## テストと story

### C-20. テストの単位は「コンポーネント＋その子」とし、ユーザが観測できるものだけを assert する

内部 state、内部メソッド、CSS クラス名を assert しません。

クエリの優先順位は **`getByRole(name)` → `getByLabelText` → `getByText`**。
`data-testid` は「他で書けない」ことを PR で説明できる場合のみ。

- **根拠**：実装詳細とは「ユーザーが使わず、見ず、知りもしないもの」。
  実装詳細をテストすると偽陰性（リファクタで壊れる）と偽陽性（壊れているのに通る）の両方を招く。
  **`getByRole` でテストが書けないコンポーネントは、アクセシブルではない**
- **対価**：役割やアクセシブル名が不安定な UI（キャンバス、複雑なグリッド、サードパーティ埋め込み）では
  testid が唯一の現実解。また `getByRole` は他クエリより遅い

**純粋なロジック（日付計算、バリデーション、フォーマッタ）は単体テストが圧倒的に費用対効果が高い**ことを
併記します。統合テスト重視の方針を「単体テストを書かない口実」に使いません。

### C-21. API モックはネットワーク境界に置く

`fetch` / HTTP クライアント / composable を直接モックしません。

- **根拠**：ネットワーク層で傍受するモックは、HTTP クライアントの入れ替えやデータ取得ライブラリの変更でハンドラが壊れない。
  **モックが「呼び出し箇所」ではなく「契約」を記述する**ため、
  単体・統合・story・ローカル開発・E2E で使い回せる
- **注意**：「このURLを呼んだか」を assert しない（それは実装詳細のテスト）

### C-22. `ui/` のコンポーネントは 100% story を持つ

**story が書けないときは、story 側で回避せずコンポーネント側を直します。**

- **根拠**：「story が書けない」＝「隔離して立ち上げられない」＝「不要な依存を抱えている」。
  story は**設計上のカップリングを機械的に発見する装置**
- **対価**：story はコンポーネントの第二の呼び出し元であり、メンテナンス対象が増える。
  **全コンポーネントに義務付けると腐った story が溜まるため、`ui/` 限定にする**

### C-23. 自動 a11y チェックを CI で回す。ただし「緑 ＝ アクセシブル」ではない

- **根拠**：自動検出できるのは監査で見つかる WCAG 問題の**およそ半分強**にとどまるという調査がある。
  残りは人間の判断が必要（代替テキストが実際に説明的か、フォーカス順序が論理的か、エラーメッセージが有用か）
- **規約に明記すること**：CI の自動チェックが緑であることは、アクセシビリティの達成を意味しない

### C-24. 視覚回帰は `ui/` にのみ適用する

feature / page には適用しません。

- **根拠**：最大の失敗要因はフレーキーさ（フォント読み込み競合、アニメーションの中間フレーム、
  遅延画像、サードパーティウィジェット）。**フレーキーな視覚テストは信頼を破壊し、結果として無効化される**
- **前提条件**：決定論性の担保（アニメーション無効化、フォントの事前読み込み、外部リソースのモック）

## 3つの検査

柱Cの境界が正しく引けているかは、次で機械的に検証できます。

1. **隔離して story が書けるか**（`C-22`）
2. **`getByRole` でテストできるか**（`C-20`）
3. **トークンだけ差し替えてテーマが変わるか**（`C-15`）
