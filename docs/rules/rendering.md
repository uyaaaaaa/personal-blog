# レンダリング戦略

[../ARCHITECTURE.md](../ARCHITECTURE.md)（設計原則） / [README.md](./README.md)（表記と適用方法）

このドキュメントは**特定の戦略名を規定しません。**技術が動き続けるため、
規約に戦略名を書き込むと2年で腐ります。規約が持つのは
**「決定表」「既定戦略」「逸脱の記録方法」の3点だけ**です。

個々の技術の現況は [../appendix/](../appendix/) を参照してください。

---

## R-1. ルートは自身のレンダリング戦略を宣言する

各ルートは、採用した戦略をコード上の設定として**明示**します（grep できる状態にする）。
既定戦略はプロジェクトごとに1つ決め、appendix に記載します。

**決定表**

| | 全ユーザ共通 | ユーザ固有 |
| :--- | :--- | :--- |
| **更新が稀（ドキュメント寄り）** | 静的生成（＋ 部分的水和で JS を削る） | 静的シェル ＋ 部分的に差し込み |
| **更新が頻繁（アプリ寄り）** | 増分再生成 / SSR + CDN キャッシュ | SSR（+ streaming）。認証必須なら CSR も可 |

**入口の問い**

> このページはドキュメントか、アプリケーションか。

ドキュメント寄り（LP・記事・カタログ）は静的＋部分的水和。
アプリ寄り（ダッシュボード・エディタ）は SSR / CSR ＋ クライアントキャッシュ。

- **強制**：レビュー。ルート追加時に戦略の宣言があるか確認する
- **根拠**：アプリ全体で単一戦略に統一すると、マーケLPと管理ダッシュボードが同一アプリに同居した瞬間に破綻する。
  一方でルートごとの自由に任せると、パフォーマンス予算もキャッシュ設計も立てられない
- **対価**：ルートごとに戦略の宣言と、逸脱時の ADR が必要になる

---

## R-2. 既定戦略からの逸脱は ADR に記録する

ADR には最低限、次を書きます。

- どのルートか
- なぜ既定では不足なのか（計測値を含む）
- 何を失うか
- **撤退条件**（この戦略をやめる判断基準）

---

## R-3. 公式に experimental / 本番非推奨とされている機能を本番で使わない

採用する場合は ADR に**撤退計画**を含めます。

- **強制**：ADR 必須
- **根拠**：[platform.md](./platform.md) の Baseline ルール（`P-1`）を、フレームワーク機能にも同じ形で適用する。
  ブラウザ機能に適用している基準を、より変化の速いフレームワーク機能に適用しないのは一貫しない
- **対価**：新機能の採用が遅れる

---

## R-4. ストリーミング／部分プリレンダリングの採用は RUM を前提条件とする

計測がない状態での導入を認めません。

- **強制**：ADR のチェック項目
- **根拠**：各ホールの到達時間が見えないと、境界を細かくすべきか粗くすべきか判断できない。
  また INP はラボ環境で測定できないため RUM が必須（`P-12`）
- **対価**：可観測性の整備が先行投資になる
- **実務報告の目安**：Suspense 境界は1ルートあたり5〜6個程度が上限。
  それを超えるとストリーミングのオーバーヘッドとフォールバック管理の複雑さが並列化の利得を上回る

**これは、規約が「速そうな技術を入れて遅くなる」事故を防ぐ数少ない実効的な歯止めです。**

## R-5. データ取得はルートを所有する層で開始する

→ [state.md `S-16`](./state.md) を参照。

レンダリング戦略とデータ取得は不可分です。
ルートローダに寄せると「ページ全体がデータ待ち」になるため、
**遅い部分を境界で切り出してストリームする設計とセットで**運用します。

なお **SSR の恩恵は初回ロードにのみ適用されます。**
クライアント遷移では消えるため、遷移後の体験は別途設計が必要です。

## 戦略選択にあたっての既知のトレードオフ

規約に「決着済み」と「未決着」を書き分けるための記録です。**いずれも未決着**として扱います。

| 戦略 | 得るもの | 失うもの |
| :--- | :--- | :--- |
| 部分的水和 / islands | JS 量の構造的削減 | **島をまたぐ状態共有が弱い。**画面全体が1つの状態機械であるアプリには不向き |
| サーバコンポーネント | バンドル削減、データソース隣接によるウォーターフォール除去 | **直列化境界という新しい制約とフレームワーク結合。**「複雑さが減る」とは限らない |
| 部分プリレンダリング | 静的シェルと動的部分の両立 | **experimental。**シェルが A/B 実験で変わるなら経済性そのものが消える |
| resumability | hydration コストの理論的解消 | エコシステムが小さく、既存資産があれば移行コストが支配的 |

**共通の出発点**：SSR + hydration の弱点は uncanny valley
（見た目は準備できているのに操作できない）。上記はすべてこの1点への異なる回答であり、
どれが正解かは**ページの性質**によって変わります。だからこそ `R-1` の決定表がルート単位なのです。
