親ドキュメント：[../ARCHITECTURE.md](../ARCHITECTURE.md)

## 分類

### S-1. 状態を6つに分類し、導入前にどれかを判別する

「状態管理」を一枚岩で語りません。分類は**ライブラリの数**ではなく**責務の名前**として導入します。

| 分類 | 所有者 | 置き場所 |
| :--- | :--- | :--- |
| サーバキャッシュ状態 | サーバ | サーバキャッシュ層／ルートローダ |
| URL 状態 | URL（ユーザが共有可能） | ルータの search params |
| フォーム（ドラフト）状態 | 編集中のユーザ | フォーム単位 |
| 一時 UI 状態 | 単一コンポーネント | ローカル state |
| グローバルクライアント状態 | アプリ全体 | ストア（**最後の手段**） |
| マシン／セッション状態 | 明示的な有限状態 | union 型 / statechart |

- **強制**：PR テンプレのチェック項目
- **根拠**：サーバキャッシュと UI 状態は本質的に異なる問題（失効、重複排除、再取得）を持つ。
  両者を混ぜることが状態管理における最大の設計ミス
- **対価**：分類の判断が毎回1つ増える

### S-2. URL に置くべきかを一問で判定する

> リロード・共有・戻るボタンで保持されるべきか？

Yes なら URL です。典型：一覧のフィルタ／ソート／ページ番号／タブ／検索語／詳細モーダルの対象 ID。
**これをローカル state に置いたらレビューで差し戻します。**

- **強制**：PR テンプレのチェック項目
- **根拠**：ディープリンク可能性は機能の到達可能性そのもの。
  URL は**サーバとクライアントで共有できる唯一の状態表現**なので、SSR との整合が自動で取れる
- **対価**：URL が長くなる。共有される前提なので、載せる情報を選ぶ必要がある

**付随ルール**

- **URL 状態は必ずスキーマで parse してから使う**（`S-17`）。ユーザが編集できる生テキストである
- **履歴モードを明示する。**ユーザの意図的なナビゲーションは `push`、タイピング中の逐次更新は `replace`。
  検索ボックスの1文字ごとに履歴エントリを作らない
- **`pushState` / `replaceState` にはブラウザ側のレート制限がある**（Chrome/Firefox ≒50ms、Safari ≒120ms）。
  スライダーや検索入力などの高頻度更新はスロットル必須
- **PII・トークン・機密フィルタ条件を URL に載せない**（Referer / ログ / 分析ツールに漏れる）
- URL 長の実用上限（目安2000文字）を超える状態は、URL ではなくサーバ側の保存済みビューにする

### S-3. 派生値は保存せず計算する

props や既存の state から計算できる情報を state に置きません。

- **強制**：なし（ガイドライン）
- **根拠**：同じデータが複数の state に重複すると同期が必要になり、矛盾した状態が表現可能になる
- **対価**：重い計算は毎レンダー走る。**メモ化を先に入れず、まず計測する**

あわせて次を守ります。

- 常に同時に更新する2つ以上の state は、1つに統合する
- 深い階層の state は避け、可能な限りフラットにする
- 派生値は読み取り専用として扱い、変更するときは元の state を更新する

### S-4. Effect / watch を「state → state」の同期に使わない

正当な用途は**外部システムとの同期のみ**（DOM API、購読、計測、フレームワーク外のライブラリ）。

| アンチパターン | 代わりに |
| :--- | :--- |
| Effect でデータ変換 | レンダー時（コンポーネント最上位）で変換する |
| Effect でユーザ操作に反応 | イベントハンドラで処理する |
| 派生値を state に保持 | レンダー中に計算する（`S-3`） |
| prop 変化で state をリセット | 外側から `key` を渡して別インスタンスにする |
| Effect の連鎖 | レンダー中に計算し、イベントハンドラで一括更新する |
| Effect で親に通知 | 同一のイベントハンドラ内で両方の state を更新する |

- **強制**：レビューの明示チェック項目
- **根拠**：Effect が走る時点では「ユーザが何をしたか」が失われている。連鎖した Effect は非効率かつ脆い
- **対価**：なし。これは規約に書ける最も費用対効果の高いルールの1つ

**どうしても Effect でフェッチする場合は、cleanup による stale レスポンス破棄を必須**とします。
ただし原則はキャッシュ層／ルートローダに寄せます（`S-16`）。

### S-5. boolean フラグを並列させず、判別可能な union で表す

`isLoading` `isError` `isSuccess` を並べると状態空間は 2^n に爆発し、その大半は到達不能または不正です。

```ts
type State =
  | { tag: 'idle' }
  | { tag: 'loading' }
  | { tag: 'error'; error: Error }
  | { tag: 'ready'; data: Data }
```

- **強制**：レビュー。型定義の追加時に確認する
- **根拠**：不正状態を型で表現不能にする
- **対価**：分岐の記述がやや冗長になる

**「データがあるか」と「通信中か」は別の軸として設計します。**
これを分けないと「背景で再取得しながら古いデータを見せる」UX が表現できません。

3つ以上の状態と分岐のある遷移（ウィザード、決済、アップロード、再接続）に限り statechart ライブラリを検討します。
それ以下は union 型で足ります。**「状態機械を使ったか」ではなく「不正状態を型で表現不能にしたか」**が判定基準です。

## サーバキャッシュ（決定②）

### S-6. リモートデータをグローバルストアの state に格納しない

ストアに入れてよいのは、**サーバに対応物が存在しない値だけ**です。

- **強制**：`{ target: './src/**/store', from: './src/**/api' }` を `import/no-restricted-paths` で禁止
- **根拠**：所有していないデータをストアに置くと、キャッシュ・失効・重複排除・再取得を全部自前で実装することになる
- **対価**：クライアント専用の同期的 state が支配的なアプリでは、この規約は窮屈になる（`S-10` の例外）

### S-7. サーバキャッシュから読んだ値をローカル state にコピーしない

例外はフォームのドラフトのみ（`S-12`）。

### S-8. 書き込み後の整合は invalidate を既定とする

キャッシュへの直接書き込み（`setQueryData` 等）は、**計測で問題が確認された箇所だけの最適化**です。
採用する PR には計測結果を書きます。

- **強制**：`setQueryData` 相当を `no-restricted-imports` の**警告**にし、理由コメントを必須にする（error にはしない）
- **根拠**：サーバを正とすることで、サーバ側の正規化結果との乖離が生まれない
- **対価**：**invalidate → 再取得の往復が入る。これは意図的に受け入れる。**
  書いておかないと、往復が気になった開発者が個別にキャッシュ書き込みを撒き始め、「どちらが真か」が曖昧になる

### S-9. 楽観的更新の実装方式は表示箇所の数で決める

| 表示箇所 | 方式 |
| :--- | :--- |
| 1つ | mutation の variables から描画する（コード量が少なく、推論しやすい） |
| 複数 | キャッシュを書き換える。`onMutate` スナップショット → `onError` ロールバック → `onSettled` invalidate の**3点セット必須** |

**楽観的更新は、ユーザの体感が実測で問題になっている操作にだけ適用します。**
無条件に適用すると、ロールバック分岐と「サーバが別の正規化結果を返す」ケースの複雑性だけが増えます。

### S-10. 正規化ストアを導入してよい条件

次の**いずれか**に該当する画面のみ。ADR を1本書きます。

- 同一エンティティが1画面に多数出現し、かつ WebSocket 等のリアルタイム更新が入る
- クライアント専用の同期的な state が支配的（エディタ、キャンバス、コラボ編集）

- **強制**：ADR 必須
- **根拠**：サーバキャッシュ層はクエリキーごとの独立スナップショットを持つため、
  正規化ストアを重ねると同じデータが2箇所で正規化され、「どちらが真か」を人間が管理し始める
- **対価**：条件に該当する画面では、キャッシュ層の invalidate 機構を実質使わなくなる

### S-11. `staleTime` はプロダクト要件として宣言する

**「どれだけ古いデータを見せてよいか」であって、性能パラメータではありません。**
ドメイン別の表を規約に持ち、未指定のクエリはレビューで差し戻します。

| ドメイン例 | staleTime |
| :--- | :--- |
| マスタデータ（分類、設定） | 分〜時間 |
| ダッシュボード、一覧 | 秒 |
| 在庫、課金、権限 | 0 |

- **強制**：レビュー。デフォルト値をプロジェクト側で明示的に設定する
- **根拠**：長くすると「他人の更新が見えない」問題が UX 上のバグとして現れる
- **対価**：ドメインごとの合意形成が必要

**キャッシュキーは階層構造を反映した配列に統一**し（`['user', id, 'posts', filters]`）、
キーファクトリを1箇所に集約します。文字列直書きは禁止です。キーは実質「依存配列」であり、
これが崩れるとキャッシュの正しさが崩れます。

### S-12. フォームは「サーバ値」と「ユーザの差分」の2層で表現する

- **強制**：なし（ガイドライン）。ただし**どちらを選んだかを PR に書く**
- **根拠**：Effect でサーバ状態にフォームをリセットする実装は、バックグラウンド再取得と壊滅的に相性が悪い。
  **ユーザが編集中の値が勝手に戻る**
- **対価**：差分方式は実装量が明確に増える。単純な設定画面では全体コピーで足りる

**編集中は当該クエリのバックグラウンド再取得を止めるか、差分方式にします。**
「編集中に勝手に値が戻る」は仕様バグとして扱います。

送信は mutation → 成功時に該当キーを invalidate。フォームの成功状態はサーバ応答に従属させます。

## 失敗と待ち

### S-13. データを表示するコンポーネントは4状態すべてを持つ

**loading / error / empty / success。**empty（0件）を error や loading に混ぜません。

### S-14. 境界の配置はワイヤーフレーム上で決めてレビューする

Suspense 境界とエラー境界の配置は UX 設計そのものです。
「レイアウトの安定領域」と「独立して失敗・再試行できる領域」の単位で置きます。

- **エラー境界は最低2層**：アプリ全体（最終防衛線＋計測）と、機能ブロック単位（部分的な劣化）
- **エラー境界が捕捉するのはレンダー中のエラーだけ。**イベントハンドラ・非同期・境界自身のエラーは届かない。
  明示的に境界へ投げるか、その場で扱う方針を決める
- **Suspense は Effect やイベントハンドラ内のフェッチを検知しない。**既存コードを救う機構ではない
- 過剰に細かく置かない。スピナーだらけになると体感が悪化する

**劣化方針を各領域で宣言します。**主要コンテンツが失敗したらページ全体をエラーに、
副次ウィジェットが失敗したらその領域だけ縮退表示。

### S-15. リトライ方針を表にする

| 対象 | 方針 |
| :--- | :--- |
| GET | 自動リトライ（指数バックオフ） |
| 4xx | 即失敗（リトライしない） |
| POST / PUT / DELETE | **自動リトライ禁止**（冪等キーがある場合のみ許可） |
| オフライン | pause し、復帰時に再開 |

- **根拠**：多くのキャッシュライブラリは既定で自動リトライする。**非冪等な操作にこれを適用してはいけない**

### S-16. fetch-on-render を既定にしない

ルート遷移に必要なデータは**「ルートを所有する層」**（ルートローダ／サーバコンポーネント／ページの setup）で開始します。

- **兄弟のクエリは必ず並列。**直列は「前の結果が本当に必要」な場合のみで、その理由を依存キーとしてコードで表現する
- **依存クエリは可能な限り API 側で1リクエストに畳む**か、サーバ側に移す
- **コード分割の境界とデータ取得の境界を重ねない**（lazy チャンクの中で初めて fetch が始まる構造を避ける）
- SSR 時は `staleTime` を 0 のままにしない（hydration 直後に全部再取得される）

- **強制**：なし（ガイドライン）。レビューでウォーターフォールを指摘する
- **根拠**：コストはレイテンシに比例して増幅する。**250ms × 4往復 = 1000ms が、平坦化で 500ms になる**
- **対価**：ルートローダに寄せると「ページ全体がデータ待ち」になるため、
  遅い部分を境界で切り出してストリームする設計と**セットで**運用する必要がある

## 境界での型契約

### S-17. 外部から入る値はすべて境界で parse する

対象：HTTP レスポンス、URL の search params、`localStorage` / `sessionStorage`、`postMessage`、
WebSocket、環境変数、フォーム入力。

- **強制**：レスポンスへの `as` キャストを lint で禁止。`fetch` を直接呼ぶ箇所を1モジュールに閉じる
- **根拠**：**TypeScript の型は実行時に消える。**`await res.json() as User` は型注釈であって検証ではなく、
  API の変更・null 混入・部分障害はアプリ内部の深いところで初めて壊れる
- **対価**：バンドルサイズと CPU コストが乗る。大量のリストでは無視できない

**付随ルール**

- アプリ内部の型は**スキーマから導出**し、手書きの型と二重管理しない
- OpenAPI / GraphQL がある場合は**スキーマ生成まで codegen し、生成物を実行時バリデータとして使う**（型だけの codegen で止めない）
- **未知のフィールドは許容（strip / passthrough）を既定にする。**厳格すぎるとサーバの後方互換な追加で壊れる
- parse 失敗は「アプリのバグ」ではなく「契約違反」として通常のエラー状態（`S-13`）に落とし、計測する。
  リスト要素単位で不正要素を捨てる degrade も選択肢に持つ
- 境界の粒度を選ぶ：重要な書き込み系・金額・権限は厳格 parse、大量の表示専用データは浅い parse

## Context / provide-inject（決定③）

### S-18. 用途を3つに分類し、混在させない

| 用途 | 手段 | 規定 |
| :--- | :--- | :--- |
| ① DI（アプリ寿命級・低頻度更新） | Context / provide | テーマ、ロケール、認証セッション、機能フラグ、テスト時の差し替え。**可** |
| ② コンポーネント内部の暗黙共有 | Context / provide | compound components 専用。`model/` に置き、モジュール外に公開しない |
| ③ 頻繁に更新される共有状態 | 購読ベースのストア | **Context で代用しない** |

- **根拠**：Context は DI 機構であって状態管理ツールではない（履歴も middleware も選択的購読もない）。
  ただし用途②を分類せずに一律規制すると compound components の実装が規約違反に見え、規約の信頼性が落ちる

### S-19. Context は型付きキーと専用の composable / hook 経由で消費する

生の `useContext` / `inject` をコンポーネントに直接書きません。

### S-20. 用途②の Context は、提供者が存在しない場合に明示的に throw する

暗黙のデフォルト値でごまかしません。

- **根拠**：compound の子を親の外に置いた誤用は**型では検出できない。**実行時に落とすのが唯一の防御

### S-21. 頻繁に変わる値と変わらない値を同一の Context に混ぜない

混ぜたくなったら、それは用途③のサインです。

- **根拠**：React Context（値の変更で全 consumer が再レンダー）と Vue provide/inject（ref なら粒度が保たれる）
  には挙動の非対称性がある。**更新粒度の保証をフレームワーク実装に依存させない**ための規定

### S-22. Context の提供者と消費者は同一の機能モジュール内に閉じる

- **強制**：`A-1` の `entry-point` が自動的に強制する（`model/` は外部から import 不可）

## PR テンプレのチェック項目

柱Bは lint で完全には縛れません。次を PR テンプレに置きます。

- [ ] 追加した state は `S-1` のどの分類か
- [ ] リロード・共有・戻るで保持すべき状態を、URL ではなくローカル state に置いていないか（`S-2`）
- [ ] Effect / watch を state の同期に使っていないか（`S-4`）
- [ ] 新規クエリに `staleTime` を設定したか（`S-11`）
- [ ] キャッシュへの直接書き込みを入れたなら、計測結果を書いたか（`S-8`）
- [ ] 新しい表示に loading / error / **empty** / success の4状態があるか（`S-13`）
- [ ] 非冪等な操作に自動リトライが効いていないか（`S-15`）
