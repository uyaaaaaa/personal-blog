## ブラウザサポート

### P-1. Baseline を採用可否のルールにする

「対応ブラウザ」を議論ではなくルールで決めます。

| 状態 | 扱い |
| :--- | :--- |
| **Widely available** | 無条件採用可 |
| **Newly available** | プログレッシブエンハンスメントとして使う場合のみ可（フォールバックが必須） |
| **Limited availability** | 原則禁止。例外は ADR を1本書く |

- **強制**：`browserslist` に Baseline 基準を設定、`eslint-plugin-compat`、Stylelint の Baseline ルールを CI 必須
- **根拠**：「手元の Safari で動いた」を根拠にしない
- **対価**：Baseline は**コアブラウザの最新安定版**の話であり、実ユーザの古い OS はカバーしない。
  実測の UA シェアと併用する

**「Ship した ≠ 使える」を規約に事例として書きます。**
Popover は Firefox に載った後も、Safari で iOS のライトディスミス不具合が直るまで Baseline 判定が遅れました。
機能が載ったことと相互運用が達成されたことは別です。

### P-2. 機能検出のみを使う。バージョン判定・UA 判定を禁止する

エンハンスメントは必ず機能検出でガードします（`@supports`、`'startViewTransition' in document` 等）。

- **強制**：`no-restricted-properties` で `navigator.userAgent` を禁止

## HTML を基底層にする

### P-3. オーバーレイ層を自作しない

| 用途 | 手段 |
| :--- | :--- |
| モーダル（背景を操作させない） | `<dialog>` + `showModal()` |
| 非モーダルの浮動UI（メニュー、トースト、ツールチップ） | `popover` 属性 |

**自前のフォーカストラップ実装の新規追加を禁止します。**

- **根拠**：`showModal()` は inert・フォーカストラップ・トップレイヤ・Esc ハンドリングをネイティブに持ち、
  **開いたときの初期フォーカスと閉じたときの復帰**まで担う
- **注意**：`popover` は意味論を持たないため、適切な要素と ARIA を自分で付ける。
  モーダル性が必要なら `<dialog>` を使う

### P-4. 開閉・アコーディオンは `<details>` に寄せる

FAQ・折りたたみセクション・排他アコーディオンは、ローカル state ではなく `<details>` で表現します。

- **根拠**：開閉状態、キーボード操作、find-in-page（閉じた中身も検索でヒットして自動展開）をネイティブに持つ
- **注意**：排他アコーディオンとアニメーション関連の機能は比較的新しいため、
  アニメーションはエンハンスメント扱いにし、非対応環境では瞬時開閉にフォールバックさせる。
  `<summary>` の中に他のインタラクティブ要素を入れない

### P-5. フォームの単一情報源は `<form>` の DOM とする

コンポーネント state を「フォームの真の値」にしません。送信時はフォーム要素と submitter から `FormData` を作ります。

- **根拠**：submitter を渡せば「どのボタンで送信されたか」が取れるため、
  **1つのフォームに複数アクション**が JS 状態なしで表現できる
- **付随ルール**
  - 宣言できる制約は HTML 属性に書く（`required` `type` `min` `max` `pattern` `minlength`）。
    JS はその上に**追加**するのであって置き換えない
  - **バリデーションの単一情報源は HTML 属性 ＋ サーバ側スキーマ。**
    クライアント JS バリデーションは第3の情報源を作らない（同じスキーマから属性を生成する）
  - スタイルは `:user-invalid` / `:user-valid` を使う（`:invalid` は初期表示で赤くなるため禁止）
  - 相関バリデーションのみ `setCustomValidity()` + `checkValidity()` / `reportValidity()`
  - `action` / `method` を必ず書く

### P-6. `setCustomValidity()` を使う箇所では ARIA を自分で貼る

- **根拠**：**`setCustomValidity()` は ARIA を一切設定しない。**
  スクリーンリーダーに伝えるには `validationMessage` を DOM に写し、
  `aria-describedby` / `aria-invalid` を自分で設定する必要がある
- **注意**：ネイティブのエラーバブルはスタイル不能で、文言は基本ブラウザ言語依存。
  i18n を厳密にやるなら `novalidate` ＋ `validity` を読んで自前描画に切り替える判断が必要

## アクセシビリティ

### P-7. `<div onClick>` を禁止する

`<button>` / `<a href>` / `<input>` / `<label>` / `<details>` / `<dialog>` を先に検討し、
使えない理由を PR に書きます。

- **強制**：lint（`jsx-a11y` 系、`vuejs-accessibility` 系）
- **根拠**：ARIA 第一のルール — 必要な意味論と振る舞いを既に備えたネイティブ要素が使えるなら、そちらを使う。
  調査では**ARIA があるページは無いページより検出エラーが平均41%多い。**ARIA は能力ではなく負債になりうる

### P-8. コンポーネントの型定義にキーボード契約を明記する

このウィジェットは Tab で入る／出る、矢印で移動する、Esc で閉じる、といった契約を型とドキュメントに書きます。
実装仕様として WAI-ARIA APG の各パターンを参照します。

- **注意**：**APG は規範仕様ではなく実装ガイド。**APG 通りに書いても支援技術の実装差で通らないパターンがある
  （特に Combobox と Grid）。「APG 準拠」をゴールにせず、実機のスクリーンリーダーでの確認を受け入れ基準に入れる

### P-9. フォーカスの所有権を1箇所に定める

ルート遷移後のフォーカス移動は誰の責務か、モーダルを閉じたとき誰が呼び出し元にフォーカスを戻すか。

- **根拠**：**所有者が曖昧だとフォーカスは必ず飛ぶ。**
  ネイティブ `<dialog>` は初期フォーカスと復帰を持つので、原則ネイティブに委譲する

### P-10. 合成ウィジェット内は Tab ではなく矢印キーで移動する

**既定は roving tabindex**（常に1つだけ `tabindex="0"`、他は `-1`）。

| 方式 | 使いどころ | 作者の責任 |
| :--- | :--- | :--- |
| roving tabindex | **既定** | 少ない。DOM フォーカスが実際に動くのでブラウザが自動でスクロールし、`:focus` でスタイルできる |
| `aria-activedescendant` | 入力欄にフォーカスを残したまま候補を移動する場合（コンボボックス） | **アクティブ表示のスタイリングとスクロール追従が作者の責任**（`:focus` は使えない） |

**クリック／タップ時も同じ更新をします。**キーボードと同様に更新しないと、
ポインタとキーボードを行き来したときに壊れます。

### P-11. ライブリージョンは既定 `polite` とする

`assertive` は「今すぐ中断してよい」ものだけ（決済失敗、セッション切れ）。

- **付随ルール**
  - リージョン要素は**空の状態で先に DOM に存在させ**、後からテキストを入れる
    （動的に挿入した直後に文字を入れると読まれない）
  - `aria-atomic` を意図的に指定する
  - **「知らせたいから」ではなく「知る必要があるから」announce する**

## パフォーマンス

### P-12. Core Web Vitals は実ユーザの75パーセンタイルで評価する

| 指標 | Good | Needs improvement | Poor |
| :--- | :--- | :--- | :--- |
| LCP | ≤ 2.5s | 2.5–4.0s | > 4.0s |
| INP | ≤ 200ms | 200–500ms | > 500ms |
| CLS | ≤ 0.1 | 0.1–0.25 | > 0.25 |

**ラボ値ではありません。**INP はラボ環境では測れない（実インタラクションが必要）ため、RUM が必須です。

- **根拠**：INP は FID を置き換えた指標で、全インタラクションのフルサイクル
  （入力遅延／イベントハンドラ実行／次の描画まで）を測る。
  **FID で良かったサイトが INP で落ちるのは、ハンドラ実行と描画までが新たに計測対象になったから**であり、
  これはレンダリングアーキテクチャの問題

### P-13. LCP はサブパートで議論する

TTFB ／ リソース発見遅延 ／ リソース読込時間 ／ 要素描画遅延。この配分がボトルネックの所在を一意に決めます。
目安は「発見遅延＋描画遅延の合計が全体の20%以内、TTFB とリソース読込がそれぞれ40%」。

### P-14. LCP 候補要素に `loading="lazy"` を付けない。初期 HTML の `<img>` として出す

- **強制**：lint
- **根拠**：LCP 画像が CSS 背景・JS 注入だと**プリロードスキャナが見つけられない。**
  これはアーキテクチャ制約であり、**クライアント側でのみ描画される英雄画像を禁止**する

LCP 候補には優先度を明示します（`fetchpriority="high"`）。

### P-15. 長いタスクを分割し、メインスレッドを明け渡す

入力ハンドラでは**見た目の更新に必要な最小限だけ**を行い、残りは次のフレーム以降へ回します。

- **根拠**：50ms を超えるタスクが INP を直撃する
- **付随ルール**：**大きな DOM ツリー自体がプレゼンテーション遅延の原因**になる。
  仮想化 / `content-visibility` / ページ分割は、パフォーマンス施策ではなく**アーキテクチャ判断**として扱う

### P-16. CLS はデザインシステムの責務として扱う

**コンポーネントが自分の占有領域を宣言します。**

- **強制**：画像・動画・iframe に `width`/`height` 属性または `aspect-ratio` を必須化（lint）
- **付随ルール**
  - フォントはフォールバックのメトリクス調整を既定にする（シフトを生む表示方式を避ける）
  - スケルトンの高さを実コンテンツと一致させる
  - 広告・埋め込み・バナー用の領域は事前に確保する

### P-17. `content-visibility` と `contain-intrinsic-size` は対で書く

- **強制**：Stylelint で対を必須にする
- **根拠**：**`contain-intrinsic-size` を省くと高さ0として扱われ**、スクロールバー長・`scrollIntoView`・
  アンカーリンクの着地位置がすべて壊れる。「初期表示は速いが Cmd+F が変な場所に飛ぶ」典型的バグ
- **注意**：Safari はスキップされたコンテンツを find-in-page の対象にしない（Chrome との挙動差）。
  検索性が要件なら Safari で検証する

### P-18. `unload` イベントの使用を禁止する

teardown は `pagehide` に書きます。復帰時の再接続・再取得は `pageshow` の `event.persisted` 分岐で行います。

- **強制**：lint
- **根拠**：**戻るボタンの体感速度は自前のキャッシュではなく bfcache が決める**（レイアウトシフトも発生しない）。
  ところが**リスナー1つで壊れる**
- **付随ルール**
  - サードパーティスクリプトが `unload` を仕込むのを `Permissions-Policy: unload=()` で封じる
  - CI または定期監査で bfcache 阻害要因を計測する
  - **SPA のソフトナビゲーションは bfcache イベントではない。**
    クライアントルーティングでは自前でスクロール復元と状態復元を書く必要がある

## ネットワーク

### P-19. キャッシュヘッダは二層で書く

| 対象 | ヘッダ |
| :--- | :--- |
| コンテンツハッシュ付きアセット（JS/CSS/画像/フォント） | `public, max-age=31536000, immutable` |
| **HTML エントリドキュメント** | **`no-cache` ＋ ETag** |
| API レスポンス / SSR ページ | `max-age=N, stale-while-revalidate=M` |

- **根拠**：**HTML を長くキャッシュすると、古い HTML が古いハッシュ名を指し続け、デプロイがユーザに届かない。**
  これがハッシュ戦略の最大の落とし穴。`immutable` を省くとリロード時に全アセットへ条件付きリクエストが飛ぶ
- **注意**：CDN 層とオリジンで `Cache-Control` の解釈が分かれる（`s-maxage`、`stale-while-revalidate` のサポート差）

### P-20. リソースヒントは「憲章」ではなく「例外」として扱う

| ヒント | 上限の目安 | 性質 |
| :--- | :--- | :--- |
| `preload` | 2〜3個 | **必須フェッチ。**ブラウザは必ず落とす。10個入れると高優先度リクエストで帯域を奪い合い逆効果 |
| `modulepreload` | — | ES module のパース・コンパイル、静的 import の再帰解決まで前倒しする。**モジュールツリーのウォーターフォールを平坦化する唯一の手段** |
| `preconnect` | 4〜6オリジン | 確実に使うオリジンだけ。DNS+TCP+TLS を消費し接続を約10秒保持する。**未使用の preconnect は純粋な浪費** |

**レビュー観点**：このヒントを消したらウォーターフォールがどう変わるか説明できるか。
説明できないヒントは削除します。

## Web Components

### P-21. Web Components の採用判定は一問で行う

> 2つ以上のフレームワークで同じコンポーネントを実際に使う予定があるか？

**No なら通常のフレームワークコンポーネント。**Yes でも **Shadow DOM は既定 OFF** とし、
スタイルの漏れが実証的に問題になったときだけ有効化します。

- **強制**：ADR 必須
- **根拠**：「Web Components の問題の約8割は、実は Shadow DOM の問題」。
  とりわけ **`aria-labelledby` / `aria-describedby` / `aria-controls` は ID 参照であり Shadow 境界を越えられない。**
  コンポーネントの外のラベルと中の input を繋げないという根本的な非互換がある
- **対価**：フレームワーク非依存という利得は仮説であり、検証が必要

**効く場所**：デザイントークン層、複数フレームワークが混在する組織横断のデザインシステム、
葉ノードの自己完結UI（アイコン、コードハイライタ、地図、チャート）、既存アプリへの段階的な埋め込み。

**痛む場所**：フォーム（form-associated custom elements が必須、ARIA 系プロパティの実装差が残る）、
アクセシビリティ（上記）、SSR/SSG、型付き props と合成の DX、バンドルサイズ。

**常に並べるべき対抗案**：Shadow DOM を避けた Web Components は実質「軽量なフレームワーク非依存コンポーネント」であり、
多くの場合 **CSS トークン ＋ 素の HTML/CSS パターン集**で代替できます（＝ Web Components 自体が不要）。

## プログレッシブエンハンスメント

### P-22. 中核のユーザージャーニーに限り、JS なしで機能が成立することを受け入れ基準に含める

**適用範囲を限定します。**中核のユーザージャーニー（閲覧・検索・送信・決済）のみが対象で、
管理画面のリッチな編集 UI 等は対象外です。

- **強制**：PR テンプレの質問項目
- **根拠**：プログレッシブエンハンスメントは反 JavaScript ではなく**反・単一障害点。**
  全機能をノー JS で動かすことがゴールではない
- **対価**：線を引かないと規約が空文化する

**PR テンプレの質問**

- [ ] JS がロードされる前にユーザーがクリックしたら何が起こるか
- [ ] JS が失敗したときの挙動は受け入れ可能か
- [ ] エンハンスメントは機能検出でガードされているか（`P-2`）
