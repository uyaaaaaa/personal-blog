# 柱A：モジュール境界と依存方向

> 依存は一方向にのみ流れる。

親ドキュメント：[../ARCHITECTURE.md](../ARCHITECTURE.md)

---

## 公開面（決定①）

### A-1. 機能モジュールの公開面はディレクトリ構造で表現する

各機能モジュールは固定語彙のセグメントを持ちます。外部から import してよいのは**公開セグメント配下のファイルのみ**で、
非公開セグメントへの import は lint error とします。

| セグメント | 役割 | 外部から |
| :--- | :--- | :--- |
| `ui/` | 描画コンポーネント | **可** |
| `api/` | この機能が外に見せる関数・型・フック | **可** |
| `model/` | 状態・ドメインロジック | 不可 |
| `lib/` | この機能専用のヘルパ | 不可 |

**この4語は固定語彙です。**プロジェクトの都合で増やす場合は、規約本体の改訂として扱います
（lint パターンが追随できないと `A-1` そのものが機能しなくなるため）。

- **強制**：`eslint-plugin-boundaries` の `entry-point`（`default: "disallow"`）
- **根拠**：公開面が grep で分かる。`features/checkout/ui/` を見れば公開 API が全部見える
- **対価**：セグメント名が規約の一部になる

### A-2. barrel file を新規に作らない

再エクスポートのみを目的とするファイルを作りません。とりわけ `export *` は禁止します。

- **強制**：`no-restricted-syntax` で `ExportAllDeclaration` を error
- **根拠**：tree-shaking とテスト起動時間の実測劣化。`export *` は特にバンドラの未使用判定を困難にする
- **対価**：「1行 import で全部入る」利便性を失う。これは意図した対価

### A-3. import パスの書き分け

モジュール**内部**の import は相対パス、モジュール**外部**への import はエイリアス
（`package.json` の `imports` フィールド、もしくは tsconfig paths）で書きます。

相対パスが `../` を2つ以上遡ったら、それは境界を越えているサインです。

- **強制**：`import/no-relative-parent-imports` 相当、または `no-restricted-imports` のパターン
- **根拠**：エイリアスは境界を跨いだことを視覚的に示す。`package.json` の `imports` はランタイムでも解決されるためビルドツール依存にならない
- **対価**：エイリアス設定を build / test / IDE の3箇所で揃える必要がある

## 依存方向

### A-4. 循環依存は error とする

警告ではありません。CI で必ず落とします。

- **強制**：`madge --circular` または `import/no-cycle`（即時性が要るなら lint、速度が問題なら CI のみ）
- **根拠**：**ESM のセマンティクスとして実際に壊れる。**循環時は先に評価された側が相手の export を
  `undefined` として見るか、TDZ で `ReferenceError` を投げる。ランタイムもバンドラも循環を「解決」しない。
  「今動いているから大丈夫」は import 順が変わった瞬間に崩れる
- **対価**：`import/no-cycle` は大規模リポジトリで lint 時間が跳ねる。`maxDepth` を絞るか CI 専用にする

**循環を壊す標準手順**（この順で試す）

1. 共通部分を第3のモジュールへ抽出する
2. 型のみの依存なら `import type` にする（実行時依存が消える）
3. 依存性注入で向きを逆転させる

**dynamic import による回避は禁止します。**問題を隠すだけで、依存グラフ上は循環が残ります。

**値の循環は禁止、型のみの循環は `import type` を必須とした上で許容**、と切り分けると実務的です。

### A-5. 依存は `shared → features → app` の一方向のみ

逆流と、同一層の横方向 import を lint で error にします。

| 層 | import してよい先 |
| :--- | :--- |
| `app` | `features`, `shared` |
| `features` | `shared`, **自分自身のみ** |
| `shared` | なし（同一 shared モジュール内のみ） |

- **強制**：`eslint-plugin-boundaries` の `element-types`（`default: "disallow"` で許可を列挙）
- **根拠**：層に上下関係を与えると、層間の循環は構造的に発生しえなくなる。残るのは同一層内の循環だけ
- **対価**：`A-13` の破綻点が発生する

### A-6. 機能同士は直接 import しない

異なる機能の合成は **`app` 層1箇所で行います。**

- **強制**：`A-5` の element-types が自動的に強制する
- **根拠**：合成点が1箇所に固定されていれば、機能の追加・削除の影響範囲が読める

## モジュールの切り方

### A-7. 第一分割はドメイン語とする

`src/` 直下の第一分割は `checkout/` `search/` `billing/` のようなドメイン語です。
`components/` `hooks/` `utils/` を第一分割にしてはいけません。

**型別ディレクトリは機能フォルダの内側でのみ使います**（`features/checkout/ui/` は可、`src/ui/checkout/` は不可）。

**判定基準（削除可能性テスト）**：
> この機能が不要になったとき、1つのフォルダを消せば消えるか？

消えないなら、境界が引けていません。

- **強制**：なし（ガイドライン）。ディレクトリ構造のレビューで判定する
- **根拠**：型別構造の失敗は技術的ではなく認知的。1つのユーザーフローを変更するために複数フォルダを飛び回ることになる
- **対価**：機能境界は予測が外れる。初期に切った境界がドメインの実態と合わないと、移動コストが継続的に発生する

**例外**：5画面未満・開発者1〜2名のフェーズでは型別のフラット構成を許可します。
ただし移行閾値を明記します（例：同一ドメインのファイルが8個を超えたら機能フォルダに切る）。

### A-8. 共有への昇格条件

feature 内のコードを共有層へ上げてよいのは、次の**3つすべて**を満たすときだけです。

1. **異なる**機能から**3箇所以上**で必要とされている（2箇所ではまだ複製したままにする）
2. 呼び出し元固有の分岐（`if (isCheckout)` のようなフラグ引数）を含まない
3. その機能のドメイン語彙に依存しない名前が付けられる

- **強制**：なし（ガイドライン）
- **根拠**：「重複は、間違った抽象よりはるかに安い」（Sandi Metz）。
  早すぎる抽象は、新要件のたびにパラメータと条件分岐を足す劣化サイクルに入る
- **対価**：3回目まで待つ間に複製の存在が忘れられる。→ 複製の検出はツール（jscpd 等）に任せ、閾値を CI で監視する

**例外**：セキュリティ・課金・法的要件に関わるロジックは、3箇所を待たず即座に共有化します。

**`shared/` `utils/` `common/` `helpers/` という名前のフォルダを新設しません。**
これらは「置き場所が分からないファイル」の引力になります。共有コードは目的で名付けます
（`formatting/` `http/` `validation/`）。置き場所が分からないファイルは、**使っている機能の中に置く**のが既定です。

### A-9. 降格手順を規約に持つ

共有モジュールに**呼び出し元を判別するフラグ引数が追加されたら、それは誤った抽象のシグナル**です。
分岐を足すのではなく、**インライン展開して各呼び出し元に戻します。**

- **強制**：なし（ガイドライン）。共有モジュールの被 import 数を依存グラフツールで可視化し、レビュー対象にする
- **根拠**：抽象を守る義務感がパラメータと条件分岐を増やし、誰も理解できないモジュールを作る

### A-10. 層を増やしてよい条件

Clean / Hexagonal をフロントに持ち込むとき実際に転移するのは
「依存は内向き」「外部I/Oはアダプタに閉じる」の2点だけです。
UseCase / Repository のクラス階層は転移しません（フロントには永続化がなく、ビジネスルールの正本はサーバにある）。

層の増設は、次の**いずれかが実在する**ときのみ認めます。

- 実装が2つ以上あるポート（テストでの差し替えを含む、具体的な必要が今ある）
- 複数クライアント（Web と React Native 等）でのドメイン共有
- 具体的な移行計画

**実装が1つしかないポート（インタフェース）は書きません。**

- **強制**：ADR 必須
- **根拠**：層を増やすとバンドルが増え、オンボーディングが難しくなる。回収されない抽象はコストのみ
- **対価**：将来の差し替えが必要になったときの改修コストを受け入れる

**ただし、次の2つは規模を問わず守ります。**

- **サーバレスポンスの型（DTO）を `api/` 境界の外に出さない。**境界でアプリ内部の型へ変換する
- **純粋な計算（料金計算、バリデーション、日付・単位ロジック）はフレームワーク非依存の関数に置く**

## 暗黙解決（決定④）

### A-11. ビルド時に注入される依存を限定する

auto-import、コンポーネント自動登録、グローバル型、マジックコメントは、
**フレームワーク組み込みAPI**（`ref` `computed` `watch` `useState` `useRoute` 等）と
**ファイルベースルーティング**に限定します。

### A-12. 自作モジュール間の依存は常に `import` 文として明示する

依存グラフに現れない依存を作りません。自作の composable / util / コンポーネントは、すべて明示 import します。

- **強制**：フレームワークの設定（[appendix/](../appendix/) 参照）＋ 依存グラフの網羅率チェック
- **根拠**：**auto-import が隠すのは「フレームワークへの依存」ではなく「機能間の依存」。**
  後者こそが長期プロダクトで管理したい唯一のものであり、これが見えないと `A-1` `A-4` `A-5` がすべて空文化する
- **対価**：素の状態より DX が落ちる。ただし書かずに済む import の大半（`ref` `computed` の類）は依然として書かずに済む

### A-13. 暗黙解決の新規導入には証明を伴う

新たな暗黙解決の導入提案は、それが柱Aの機械的強制（循環検出・方向ルール・公開面）を
**無効化しないことの証明**を伴うこと。

この形にしておくと、コード生成物・module augmentation・ビルド時注入など、
フレームワークを問わず同じ判断基準が効きます。

## 既知の破綻点

### A-14. 共有コンポーネントが feature ロジックを必要とする場合

`A-5` の最頻出の破綻です。共有UIコンポーネント（`ProductCard`）が feature 固有のロジック
（wishlist、addToCart）へのアクセスを必要とするが、`shared → features` の import は禁止されている。
bulletproof-react の issue #238 は、この問題を未解決のまま残しています。

**規約側の回答は次の順序です。**

1. **共有コンポーネントは振る舞いを注入で受け取る**（props / slot / render prop / provide-inject）。
   共有層が feature を import するのではなく、**feature が共有コンポーネントに振る舞いを渡す**
2. それでも解けないなら、**その UI は共有ではない。**feature 側へ降格させる（`A-9`）
3. 合成が必要なら `app` 層で行う（`A-6`）

**prop drilling が深くなることを理由に、共有層へビジネスロジックを移すことは認めません。**
prop drilling が2階層を超えたら、まず合成（`C-5`）に書き換えます。

## 強制手段の段階導入

| 規模 | 手段 |
| :--- | :--- |
| 全規模 | `import/no-restricted-paths`（方向）＋ `madge --circular`（循環、**error**） |
| 中規模 | `eslint-plugin-boundaries` の `element-types` + `entry-point`（deny-by-default） |
| モノレポ／複数チーム | Nx タグの `depConstraints`（**ドメイン軸と層軸を別タグで直交させる**）、TypeScript project references |

**共通の作法**

- **deny-by-default。**許可を列挙する
- **lint の `message` に規約セクションの URL を埋め込む。**違反者が「なぜ」に到達できないルールは回避される
- **導入は必ずベースライン＋ラチェット**（M-3）

設定例は [appendix/](../appendix/) を参照してください。
