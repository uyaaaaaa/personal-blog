## 表記の約束

各ルールには次の3つを併記します。

- **強制**：どのツールがどう落とすか。ないなら「なし（ガイドライン）」と書く
- **根拠**：なぜそうするか。1〜2行
- **対価**：この決定で何を失うか

**機械チェックできないものを「ルール」と呼びません。**
CI で落ちない規約は、レビュー担当者の記憶力に依存します。人が入れ替わる前提のチームでは、
それは規約ではなく口伝です。強制手段のないものはラベルを「ガイドライン」に変え、期待値を下げておきます。

**根拠のないルールは書きません。** 根拠が書いてあれば、根拠が失効したときに規約ごと廃止できます。
根拠を書かずに残したルールは、失効しても誰にも消せません。

lint の `message` には必ず該当ルールの URL を含めます。ルール ID だけでは、指摘された人が根拠に辿り着けません。

## 既存コードへの適用

**ベースライン＋ラチェット。** 既知の違反をベースラインファイルに固定し、新規違反だけを落とします。
一括修正を前提にしたルール導入は、ほぼ確実に失敗します。

あわせて `eslint-disable` の**件数を計測対象**にします。
増加は「ルールが現実と合っていない」シグナルであり、開発者の規律の問題として扱いません。

## 導入順序

費用対効果順。上から入れます。いずれもベースライン＋ラチェットで導入します。

1. **循環禁止**（`A-4`）— コスト極小・効果最大・議論の余地なし
2. **一方向の依存ルール1本**（`A-5` 〜 `A-6`）＋ lint 強制
3. **状態の分類表**（`S-1`）とレビュー時の判定。特に `S-2`（URL に置くべきか）と `S-4`（Effect で state を同期していないか）
4. **第一分割をドメイン語に**（`A-7`）— 削除可能性テストで検証
5. **共有への昇格条件と降格手順**（`A-8` 〜 `A-9`）
6. **Baseline のブラウザサポートルール**（`P-1`）＋ 禁止 lint 3点（`P-7` `P-14` `P-18`）
7. **トークン3層と `@layer` 順序**（`C-15` 〜 `C-16`）

Vue / Nuxt では `A-11` 〜 `A-13`（暗黙解決の制限）が 1〜2 の前提条件です。
auto-import が有効なままでは依存グラフに import が現れず、`A-4` `A-5` の強制が無言で無効になります。
