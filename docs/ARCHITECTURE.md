# フロントエンドアーキテクチャ規約

React または Vue で構築する長期プロダクト向けの、フレームワーク非依存のアーキテクチャ規約です。
特定のライブラリやバージョンに依存する記述は [appendix/](./appendix/) に隔離しています。

## この規約の読み方

| ドキュメント | 内容 |
| :--- | :--- |
| 本ファイル | メタ規約（規約自体の設計方針）と、4本の柱 |
| [rules/boundaries.md](./rules/boundaries.md) | 柱A：モジュール境界と依存方向（`A-n`） |
| [rules/state.md](./rules/state.md) | 柱B：状態とデータフロー（`S-n`） |

| [appendix/](./appendix/) | フレームワーク固有の実装。**腐ることを前提に隔離した場所** |

## 第0層：メタ規約

具体的なルールより先に、この3つを合意します。これがないと規約は必ず腐ります。

### M-1. 「ルール」と「ガイドライン」を書き分ける

**機械チェックできないものを「ルール」と呼ばない。**

CI で落ちない規約は、レビュー担当者の記憶力に依存します。人が入れ替わる前提のチームでは、それは規約ではなく口伝です。
強制手段のないものは「ガイドライン」と明示的にラベルを変え、期待値を下げておきます。

各ルールには次の3つを必ず併記します。

- **強制**：どのツールがどう落とすか。ないなら「なし（ガイドライン）」と書く
- **根拠**：なぜそうするか（M-2）
- **対価**：この決定で何を失うか

### M-2. すべてのルールに「なぜ」を1〜2行で併記する

この分野の定説の多くは、**提唱者自身が撤回しています。**

| かつての定説 | その後 |
| :--- | :--- |
| Container / Presentational Components | Dan Abramov が2019年に原典へ撤回の追記 |
| Atomic Design の atoms/molecules/organisms | Brad Frost 自身が「語彙は失敗だった」と総括 |
| Feature-Sliced Design の features/entities 既定 | 作者が v2.1「Pages come first」で降格 |
| ランタイム CSS-in-JS | RSC と構造的に非互換 |

根拠が書いてあれば、根拠が失効したときに規約ごと廃止できます。
**根拠なしのルールは、撤回された定説として次の世代に残ります。**

### M-3. 既存コードへの適用はベースライン＋ラチェット

既知の違反をベースラインファイルに固定し、**新規違反だけを落とす。**
一括修正を前提にしたルール導入は、ほぼ確実に失敗します。

あわせて `eslint-disable` の**件数を計測対象**にします。増加は「ルールが現実と合っていない」シグナルであり、
開発者の規律の問題として扱いません。

## 第1層：4本の柱

個別のルールはすべて、次の4つの命題のいずれかの系です。

```
A. 方向     依存は一方向にのみ流れる
B. 所有     すべての状態には所有者が1人だけいる
C. 移植性   移植可能なものと不可能なものを分離する
D. 基盤     プラットフォームが基底層、フレームワークはその上の薄い層
```

### A. 方向 — 依存は一方向にのみ流れる

層に上下関係を与え、import は厳密に下位方向のみ。同一層の横方向 import は禁止。
これだけで**層間の循環は構造的に発生しなくなります。**

循環依存を禁止する理由は美観ではなく、ESM のセマンティクスとして実際に壊れるからです。
循環時は先に評価された側が相手の export を `undefined` として見るか、TDZ で `ReferenceError` を投げます。
ランタイムもバンドラも循環を「解決」しません。「今動いているから大丈夫」は、
import 順が変わった瞬間（ファイル追加、コード分割の変更、テストランナー）に崩れます。

→ [rules/boundaries.md](./rules/boundaries.md)

### B. 所有 — すべての状態には所有者が1人だけいる

「状態管理」を一枚岩で語らない。サーバキャッシュと UI 状態は本質的に異なる問題を持つため、
異なる方法で管理します。両者を混ぜることが、状態管理における最大の設計ミスです。

→ [rules/state.md](./rules/state.md)

### C. 移植性 — 移植可能なものと不可能なものを分離する

振る舞い・アクセシビリティ・状態機械はプロジェクトを跨いで不変。
見た目・DOM 構造・語彙はプロジェクト固有。headless UI が成立する理由はこの非対称性のみです。

この境界が正しく引けているかは、**3つの検査で機械的に検証できます。**

1. 隔離して story が書けるか（書けない ＝ 不要な依存を抱えている）
2. `getByRole` でテストできるか（書けない ＝ アクセシブルでない）
3. トークンだけ差し替えてテーマが変わるか（変わらない ＝ 値がコンポーネントに漏れている）

→ [rules/components.md](./rules/components.md)

### D. 基盤 — プラットフォームが基底層

プログレッシブエンハンスメントは「反JavaScript」ではなく **「反・単一障害点」** です。
JS が遅れる／落ちる／失敗する状況でも中核機能が成立するよう層を積む設計規律を指します。

| 層 | 提供するもの | 壊れたときの結果 |
| :--- | :--- | :--- |
| HTML | 意味論、フォーム送信、リンク遷移、`<dialog>`/`<details>`/ネイティブ検証 | 機能そのものが無い |
| CSS | レイアウト、状態表現、アニメーション | 見た目が素朴になるだけ |
| JS | 楽観的更新、キーボード拡張、遷移演出 | **体験は劣化するが機能は残る** |

→ [rules/platform.md](./rules/platform.md) / [rules/rendering.md](./rules/rendering.md)

## 決定記録

規約の根幹をなす5つの選択。いずれも対立する選択肢が実在したため、**選ばなかった側とその理由**を残します。

### 決定① 公開面は lint で定義する（barrel は作らない）

FSD は「`index.ts` を public API に」、bulletproof-react は「barrel file を避けよ（tree-shaking を阻害する）」
と主張し、両者は正面から衝突しています。

**採用：公開面をパス規約と lint で定義し、barrel ファイルでは定義しない。**

- **理由**：barrel の実測コストが無視できない（MUI Button の barrel 経由でバンドルがほぼ倍、
  barrel 除去でテストの変換対象ファイルが約85%減という報告）。カプセル化の利得は lint でも得られる
- **対価**：セグメント名が規約の一部になる（好みで増やせない）。IDE の自動リファクタが前提条件になる

→ `A-1` 〜 `A-3`

### 決定② 非正規化＋invalidate を既定とする

Redux 系は正規化を推奨し、サーバキャッシュ系はクエリキーごとの独立スナップショット＋invalidate で解消します。
**両方採用すると同じデータが2箇所で正規化され、「どちらが真か」を人間が管理し始めます。**

**採用：非正規化＋invalidate。グローバル正規化ストアは条件付きの例外とする。**

- **理由**：サーバを正とする方が、サーバ側の正規化結果との乖離を生まない
- **対価**：1エンティティの更新で全リストが揃うのに往復が増える。**これは意図的に受け入れる**

→ `S-6` 〜 `S-11`

### 決定③ Context / provide-inject は用途を3分類する

Context は DI 機構であって状態管理ツールではない、という立場（Mark Erikson）が一方にあります。
ただし React Context（値の変更で全 consumer が再レンダー）と Vue provide/inject（ref を注入すれば粒度が保たれる）
には**挙動の非対称性**があり、フレームワーク非依存の規約で一律に書くと片方で不正確になります。

**採用：用途を DI / コンポーネント内部の暗黙共有 / 頻繁に更新される共有状態 の3つに分類し、それぞれ別のルールを与える。**

- **理由**：compound components が内部で Context を使うのは「状態管理」ではなく実装詳細の受け渡しであり、
  これを一律に規制すると柱Cのルールと衝突して規約の信頼性が落ちる
- **対価**：分類の判断が1つ増える

→ `S-18` 〜 `S-22`

### 決定④ 暗黙解決はフレームワーク組み込みAPIとルーティングに限定

auto-import と「検証可能な境界」は**原理的に両立しません。**
`madge` / `dependency-cruiser` / `eslint-plugin-boundaries` はすべて `import` 文を解析するため、
auto-import されたモジュールは依存グラフに現れず、柱Aの強制も決定①も無効化されます。

**採用：フレームワーク組み込みAPI（`ref` `computed` `useState` 等）とファイルベースルーティングのみ暗黙解決を許可。**

- **理由**：auto-import が隠すのは「フレームワークへの依存」ではなく **「機能間の依存」** であり、
  後者こそが長期プロダクトで管理したい唯一のもの
- **対価**：素の状態より DX が落ちる。ただし書かずに済む import の大半は依然として書かずに済む

→ `A-11` 〜 `A-13`

### 決定⑤ 既定戦略＋ルート単位の逸脱を決定表と ADR で許す

レンダリング戦略は技術が動き続けるため、規約に特定の戦略名を書き込むと2年で腐ります。

**採用：規約が持つのは「決定表」「既定戦略」「逸脱の記録方法」の3点のみ。個々の技術名は付録に置く。**

- **理由**：単一戦略への統一は、マーケLPと管理ダッシュボードが同一アプリに同居した瞬間に破綻する。
  一方でルートごとの自由に任せると、パフォーマンス予算もキャッシュ設計も立てられない
- **対価**：ルートごとに戦略の宣言と、逸脱時の ADR が必要になる

→ `R-1` 〜 `R-4`

## 導入順序

費用対効果順。上から順に入れます。

1. **循環禁止**（`A-4`）— コスト極小・効果最大・議論の余地なし
2. **一方向の依存ルール1本**（`A-5` 〜 `A-6`）＋ lint 強制
3. **状態の分類表**（`S-1`）とレビュー時の判定。特に `S-2`（URL に置くべきか）と `S-4`（Effect で state を同期していないか）
4. **第一分割をドメイン語に**（`A-7`）— 削除可能性テストで検証
5. **共有への昇格条件と降格手順**（`A-8` 〜 `A-9`）
6. **Baseline のブラウザサポートルール**（`P-1`）＋ 禁止 lint 3点（`P-7` `P-14` `P-18`）
7. **トークン3層と `@layer` 順序**（`C-15` 〜 `C-16`）

いずれも M-3（ベースライン＋ラチェット）で導入します。
