# issue の拾い方

**ここでは直さない。** 選んで起こすところまで。1 issue の進め方は `assign` が持つ。

**拾わない側に倒す。** 拾い損ねても次の回で拾える。間違って拾うと、要らない PR が1本残る。

## 1. 数える

未マージの PR を数える。**5本以上あれば、この回は1本も拾わない。** ラベルは問わない。レビューとマージは書き手が持つので、PR が溜まると詰まる。

## 2. 落とす

open issue を集め、上から順に落とす。

| 落とす                                                                         | なぜ                                                             |
| :----------------------------------------------------------------------------- | :--------------------------------------------------------------- |
| `documentation` ラベル                                                         | 記事のネタで、`article` の対象                                   |
| `## ゴール` `## 現状` `## 完了条件` が揃っていない                             | 完了条件が外から判定できることが自走の前提（→ `create-issues`） |
| 完了条件が4つ以上                                                              | issue が2本に割れている                                          |
| `claude/issue-<番号>-` の remote branch があるか、`Closes #<番号>` の open PR がある | 既に走っている                                                   |

**assignee は見ない。** このリポジトリでは「着手中」の意味で使われていない。

**取り残しは拾い直す。** branch はあるが open PR が無く、最終コミットが6時間より古いなら落とさない。報告に1行書く。接尾辞が変わるので衝突しない。

## 3. 読んで落とす

残ったものを読む。次のどれかに当たれば落とす。

- **完了条件が判断を含む。** 「〜が決まっている」「〜の扱いが決まり」は、決めるのが書き手の仕事で、直す作業ではない
- **簡単には変えられない判断を要求する。** `.claude/rules/docs.md` の ADR 基準（①アーキテクチャ設計・規約、テスト設計、デザインの大方針のどれか ②覆すと複数ファイル・公開 URL・ビルド設定・テストの走らせ方が変わる）の両方に当たる。既存の ADR を差し替えるものも同じ
- **完了条件が外から判定できない。** 「使いやすくなっている」は条件ではない

**迷ったら落とす。**

## 4. 並べる

`bug` を先、`enhancement` を後。同じなら作成が古い順。放置され続ける issue を作らない。

## 5. 起こす

先頭から**最大2本**。1 issue につき `Agent` ツールを1回、次の指定で呼ぶ。提案カード止まりの手段（`spawn_task` 等）は使わない。ユーザーの承認を待たず、その場で動き出すこと。

| 指定するもの | 値 |
| :--- | :--- |
| `isolation` | `"remote"`。**`"worktree"` にしない。** dispatch 自身が使い捨てのコンテナで動くため、ローカル worktree にするとこのセッションの終了に道連れで止まる。`remote` は常にバックグラウンドで動く |
| `model` | `"opus"` |
| `subagent_type` | `general-purpose` |
| `description` | `issue #<番号>` |
| プロンプト | リポジトリ URL（`https://github.com/uyaaaaaa/personal-blog`。新しいセッションはこの会話を引き継がないので明記する）／`assign` に従って `#<番号>` を進めること／作業ブランチは `claude/issue-<番号>-<英数字4〜6>`（→ `assign`。次の回の重複判定がこれを見る）にすること／答えを待てる相手がいないこと。これだけ |

**実装の方針を渡さない。** issue の読み方は `assign` が持っている。

**起こしたら待たない。** `Agent` 呼び出しの完了を待機・ポーリングしない。

## 6. 報告

Slack の `#blog-agent`（`C0BV67WD6Q5`）に、1回の発火につき最大1つ。書くのは次のどれか。

- 起こした issue。番号とタイトル（`Agent` の内部 ID は書かない）
- 前回から変わった PR。出た / 緑になった / 赤いまま見る者がいない
- 取り残しを拾い直した
- PR が5本以上で拾わなかった

**どれも無ければ投稿しない。** 毎時の「なし」を残さない。

**出す前にチャンネルの直近を読み、同じことを書くならやめる。** 状態を持たずに重複を防ぐ。
