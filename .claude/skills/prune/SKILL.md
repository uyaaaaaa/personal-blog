# テストを減らす

**判定は1問。「消すと、どんな現実的な不具合を見逃すか」。** 答えが「無い」か「別のテストが既に捕まえる」なら消す。件数もカバレッジも目的にしない。「念のため」は残す理由にならない。実行時間・不安定さ・直すときの手間と、守っているものの価値を比べる。

**検査を足すたびにテストが増える**（→ `.claude/rules/checks.md`）。ここが減らさないと、増える一方になる。散文を減らすのは `context-review`。

## 消す候補

- **実装の写し。** 実装と同じ式をアサーションに書き直しただけのもの
- **型が保証していること。** optional を渡さない、来ない分岐
- **ライブラリやモックの自己検証。** スタブが返す値をそのまま確かめているもの
- **隣の `it` の部分集合。** 同じ入力で同じ壊れ方を捕まえる
- **判定の正本が別にあるもの。** 判定を import して通すだけの検査で、判定の中身を並べ直したもの。配線（読む範囲・出力・終了コード）だけが固有
- **実装の中身への依存。** 内部スコアの大小、呼ばれた回数それ自体

**候補ごとに「代わりに何が捕まえるか」を1行で言えるまで消さない。** 言えないものは残す。

## 消さないもの

- **検査のテストの、破る例1本と通す例1本**（→ `.claude/rules/checks.md`）。それ以上の例は候補
- **ある util の唯一のテスト。** 消すと [ADR 08](../../../docs/adr/08-test-as-second-use.md) の戻す条件に当たり、util を呼び出し元に戻す判断が要る。消さず `needs-decision` の issue にして書き手に返す
- **実装の穴を埋めている記述。** 実行環境が持たないもの（レイアウト、フォーカスの移動）を自前で補っている部分。理由がコメントに書いてある

## 範囲

**1回1層。** `tests/` をディレクトリ単位で1つ選ぶ。直近の変更で増えた層を先に。全域を一度に触ると差分がレビューできず、消しすぎたことに次のセッションまで気付けない。

## 手順

1. 層の `it` を1つずつ、判定の1問にかける
2. 消す前と後で `npm test` と `npm run lint` を通す（→ `verify`）。後で落ちたら、残したテストが消した方に依っていた
3. 消した `it` ごとに、代わりに何が捕まえるかを PR 本文に1行。判定の記憶は PR が持つ

除外リストも進捗表も作らない（→ [ADR 11](../../../docs/adr/11-no-enforcement-inventory.md)）。

## 終わり方

**1件も消せなければ報告しない。** 消せるものが無いのは正常な結果で、その層は既に絞れているというだけ。
