# issue の作り方

**対象は番号の無い課題の持ち込みだけ。** 対応はこのスキルの範囲外で、着手は `assign` に渡る。

**issue の主役は完了条件で、解決手段ではない。** 手段を書き込むほど、対応する人の思考はそこに寄る。

## 1. 聞く

**聞く前に取れる事実は取る。** 該当ファイル、`docs/DESIGN_GUIDELINE.md` と `docs/DECISIONS.md`（方針と衝突しないか）、同じ課題の既存 issue（重複は検索して確かめる）。調べた結果は質問と一緒に短く出す。

質問は `AskUserQuestion` で。**答えを聞かないと立てられない質問を、同じラウンドに混ぜない。**

**ラウンド1 — 前提なしで答えられる**

- **どうなってほしいか。** 1文で言い切ると?
- **いま何が起きているか。** いつ・どこで気づいたか
- **放っておくと何が困るか**

**ラウンド2 — ラウンド1が決まって初めて聞ける**

- **何を見れば「終わった」と分かるか**
- **今回やらないこと。** 一緒に見つけた別の問題を含めるか
- **触ってほしくないもの。** 既にある判断と衝突しないか

## 2. 裏を取る

**issue に書く事実は、書く前に実装で確かめる。**

- 行番号・変数名・ファイル名を書くなら、開いて今の状態を見る
- 再現を試す。再現しないなら条件が揃っていないだけのことがあるので、**条件を現状に書く**
- 確かめられなかったことは「推測」と1語で明示するか、書かない

## 3. 詰める

上から順。任意の節は、書くことが無ければ落とす。

| 節 | 中身 | 必須 |
| :--- | :--- | :--- |
| ゴール | 何がどうなってほしいか。1〜2文の言い切り | 必須 |
| 現状 | 観測できる事実だけ。再現手順・出力・該当箇所 | 必須 |
| 完了条件 | チェックリスト。満たしたかを外から判定できる状態 | 必須 |
| 前提・制約 | 触らないもの、既にある判断へのリンク | 任意 |
| 手がかり | 読む場所と観測した事実。**指示ではないと明記** | 任意 |
| 範囲外 | 今回やらないこと。送り先の issue 番号 | 任意 |

- **完了条件に手段を含めない。** ✗「フォールバックを入れる」 → ○「日本語だけのタグでも、その一覧に他のタグの記事が混ざらない」
- **誰が見ても判定が同じになる形にする。** 「使いやすくなっている」は条件ではない
- **完了条件は3つまで。** 4つ以上になったら、issue が2本に割れている（→ 分ける。親子にしてよい）
- **実装案・編集の手順・ライブラリや API の名前を書かない**
- **本文40行以内、1節5項目以内、1項目1行。** リストと体言止めで書き、言い切る

## 4. 出す

- タイトルは**1行の言い切り**。分類の接頭辞は付けない
- ラベルは `bug` / `enhancement` / `documentation` から1つ
- 書き手が決めるまで動かせないものには `needs-decision` を足す
- 発行は GitHub MCP の issue 作成ツール
- 発行したら番号と URL を報告する。複数に割ったら、その関係も
