# レビューの手順

指摘の探索は組み込みの `code-review` に任せる。**このスキルが決めるのは、何を捨てるかと、どう書くかの2つ。**

**レビューは差分を読ませる作業ではなく、書き手の手を止めるかどうかの判定。** 判定に効かない指摘は、正しくても書かない。

## 1. 集める

`code-review` を呼ぶ。**`--comment` も `--fix` も付けない。** 投稿の型はこのスキルが握り、直すかどうかは書き手が決める。

| 対象 | 渡すもの |
| :--- | :--- |
| 作業ツリー | 引数なし（`main` からの差分） |
| PR | PR 番号 |
| ブランチ・パス | そのブランチ名 / パス |

effort の既定は **medium**。生成物・ルーティング・データ取得に触る差分だけ `high` にして、捨てる側で絞り直す。
先に `git diff main...HEAD --stat` で範囲を見る。

## 2. 捨てる

残るのは、**機械が落とさず、ルールに照らして壊れているもの**だけ。

- **レビューの前に `npm run lint` と `npm test` を通す。落ちたものは検査の担当**なので、指摘には起こさない。伝えるならサマリの1行
- **効いている検査の一覧は持たない**（→ [ADR 11](../../../docs/adr/11-no-enforcement-inventory.md)）。どれが機械の担当かは、一覧を引かずに実行して確かめる
- 通せないときは、サマリの「実測」に未実施と書き、機械が見ていそうな範囲（整形・import・循環・型）は指摘を控える
- **差分が触るファイルの `.claude/rules/` を、指摘を選ぶ前に読む。** ルールが禁じていることを勧める指摘は、一般論として正しく見えても間違い
- **ルールが何も言っていないことは好みなので書かない**
- **「かもしれません」が入るなら落とす。** 読んで判断しただけのものは指摘ではなく質問
- **上限の目安は5件。** 多く挙げるほど、重い1件が埋もれる

記事本文（`content/`）は `article`、実測の手順は `verify` の範囲。ただし **PR の「確認」に、走らせていないコマンドの結果が書かれていないか**は見る。

## 3. 判定する

**判定は必ず1つ選び、サマリの先頭に置く。** 迷ったら `Comment`。

| 判定 | 使うとき |
| :--- | :--- |
| `Approve` | 要対応が0件 |
| `Comment` | 任意の指摘だけ。判断は書き手に渡す |
| `Request changes` | 壊れる・生成物が変わる・方針に反する、のどれか1つ以上 |

**`Request changes` は「壊れる」ときだけ。** 好みや改善提案では出さない。

## 4. 書く

### サマリコメント（1本、必ず出す）

```md
**判定: Request changes** — 目次の開閉が生成 HTML に出ず、初期表示が閉じたままになる。

- 要対応 1件 / 任意 2件
- 実測: `npm run lint` `npm test` は終了コード 0
```

- 先頭行は **判定 + ダッシュ + 理由1文**。`Approve` なら判定だけでよい
- 続けるのは**件数**と**実測の状態**の2行まで
- 前置き、総評、褒め言葉、差分の要約は書かない

### インラインコメント（1件1論点）

```md
**静的生成の HTML では閉じたままになる**

`onMounted` 後にしか開閉が決まらないため、初期状態がビルド時に焼き付く。
CSS で出し分けるか、初期値を props で受ける。
```

| | 決まり |
| :--- | :--- |
| 見出し | 1行。**何が起きるか**を言い切る。「〜すべき」ではなく「〜になる」 |
| 本文 | 3行以内。1行40字目安。理由 → 代案の順 |
| 合計 | 見出し・本文・コード片を合わせて6行以内 |
| 論点 | 1コメント1つ。2つあるなら2コメントに割る |
| コード片 | 提案が1〜5行で書けるときだけ。それ以上は文章で書く |

**書かないもの。** 差分の写し、前置き、「かもしれません」、他の指摘への参照、ソースコードレベルの情報を並べただけの説明。

## 5. 出す

- 投稿は GitHub MCP のレビューツール。pending review を作る → コメントを足す → submit の順
- サマリはレビュー本体の本文に置く。インラインは該当行に付ける
- 作業ツリーのレビュー（PR が無い）は投稿せず、同じ型で会話に返す
- 各コメントの末尾に `_Generated by [Claude Code](https://claude.ai/code)_` のフッターを付ける
- **投稿したら、判定と件数だけを報告して終わり**

## 見届けを頼まれたとき

**PR を1本、継続して見る依頼で起きたセッションだけがここに従う。** 1回のレビューを頼まれたなら、上の1〜5で終わり。

**判定を返すのがこちらの仕事で、差分は直さない。** CI の赤も直さない。直すのは書いたセッション。

- **見始めたら PR に `in review` を付ける。** 「レビューのセッションが見ている」という意味で、見ている間だけ付いている
- **まず1回レビューする**（1〜5に従う）。セッション名を `Review PR #N` に変える
- **その後は自分宛のチェックインを予約して見に行く。** 目安は30分。起きたら head と CI とスレッドを見る
- **予約する手段が無ければ、最初の1回で終える**
- **見るのは head が変わったときだけ。** 変わっていなければ何も書かず、次の確認を予約する
- **再レビューは前回からの差分に当てる。** 直った指摘は書かない。直っていない指摘は繰り返さず、未対応の件数をサマリの1行に置く
- **返答だけで差分が無いものに、判定を出し直さない**

### 終える条件

| 条件 | 最後にすること |
| :--- | :--- |
| 判定が `Approve` | 何も足さない。マージはしない |
| merged / closed | 何も書かない |
| 再レビューが3回に達した | 残った論点を1コメントにまとめ、判断を書き手に渡す |
| 同じ指摘が2回続けて動かない | 同上 |

**どの条件でも `in review` を外し、打ち切りなら理由を1行残す。** 誰も見ていない PR を、見ているように見せない。
