# レビューの手順

指摘の探索は組み込みの `code-review` に任せる。**このスキルが決めるのは2つだけ。**

1. **何を捨てるか**（機械とルールが持つ領分、確信の持てないものを落とす）
2. **どう書くか**（Approve 可否を先頭に、1コメント1論点で短く）

レビューは差分を読ませる作業ではなく、**書き手の手を止めるかどうかの判定**。判定に効かない指摘は、正しくても書かない。

## 全体

| フェーズ | やること | 終了条件 |
| :--- | :--- | :--- |
| 1. 集める | `code-review` を回す | 生の指摘が手元にある |
| 2. 捨てる | 機械とルールが持つものを落とす | 残ったものが全部「消せない理由」を言える |
| 3. 判定する | Approve 可否を1つ決める | 判定と理由が1行で言える |
| 4. 書く | 型に沿って整形する | 1コメント1論点、6行以内 |
| 5. 出す | サマリ＋インラインで投稿する | 先頭に判定が載った |

---

## 1. 集める

`code-review` スキルを呼ぶ。**`--comment` は付けない。** 投稿はこのスキルが行う（フォーマットを握るため）。
`--fix` も付けない。直すのは書き手の判断。

| 対象 | 渡すもの |
| :--- | :--- |
| 作業ツリー | 引数なし（`main` からの差分） |
| PR | PR 番号 |
| ブランチ・パス | そのブランチ名 / パス |

effort の既定は **medium**。生成物・ルーティング・データ取得に触る差分だけ `high` にして、捨てる側で絞り直す。

**差分の範囲を先に確認する。** `git diff main...HEAD --stat` の出力を見てから読む。

## 2. 捨てる

### 機械が持っている領分は書かない

`npm run lint` / `npm run build` / `npm test` / Git フックが落とすものを人が指摘しても、検査と二重になるだけ。

**効いている検査の一覧は持たない**（→ [ADR 11](../../../docs/adr/11-no-enforcement-inventory.md)）。写した表は追従されず、必ず嘘になる。**どれが機械の担当かは、一覧を引かずに実行して確かめる。**

- レビューの前に `npm run lint` と `npm test` を通す。**落ちたものは検査の担当**なので、指摘には起こさない。伝えるならサマリの1行で足りる
- 依存が無いなどで通せないときは、サマリの「実測」に未実施と書き、機械が見ていそうな範囲（整形・import・循環・型）は指摘を控える

### ルールが持っている判断は写さない

**差分が触るファイルの `.claude/rules/` を、指摘を選ぶ前に読む。** 何を良しとするかはそちらが持つ。ここに写せば追従されず、上と同じことが起きる。

- ルールが**禁じている**ことを勧める指摘は、一般論として正しく見えても間違い。読まずに書くとこれを踏む
- ルールが**何も言っていない**ことは好みなので書かない
- 記事本文（`content/`）は `article`、実測の手順は `verify` の範囲。ただし **PR の「確認」に、走らせていないコマンドの結果が書かれていないか**は見る

残るのは、**機械が落とさず、ルールに照らして壊れているもの**だけ。それだけが指摘になる。

### 確信が持てないものは書かない

- 本文に「かもしれません」「可能性があります」が入るなら**落とす**。読んで判断しただけのものは指摘ではなく質問。
- どうしても伝えるなら、指摘ではなく**サマリの1行**にまとめる。
- **上限の目安は5件。** 超えたら重い順に落とす。多く挙げるほど、重い1件が埋もれる。

## 3. 判定する

**判定は必ず1つ選び、サマリの先頭に置く。** 迷ったら `Comment`。

| 判定 | 意味 | 使うとき |
| :--- | :--- | :--- |
| `Approve` | このまま出せる | 要対応が0件 |
| `Comment` | 直さなくても出せる | 任意の指摘だけ。判断は書き手に渡す |
| `Request changes` | 直さないと出せない | 壊れる・生成物が変わる・方針に反する、のどれか1つ以上 |

**`Request changes` は「壊れる」ときだけ。** 好みや改善提案では出さない。

## 4. 書く

### サマリコメント（1本、必ず出す）

先頭行が判定。理由は1行で言い切る。

```md
**判定: Request changes** — 目次の開閉が生成 HTML に出ず、初期表示が閉じたままになる。

- 要対応 1件 / 任意 2件
- 実測: `npm run lint` `npm test` は終了コード 0
```

- 先頭行は **判定 + ダッシュ + 理由1文**。`Approve` なら理由は不要で判定だけでよい。
- 続けるのは**件数**と**実測の状態**の2行まで。
- 前置き、総評、褒め言葉、差分の要約は書かない。

### インラインコメント（1件1論点）

```md
**静的生成の HTML では閉じたままになる**

`onMounted` 後にしか開閉が決まらないため、初期状態がビルド時に焼き付く。
CSS で出し分けるか、初期値を props で受ける。
```

| | 決まり |
| :--- | :--- |
| 見出し | 1行。**何が起きるか**を言い切る。「〜すべき」ではなく「〜になる」 |
| 本文 | 3行以内。1行40字目安。理由 → 代案の順 |
| 合計 | 見出し・本文・コード片を合わせて6行以内 |
| 論点 | 1コメント1つ。2つあるなら2コメントに割る |
| コード片 | 提案が1〜5行で書けるときだけ。それ以上は文章で書く |

**書かないもの。** 差分の写し、前置き（「素晴らしい変更ですが」）、「かもしれません」、他の指摘への参照、ソースコードレベルの情報を並べただけの説明。

## 5. 出す

- 投稿は GitHub MCP のレビューツール。pending review を作る → コメントを足す → submit の順
- サマリはレビュー本体の本文に置く。インラインは該当行に付ける
- 作業ツリーのレビュー（PR が無い）は投稿せず、同じ型で会話に返す
- 各コメントの末尾に `_Generated by [Claude Code](https://claude.ai/code)_` のフッターを付ける
- **投稿したら、判定と件数だけを報告して終わり。** 直すかどうかは書き手が決める
