# レビューの手順

指摘の探索は組み込みの `code-review` に任せる。**このスキルが決めるのは、何を捨てるか・どのグレードを付けるか・どう書くかの3つ。**

## 1. 集める

`git diff main...HEAD --stat` で範囲を見てから `code-review` を呼ぶ。**`--comment` も `--fix` も付けない。**

| 対象 | 渡すもの |
| :--- | :--- |
| 作業ツリー | 引数なし（`main` からの差分） |
| PR | PR 番号 |
| ブランチ・パス | そのブランチ名 / パス |

生成物・ルーティング・データ取得に触る差分だけ `high` を渡し、捨てる側で絞り直す。

## 2. 捨てる

残るのは、**機械が落とさず、ルールに照らして壊れているもの**だけ。

- **先に `verify` に従って `npm test` と `npm run lint` を通す。落ちたものは検査の担当**なので、指摘には起こさない。伝えるならサマリの1行
- 通せないときは、サマリの「実測」に未実施と書き、機械が見ていそうな範囲（整形・import・循環・型）は指摘を控える
- **効いている検査の一覧は引かない。実行して確かめる**（→ [ADR 11](../../../docs/adr/11-no-enforcement-inventory.md)）
- **差分が触るファイルの `.claude/rules/` を、指摘を選ぶ前に読む。** ルールが禁じていることを勧める指摘は落とす
- **ルールが何も言っていないことは書かない**
- **「かもしれません」が入るなら落とす**
- **合計5件まで。うち `imo` と `nits` は合わせて2件まで**

記事本文（`content/`）は `article`、実測の手順は `verify` の範囲。ただし **PR の「確認」に、走らせていないコマンドの結果が書かれていないか**は見る。

## 3. グレードを付ける

**残った指摘1件ごとに、グレードを1つ選ぶ。** 迷ったら下の行にする。

| グレード | 付けるとき | saved reply の本文 |
| :--- | :--- | :--- |
| `must` | 壊れる・生成物が変わる・方針に反する。直さないとマージできない | `![must](https://img.shields.io/badge/must-d73a4a)` |
| `suggestion` | 直せば良くなる具体案がある。採否は書き手が決める | `![suggestion](https://img.shields.io/badge/suggestion-fbca04)` |
| `imo` | 自分ならこうする、という別案。採らなくてよい | `![imo](https://img.shields.io/badge/imo-0075ca)` |
| `nits` | 命名・表記の細かい点。直さなくても動く | `![nits](https://img.shields.io/badge/nits-cfd3d7)` |

**グレードはこの4本の saved reply でだけ表す。** GitHub の Settings → Saved replies に、グレード名をタイトル・右列を本文として登録しておき、コメントの先頭はそこから挿入する。手で書くのは見出しから下だけ。

- **`must` は「壊れる」ときだけ。** 好みや改善提案には付けない
- **`nits` に整形・import 順・型を入れない**（→ 2 で捨てる側）
- グレードが2つ付くなら指摘が2つ入っている。2コメントに割る
- 本文は右列のまま。色・文言・URL を変えず、ここに無いグレードを足さない

## 4. 判定する

**判定は必ず1つ選び、サマリの先頭に置く。**

| 判定 | 使うとき |
| :--- | :--- |
| `Request changes` | `must` が1件以上 |
| `Comment` | `must` が0件で、`suggestion` が1件以上 |
| `Approve` | 指摘が0件、または `imo` と `nits` だけ |

## 5. 書く

### サマリコメント（1本、必ず出す）

```md
**判定: Request changes** — 目次の開閉が生成 HTML に出ず、初期表示が閉じたままになる。

- must 1 / suggestion 2
- 実測: `npm run lint` `npm test` は終了コード 0
```

- 先頭行は **判定 + ダッシュ + 理由1文**。`Approve` なら判定だけでよい
- 続けるのは**グレードごとの件数**と**実測の状態**の2行まで。0件のグレードは書かない
- 前置き、総評、褒め言葉、差分の要約は書かない

### インラインコメント（1件1論点）

```md
![must](https://img.shields.io/badge/must-d73a4a) **静的生成の HTML では閉じたままになる**

`onMounted` 後にしか開閉が決まらないため、初期状態がビルド時に焼き付く。
CSS で出し分けるか、初期値を props で受ける。
```

| | 決まり |
| :--- | :--- |
| 1行目 | グレードの saved reply 1つ + 見出し。**何が起きるか**を言い切る。「〜すべき」ではなく「〜になる」 |
| 本文 | 3行以内。1行40字目安。理由 → 代案の順 |
| 合計 | 見出し・本文・コード片を合わせて6行以内 |
| 論点 | 1コメント1つ |
| コード片 | 提案が1〜5行で書けるときだけ。それ以上は文章で書く |

**書かないもの。** 差分の写し、前置き、「かもしれません」、他の指摘への参照、ソースコードレベルの情報を並べただけの説明。

## 6. 出す

- 投稿は GitHub MCP のレビューツール。pending review を作る → コメントを足す → submit の順
- API からは saved reply を挿入できない。3 の表の本文を1文字も変えずに先頭へ写す
- サマリはレビュー本体の本文に置く。インラインは該当行に付ける
- 作業ツリーのレビュー（PR が無い）は投稿せず、同じ型で会話に返す
- **投稿したら、判定と件数だけを報告して終わり**

---

## 見届けを頼まれたとき

**PR を1本、継続して見る依頼で起きたセッションだけがここに従う。** 1回のレビューを頼まれたなら、上の1〜6で終わり。

**差分も CI の赤も直さない。** 直すのは書いたセッション。

- **見始めたら PR に `in review` を付ける**
- **まず1回レビューする**（1〜6に従う）。セッション名を `Review PR #N` に変える
- **その後は自分宛のチェックインを予約して見に行く。** 目安は30分。起きたら head と CI とスレッドを見る
- **予約する手段が無ければ、最初の1回で終える**
- **見るのは head が変わったときだけ。** 変わっていなければ何も書かず、次の確認を予約する
- **再レビューは前回からの差分に当てる。** 直った指摘は書かない。直っていない指摘は繰り返さず、未対応の件数をサマリの1行に置く
- **返答だけで差分が無いものに、判定を出し直さない**

### 終える条件

| 条件 | 最後にすること |
| :--- | :--- |
| 判定が `Approve` | 何も足さない。マージはしない |
| merged / closed | 何も書かない |
| 再レビューが3回に達した | 残った論点を1コメントにまとめ、判断を書き手に渡す |
| 同じ指摘が2回続けて動かない | 同上 |

**どの条件でも `in review` を外し、打ち切りなら理由を1行残す。**
