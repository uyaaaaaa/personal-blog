# レビューの手順

指摘の探索・選別・グレード付けはエージェント `review` がやる。**このスキルが決めるのは、起こし方と出し方の2つ。**

## 1. 起こす

`Agent(subagent_type: "review")` に渡すのは PR 番号だけ。

```
PR #123 をレビューする
```

- **実装の意図・見どころ・直した点は渡さない。** 直したい形が先に見えていると判定にならない
- 作業ツリー（PR が無い）なら `main からの差分をレビューする`
- **lint と test は CI が打つ。自分では打たない。** PR の無い作業ツリーだけ自分で通す

## 2. 出す

- **投稿は `Review` ワークフローに渡す。** 自分のトークンで直接 submit しない。GitHub は PR の作者による `APPROVE` と `REQUEST_CHANGES` を拒むので、判定が黙って COMMENT に落ちる
- **判定を本文に書いた通常コメントで代えない。** それはレビューではないので、Approve も Request changes も付かない

エージェントが返す JSON は `scripts/review-args.mjs` の出力で、発火にそのまま渡せる形。

```json
{
	"method": "run_workflow",
	"workflow_id": "review.yml",
	"ref": "main",
	"inputs": { "pr": "123", "review": "<レビューの JSON を文字列にしたもの>" }
}
```

- **判定・バッジ・件数の上限・サマリの組み立ては、`references/` を読んでスクリプトが決める。**手で書き写さない
- **発火は、`.claude/hooks/review-guard.mjs` が検査する経路で打つ。** 検査に当たらない経路だと、バッジも上限も判定も素通りする
- 渡すのは出力のまま。キーを落とさない、組み替えない
- **走らせたら結果を見る。** `review.yml` の最新の run が `success` でなければ投稿できていない。失敗したまま報告しない
- 作業ツリーのレビュー（PR が無い）は投稿せず、返ってきた形のまま会話に返す
- **同じ PR への再レビューが3回に達したら出さない。** 直すのもここで止め、残った論点を1コメントにまとめて人に渡す

## 3. 報告する

**判定と件数だけを報告して終わり。** マージはしない。
