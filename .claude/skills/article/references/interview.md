# フェーズ1〜2: 取材して詰める

記事の書き方（[SKILL.md](../SKILL.md)）のフェーズ1と2の手順。
主題が1つに絞れ、取り決めシートが承認されるまでが範囲。

## フェーズ1: 素材を見極める

**まず取材源を判定する。** ここを飛ばすと、見えないものを調べようとするか、聞けば済むことを聞かずに書く。

| 取材源 | 例 | 自力で取れるか | やること |
| :--- | :--- | :--- | :--- |
| **業務・別リポジトリ** | 6,500万件のテーブル、React Native の実機不具合 | **取れない。かつそのままは出せない** | 記憶を聞き出し、一般化する |
| **手元の環境** | dotfiles、vim / zsh の設定、インストール作業 | セッションから見えないことが多い | 設定・バージョン・出力を貼ってもらう |
| **読んだ本・記事** | 書評、輪読の感想 | 取れない | 何がどう刺さったかを聞く |
| **公開情報** | 公式ドキュメント、OSS の Issue、言語仕様 | 取れる | 一次情報に当たり、リンクする |
| **その場で試したこと** | 記事のために手元で再現する | 実行できる | 最小再現例を作って動かす |
| **このリポジトリ** | ブログ自体の実装 | 取れる | コード・Issue・PR を先に読む |

**「このリポジトリ」は少数派。** ここに当てはまらない依頼のほうが多いと考える。

### 事実は取りにいく。決定は本人に返す

- **取れる事実は、聞く前に取る。** 公開情報とこのリポジトリの分は先に調べる。
  調べた結果は質問と一緒に短く出す。「調べたらこうだった。この理解で合っているか」の形にすると1往復で済む
- **取れない事実は、聞く。** 業務の記憶や手元の環境は、どれだけ調べても出てこない。**ここが取材**
- **決定は必ず本人に返す。** メッセージ・想定読者・型・何を公開するかを、こちらで決めない

### そのまま書けないものを先に分ける

業務由来の素材には、公開できない情報が混ざる。**書き始めてから気づくと構成ごと崩れる**ので先に仕分ける。

- コード・スキーマ・クエリの原文、社内の固有名詞、URL、正確な数値、顧客名
- → **一般化する。** 既存記事は実際にそうしている（`mysql-index.md` はカラム名を「カラムA」、型を「TEXT型のnullable」とだけ書く）
- → **一般化すると主題が消えるなら、その記事は書かない**か、別の切り口にする

> [!WARNING] 出せる / 出せないの判断は書き手がする
> 何を公開してよいかは決定であって事実ではない。こちらで決めず、迷うものは必ず本人に確認する。

## フェーズ2: 詰める

### 確定させる7項目

これが埋まるまで本文を1行も書かない。

| 項目 | 形式 |
| :--- | :--- |
| **メッセージ** | 80字以内の1文。「読んだ人に何を持ち帰ってほしいか」 |
| **想定読者** | 1文。「◯◯していて、△△に困っている人」 |
| **説明しないこと** | 想定読者がすでに知っていること |
| **説明すること** | 想定読者が知らず、かつメッセージに必要なこと |
| **素材と裏取り** | 何をもとに書くか。何で裏を取るか |
| **型** | [型の表](./writing.md#型を選ぶ)から1つ |
| **今回落とすもの** | 書きたいが入らないもの・出せないもの |

**「説明しないこと」と「説明すること」が、そのまま分量を決める。**
読者を決めていないとこの線が引けないので、結果として全部書くことになる。これが冗長化の最大の原因。

### 質問の順序

**答えを聞かないと立てられない質問を、同じラウンドに混ぜない。**
前のラウンドの答えが決まって初めて意味を持つ問いは、次のラウンドに送る。

**ラウンド1 — 前提なしで答えられる**

| # | 聞くこと | なぜ効くか |
| :--- | :--- | :--- |
| 1 | **言い切ると何になるか。** 「◯◯について」はテーマ。1文で言い切ると? | テーマのままでは構成が決まらない |
| 2 | **誰が読むか。その人は何を知っているか** | 説明の下限と上限が決まり、分量が決まる |
| 3 | **何時のことか。何をもとに書くか。何を使っていたか** | 素材の所在とバージョンが決まらないと、裏の取りようがない |

**ラウンド2 — ラウンド1が決まって初めて聞ける**

| # | 聞くこと | 何に依存するか |
| :--- | :--- | :--- |
| 4 | **意外なのはどこか。** 読者が予想しないのはどの部分か | 2。読者が決まらないと「意外」が定義できない |
| 5 | **主張は1つか。** 2つあるなら、どちらを今回書くか | 1。言語化されて初めて数えられる |
| 6 | **裏はどう取れるか。** ログ・設定・エラー文はあるか。公式ドキュメントは何と言っているか | 3。素材の所在で手段が変わる |
| 7 | **そのまま書けないものはあるか** | 3。同上 |

**ラウンド3 — 残っていれば**

| # | 聞くこと | なぜ効くか |
| :--- | :--- | :--- |
| 8 | **落とすものに合意できるか** | 先に合意しておくと、フェーズ4で削る抵抗が減る |

**ラウンド1で崩れたら、そこで止める。** 「実は2記事だった」「意外な点がない」と分かった時点で、
残りの質問は無意味になる。

補足として効く問い。

- メッセージの1文が「かつ」「また」「ついでに」で繋がったら、**2記事に分ける**
- 想定読者がその技術の初心者まで広がったら、**狭める**。広く狙うと一般解説が膨らんで主題が薄まる
- 想定読者がすでに知っていることをメッセージにしていないか。そうなら記事として成立しない

### 聞き方

- **1ラウンド分をまとめて聞く。** `AskUserQuestion` で複数問を一度に出す。1問ずつ往復しない
- **全問に推奨案を付ける。** 選択肢の先頭を推奨にして「（推奨）」と書く。
  書き手が「全部それでいい」の一言で返せる状態にする。推奨の無い質問は、こちらが考えていないだけ
- **調査待ちでラウンドを止めない。** 公式ドキュメントの確認などが要るときは、
  **それに依存する質問だけ次ラウンドに送り**、残りは今のラウンドで聞く
- **記憶があやふやな部分は、そのまま流さない。** 「推測として書くか、落とすか」を選ばせる
- **収束しないなら分割を提案する。** ラウンドを重ねても主張が1つにならないなら、テーマが大きすぎる

### 取り決めシート

7項目を並べて提示し、承認を取ってから書き始める。

**埋まっているだけでは終わっていない。** 各欄について、書き手のどの答えから決まったかを辿れるか確認する。
聞かずにこちらで埋めた欄があれば、それは暗黙の前提であって決定ではない。

```
メッセージ　: 6,500万件のテーブルへのCREATE INDEXは、オンラインDDLなら止めずに打てる。
　　　　　　  ただし事前に確認すべきことがある
想定読者　　: 本番のMySQLに大きなテーブルを抱えていて、インデックス追加が怖い人
説明しない　: インデックスの仕組み、SQLの基本、DDL/DML/DCLの分類
説明する　　: オンラインDDLで何がロックされないのか、実行前に何を確認したか
素材と裏取り: 業務での実作業（記憶）＋ MySQL公式ドキュメント ＋ テスト環境での実測
型　　　　　: 作業ログ
落とすもの　: 実テーブル名・スキーマ（一般化する）、DDLの用語解説（一般解説なので落とす）
```

> [!NOTE] シートは本文に書かない
> 「対象読者」という見出しを立てて宣言はしない。想定読者は構成の裏側で効かせる。
> ただし、トラブルシュート型・作業ログ型の「前提条件・環境」は別。
> あれは読者の宣言ではなく**再現条件の事実**なので、必要なら書く。

Issue から始まった記事なら、シートを Issue に書き残す。無ければ、やりとりの中で確定させておけばよい。
