# 記事の書き方

`content/article/` に置く技術記事の方針。文章の巧拙は問わない。
**伝えたいことが1つに絞れていること**と、**それが想定読者に短く届くこと**だけを見る。

## 優先順位

上が勝つ。迷ったら上を取る。

1. **メッセージが1つに絞れている**
2. **想定読者にとって短い**
3. **網羅的である**

3が一番下なのが要点。網羅性を守るために長くなるくらいなら、範囲を狭めて短く書く。

> [!WARNING] 「短くするために不正確に書く」は禁止
> 3の優先度が低いのは「書ききれない厳密さを**落としてよい**」という意味であって、
> 「**ぼかしてよい**」ではない。曖昧な記述は短くならないうえに誤読を生むので、両取りできない。
> 書けないものは丸ごと消す。消したことを断りたいときだけ「本記事は◯◯の場合に限ります」と1文入れる。
> 未検証の推測は、1文で「推測」と明示するか、書かない。

---

## 書き始める前に決める2つ

**メッセージ（何を）** と **想定読者（誰に）** を、本文を1行も書かないうちに決める。
どちらも**記事本文には書かない**。書くための道具であって、読者に見せるものではない。

### 1. メッセージ

**「この記事を読んだ人に、何を持ち帰ってほしいか」を80字以内の1文**で書く。
構成も見出しも分量も、すべてこの1文から決まる。

```
例）Cloudflare Pagesで@nuxt/contentの記事がSSR時だけ取得できないのは、
    実行環境がネイティブNode.jsモジュールに対応していないから。プリレンダリングで回避できる。
```

### 2. 想定読者

**「誰が読んだら得をするか」を1文**で書く。**「◯◯していて、△△に困っている人」**の形にする。

```
例）Nuxt + Cloudflare Pages で個人ブログを動かしていて、
    ローカルでは出る記事が本番だけ表示されない現象に当たった人
```

書いたら、そこから2つ導く。**これが分量を決める。**

| | 例 |
| :--- | :--- |
| **説明しなくていいこと** | SSR / CSR の違い、Cloudflare Pages のデプロイ手順 |
| **説明が要ること** | なぜ SSR のときだけ失敗するのか、`better-sqlite3` が絡む理由 |

「説明しなくていいこと」を書いてしまうのが冗長化の最大の原因。
**読者を決めていないと、この線が引けないので全部書くことになる。**

> [!NOTE] 本文には書かない
> 「対象読者」という見出しを立てて宣言はしない。想定読者は構成の裏側で効かせる。
> ただし、トラブルシュート型・作業ログ型の「前提条件・環境」は別。
> あれは読者の宣言ではなく**再現条件の事実**なので、必要なら書く。

記事の元ネタが Issue にあるなら、**メッセージと想定読者の2文は Issue 側に書き残す**。
本文に残らないので、書かないとリライト時に前提が失われる。

### 2つの検算

- **メッセージの1文が「かつ」「また」「ついでに」で繋がったら、記事を分ける。** 2つ書きたいなら2記事
- **想定読者がその技術の初心者まで広がったら、狭める。** 広い読者を狙うと一般解説が膨らんで主題が薄まる
- **想定読者がすでに知っていることをメッセージにしていないか。** そうなら記事として成立しない
- **全部の見出しがメッセージに奉仕しているか。** していない見出しは削る。惜しければ Issue にして次の記事にする
- **`description` フロントマターは、メッセージの1文を縮めたものにする。** 書けないなら絞れていない

### 例外

Tips集（`vim-command.md`, `shell-utilities.md` など）は見出しごとに独立してよい。
ただし**道具は1つに固定する**（vimならvimだけ）。道具が混ざったらそれは分割対象。
この型では、想定読者が「その道具をすでに日常的に使っている人」に固定される。

## 全体構成

### 共通の骨格

| ブロック | 役割 | 分量 |
| :--- | :--- | :--- |
| 入り口 | 読者が「自分の話だ」と気づく。事象・疑問・きっかけ | 1〜3文 |
| 本題 | メッセージそのもの。原因 / 仕組み / 手順 | 全体の6割以上 |
| 結論 | メッセージの1文を、読者が使える形で再掲 | 数文 |
| 参考 | 一次情報へのリンク | リンクのみ |

「入り口」で背景を語りすぎない。**「本題」に一番文字数が割かれていない記事は、構成を間違えている。**

### 型を選ぶ

書きたいものがどれかを最初に決める。混ぜない。

| 型 | 見出しの並び | 手本 |
| :--- | :--- | :--- |
| **トラブルシュート** | 前提・環境 → 発生した問題 → 原因 → 解決策 → 参考 | `nuxt-content-cloudflare.md` |
| **疑問の深掘り** | 不思議に思ったこと → 調べてみた → 注意したい点 | `php-null.md` |
| **道具の紹介** | はじめに → 何ができるか → 使い方 → おわりに | `linux-fg-bg.md` |
| **作業ログ** | 背景と前提 → 工程ごとの見出し → ハマった点 → おわりに | `s3-to-rds.md` |
| **Tips集** | 見出し = Tips 1つ。並列 | `vim-command.md` |
| **書評** | どんな本か → 印象に残った点 → おすすめの読者 | `architecture-textbook.md` |

新しい型が必要になったらこの表に足す。

### 分量の目安

既存記事の実測は本文 1,200〜6,200字。

- 本文 **1,500〜4,000字**
- `##` 見出し **3〜6個**
- 1セクション **5〜15行**

**6,000字 / 200行を超えたら分割を検討する。** 作業ログ型だけは工程数ぶん超えてよい。

## 削るもの

長い記事は、たいてい以下が混ざっている。書いたあとに探して消す。

| 削るもの | 具体例 | どうするか |
| :--- | :--- | :--- |
| 前置きの自分語り | 「業務で〜という機会がありまして…」 | 1文に圧縮する |
| 調査過程の実況 | 試して外した案の逐一再現 | 結論に効いたものだけ残す |
| 教科書的な一般解説 | 用語の定義を一から説明する | 公式ドキュメントへのリンクで済ませる |
| 網羅的な例外リスト | 主筋に関係ない条件分岐 | 丸ごと落とす（ぼかさない） |
| 想定読者が知っていること | 前提技術の基礎解説 | 消す。読者を決めた時点で線は引けている |
| コードの全文貼り | 設定ファイル全体 | 差分と要点だけ。10行超えたら疑う |
| 言い換えの段落 | 「つまり」で始まり前段と同義 | 片方を消す |
| まとめでの本文再説明 | おわりに で全部おさらいする | メッセージの1文だけ残す |

## このブログの作法

### フロントマター

スキーマは `content.config.ts`。**スキーマ外のキーは Zod が黙って捨てるので書かない**（`layout` など）。

```md
---
title: "記事タイトル"
emoji: "🐘"
description: "メッセージの1文を縮めたもの"
published: true
date: 2026-09-01
tags:
  - nuxt.js
  - cloudflare
category: blog
---
```

`published: false` で下書きとして置ける。`category` は `blog` / `book`。

### 見出し

- `#` は使わない（`title` が h1）。本文は `##` から
- 見出しに「まとめ」ではなく中身を書く。読者は見出しだけ拾う

### コードブロック

言語指定は `nuxt.config.ts` の `langs` にあるものだけ色がつく。

`js` `ts` `json` `html` `css` `vue` `shell` `sh` `bash` `md` `mdc` `yaml` `vim` `lua` `sql` `php`

これ以外を使いたいときは `nuxt.config.ts` に追加する。

### Callout

Obsidian互換。`> [!TYPE] タイトル` で書く。

```md
> [!WARNING] ハマりどころ
> 本文
```

使えるタイプ: `note` `abstract` `info` `todo` `tip` `success` `question` `warning` `failure` `danger` `bug` `example` `quote`
（`summary` `tldr` `hint` `important` `check` `done` `help` `faq` `caution` `attention` `fail` `missing` `error` `cite` はエイリアス。未知のタイプは `note` になる）

`> [!NOTE]- タイトル` で折りたたみ（`-` は初期状態が閉、`+` は開）。

**多用しない。** 1記事に2〜3個まで。全部が強調されている記事は、何も強調されていない。

### リンク

- 外部の一次情報は本文中か「参考」に置く
- 同じ記事内の見出しへのリンクは `[見出し](#見出しのid)`

## 手順

1. **メッセージの1文を書く**（80字以内）
2. **想定読者の1文を書き、「説明しなくていいこと」を先に決める**
3. **型を選ぶ**（上の表から。混ぜない）
4. **見出しだけ並べる。** ここで「メッセージに奉仕していない見出し」を落とす
5. **本文を書く**
6. **削る**（上の表を上から順に探す）
7. **`npm run build` を通す**（コードブロックの言語指定漏れはここで出る）
8. **`description` とメッセージの1文がズレていないか確認する**

## レビューするとき

既存記事や下書きを見るときは、この順で見る。文章表現は指摘しない。

1. メッセージが1文で言えるか。言えないなら分割を提案する
2. **想定読者を本文から推測できるか。** できないなら、誰に向けたか決めずに書いている
3. 本題に6割以上の分量が割かれているか
4. 「削るもの」の表に当てはまる段落がないか
5. 分量が目安を超えていないか
