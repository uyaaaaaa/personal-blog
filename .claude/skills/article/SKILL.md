# 記事の書き方

`content/article/` に置く技術記事の進め方。**文章の巧拙は問わない。**
見るのは「伝えたいことが1つに絞れているか」と「それが想定読者に短く届くか」だけ。

## 前提

**記事の素材は、たいていこのリポジトリの外にある。**
既存記事の素材は業務・手元の環境・読んだ本が大半で、このブログ自体の実装を扱った記事は少数派。
コミットや Issue を読めば分かる、という前提で進めない。

**素材の一次情報は、たいてい書き手の記憶にある。**
だから質問は「確認」ではなく**取材**。調べてから聞くのではなく、聞かないと調べる対象すら分からない。

記事化の依頼は、たいてい**テーマ**の状態で来る（「インデックスの話を記事にしたい」）。
テーマのまま書き始めると、長いのに何も言っていない記事になる。
**テーマを1つの主張に詰めてから書く**のがこのスキルの本体。

## 進め方

**そのフェーズに入るときに、手順書を読む。先にまとめて読まない。**

| フェーズ | やること | 終了条件 | 手順書 |
| :--- | :--- | :--- | :--- |
| 1. 素材を見極める | 素材がどこにあり、何が自力で取れるかを判定する | 聞くべきことと、調べるべきことが分かれた | [interview.md](./references/interview.md) |
| 2. 詰める | 質問で取材しつつ、主題を1つに絞る | 暗黙の前提がゼロになり、シートが承認された | 同上 |
| 3. 書く | 型に沿って本文を書く | 全部の見出しがメッセージに奉仕している | [writing.md](./references/writing.md) |
| 4. 削る | 冗長を落とす | 分量の目安に収まった | 同上 |

書式（フロントマター・コードブロック・Callout）は、本文のファイルを触るときに [markdown.md](./references/markdown.md)。

**フェーズ2を飛ばさない。** 飛ばしてよいのは以下だけで、このときはフェーズ3から入る。

- 依頼にメッセージと想定読者が既に書かれている
- 既存記事のリライト・短縮（主題は決まっている）
- Tips集型（主題ではなく道具が軸）

## 優先順位

上が勝つ。迷ったら上を取る。

1. **メッセージが1つに絞れている**
2. **想定読者にとって短い**
3. **網羅的である**

3が一番下なのが要点。網羅性を守るために長くなるくらいなら、範囲を狭めて短く書く。

> [!WARNING] 「短くするために不正確に書く」は禁止
> 書けないものは丸ごと消す。消したことを断りたいときだけ「本記事は◯◯の場合に限ります」と1文入れる。
> 未検証の推測は、1文で「推測」と明示するか、書かない。

## レビューするとき

既存記事や下書きを見るときは、この順で見る。**文章表現は指摘しない。**

1. **本文からメッセージと想定読者を1文ずつ復元できるか。** できないなら、決めずに書いている
2. メッセージが1文で言えるか。言えないなら分割を提案する
3. 本題に6割以上の分量が割かれているか
4. 「[削るもの](./references/writing.md#フェーズ4-削る)」の表に当てはまる段落がないか
5. **読者が再現できるか。** バージョン・環境・一次情報のリンクが足りているか
6. [分量の目安](./references/writing.md#分量の目安)を超えていないか
