# 記事の書き方

`content/article/` に置く技術記事の進め方。**文章の巧拙は問わない。**
見るのは「伝えたいことが1つに絞れているか」と「それが想定読者に短く届くか」だけ。

## 前提

**記事の素材は、たいていこのリポジトリの外にある。**
既存記事の素材は業務・手元の環境・読んだ本が大半で、このブログ自体の実装を扱った記事は少数派。
コミットや Issue を読めば分かる、という前提で進めない。

**素材の一次情報は、たいてい書き手の記憶にある。**
だから質問は「確認」ではなく**取材**。調べてから聞くのではなく、聞かないと調べる対象すら分からない。

記事化の依頼は、たいてい**テーマ**の状態で来る（「インデックスの話を記事にしたい」）。
テーマのまま書き始めると、長いのに何も言っていない記事になる。
**テーマを1つの主張に詰めてから書く**のがこのスキルの本体。

## 進め方

| フェーズ | やること | 終了条件 |
| :--- | :--- | :--- |
| 1. 素材を見極める | 素材がどこにあり、何が自力で取れるかを判定する | 聞くべきことと、調べるべきことが分かれた |
| 2. 詰める | 質問で取材しつつ、主題を1つに絞る | 暗黙の前提がゼロになり、シートが承認された |
| 3. 書く | 型に沿って本文を書く | 全部の見出しがメッセージに奉仕している |
| 4. 削る | 冗長を落とす | 分量の目安に収まった |

**フェーズ2を飛ばさない。** 飛ばしてよいのは「[詰めない場合](#詰めない場合)」だけ。

## 優先順位

上が勝つ。迷ったら上を取る。

1. **メッセージが1つに絞れている**
2. **想定読者にとって短い**
3. **網羅的である**

3が一番下なのが要点。網羅性を守るために長くなるくらいなら、範囲を狭めて短く書く。

> [!WARNING] 「短くするために不正確に書く」は禁止
> 3の優先度が低いのは「書ききれない厳密さを**落としてよい**」という意味であって、
> 「**ぼかしてよい**」ではない。曖昧な記述は短くならないうえに誤読を生むので、両取りできない。
> 書けないものは丸ごと消す。消したことを断りたいときだけ「本記事は◯◯の場合に限ります」と1文入れる。
> 未検証の推測は、1文で「推測」と明示するか、書かない。

## フェーズ1: 素材を見極める

**まず取材源を判定する。** ここを飛ばすと、見えないものを調べようとするか、聞けば済むことを聞かずに書く。

| 取材源 | 例 | 自力で取れるか | やること |
| :--- | :--- | :--- | :--- |
| **業務・別リポジトリ** | 6,500万件のテーブル、React Native の実機不具合 | **取れない。かつそのままは出せない** | 記憶を聞き出し、一般化する |
| **手元の環境** | dotfiles、vim / zsh の設定、インストール作業 | セッションから見えないことが多い | 設定・バージョン・出力を貼ってもらう |
| **読んだ本・記事** | 書評、輪読の感想 | 取れない | 何がどう刺さったかを聞く |
| **公開情報** | 公式ドキュメント、OSS の Issue、言語仕様 | 取れる | 一次情報に当たり、リンクする |
| **その場で試したこと** | 記事のために手元で再現する | 実行できる | 最小再現例を作って動かす |
| **このリポジトリ** | ブログ自体の実装 | 取れる | コード・Issue・PR を先に読む |

**「このリポジトリ」は少数派。** ここに当てはまらない依頼のほうが多いと考える。

### 事実は取りにいく。決定は本人に返す

- **取れる事実は、聞く前に取る。** 公開情報とこのリポジトリの分は先に調べる。
  調べた結果は質問と一緒に短く出す。「調べたらこうだった。この理解で合っているか」の形にすると1往復で済む
- **取れない事実は、聞く。** 業務の記憶や手元の環境は、どれだけ調べても出てこない。**ここが取材**
- **決定は必ず本人に返す。** メッセージ・想定読者・型・何を公開するかを、こちらで決めない

### そのまま書けないものを先に分ける

業務由来の素材には、公開できない情報が混ざる。**書き始めてから気づくと構成ごと崩れる**ので先に仕分ける。

- コード・スキーマ・クエリの原文、社内の固有名詞、URL、正確な数値、顧客名
- → **一般化する。** 既存記事は実際にそうしている（`mysql-index.md` はカラム名を「カラムA」、型を「TEXT型のnullable」とだけ書く）
- → **一般化すると主題が消えるなら、その記事は書かない**か、別の切り口にする

> [!WARNING] 出せる / 出せないの判断は書き手がする
> 何を公開してよいかは決定であって事実ではない。こちらで決めず、迷うものは必ず本人に確認する。

## フェーズ2: 詰める

### 確定させる7項目

これが埋まるまで本文を1行も書かない。

| 項目 | 形式 |
| :--- | :--- |
| **メッセージ** | 80字以内の1文。「読んだ人に何を持ち帰ってほしいか」 |
| **想定読者** | 1文。「◯◯していて、△△に困っている人」 |
| **説明しないこと** | 想定読者がすでに知っていること |
| **説明すること** | 想定読者が知らず、かつメッセージに必要なこと |
| **素材と裏取り** | 何をもとに書くか。何で裏を取るか |
| **型** | [型の表](#型を選ぶ)から1つ |
| **今回落とすもの** | 書きたいが入らないもの・出せないもの |

**「説明しないこと」と「説明すること」が、そのまま分量を決める。**
読者を決めていないとこの線が引けないので、結果として全部書くことになる。これが冗長化の最大の原因。

### 質問の順序

**答えを聞かないと立てられない質問を、同じラウンドに混ぜない。**
前のラウンドの答えが決まって初めて意味を持つ問いは、次のラウンドに送る。

**ラウンド1 — 前提なしで答えられる**

| # | 聞くこと | なぜ効くか |
| :--- | :--- | :--- |
| 1 | **言い切ると何になるか。** 「◯◯について」はテーマ。1文で言い切ると? | テーマのままでは構成が決まらない |
| 2 | **誰が読むか。その人は何を知っているか** | 説明の下限と上限が決まり、分量が決まる |
| 3 | **何時のことか。何をもとに書くか。何を使っていたか** | 素材の所在とバージョンが決まらないと、裏の取りようがない |

**ラウンド2 — ラウンド1が決まって初めて聞ける**

| # | 聞くこと | 何に依存するか |
| :--- | :--- | :--- |
| 4 | **意外なのはどこか。** 読者が予想しないのはどの部分か | 2。読者が決まらないと「意外」が定義できない |
| 5 | **主張は1つか。** 2つあるなら、どちらを今回書くか | 1。言語化されて初めて数えられる |
| 6 | **裏はどう取れるか。** ログ・設定・エラー文はあるか。公式ドキュメントは何と言っているか | 3。素材の所在で手段が変わる |
| 7 | **そのまま書けないものはあるか** | 3。同上 |

**ラウンド3 — 残っていれば**

| # | 聞くこと | なぜ効くか |
| :--- | :--- | :--- |
| 8 | **落とすものに合意できるか** | 先に合意しておくと、フェーズ4で削る抵抗が減る |

**ラウンド1で崩れたら、そこで止める。** 「実は2記事だった」「意外な点がない」と分かった時点で、
残りの質問は無意味になる。

補足として効く問い。

- メッセージの1文が「かつ」「また」「ついでに」で繋がったら、**2記事に分ける**
- 想定読者がその技術の初心者まで広がったら、**狭める**。広く狙うと一般解説が膨らんで主題が薄まる
- 想定読者がすでに知っていることをメッセージにしていないか。そうなら記事として成立しない

### 聞き方

- **1ラウンド分をまとめて聞く。** `AskUserQuestion` で複数問を一度に出す。1問ずつ往復しない
- **全問に推奨案を付ける。** 選択肢の先頭を推奨にして「（推奨）」と書く。
  書き手が「全部それでいい」の一言で返せる状態にする。推奨の無い質問は、こちらが考えていないだけ
- **調査待ちでラウンドを止めない。** 公式ドキュメントの確認などが要るときは、
  **それに依存する質問だけ次ラウンドに送り**、残りは今のラウンドで聞く
- **記憶があやふやな部分は、そのまま流さない。** 「推測として書くか、落とすか」を選ばせる
- **収束しないなら分割を提案する。** ラウンドを重ねても主張が1つにならないなら、テーマが大きすぎる

### 詰めない場合

以下はフェーズ2を飛ばしてよい。

- 依頼にメッセージと想定読者が既に書かれている
- 既存記事のリライト・短縮（主題は決まっている）
- Tips集型（主題ではなく道具が軸）

### 取り決めシート

7項目を並べて提示し、承認を取ってから書き始める。

**埋まっているだけでは終わっていない。** 各欄について、書き手のどの答えから決まったかを辿れるか確認する。
聞かずにこちらで埋めた欄があれば、それは暗黙の前提であって決定ではない。

```
メッセージ　: 6,500万件のテーブルへのCREATE INDEXは、オンラインDDLなら止めずに打てる。
　　　　　　  ただし事前に確認すべきことがある
想定読者　　: 本番のMySQLに大きなテーブルを抱えていて、インデックス追加が怖い人
説明しない　: インデックスの仕組み、SQLの基本、DDL/DML/DCLの分類
説明する　　: オンラインDDLで何がロックされないのか、実行前に何を確認したか
素材と裏取り: 業務での実作業（記憶）＋ MySQL公式ドキュメント ＋ テスト環境での実測
型　　　　　: 作業ログ
落とすもの　: 実テーブル名・スキーマ（一般化する）、DDLの用語解説（一般解説なので落とす）
```

> [!NOTE] シートは本文に書かない
> 「対象読者」という見出しを立てて宣言はしない。想定読者は構成の裏側で効かせる。
> ただし、トラブルシュート型・作業ログ型の「前提条件・環境」は別。
> あれは読者の宣言ではなく**再現条件の事実**なので、必要なら書く。

Issue から始まった記事なら、シートを Issue に書き残す。無ければ、やりとりの中で確定させておけばよい。

## フェーズ3: 書く

### 共通の骨格

| ブロック | 役割 | 分量 |
| :--- | :--- | :--- |
| 入り口 | 読者が「自分の話だ」と気づく。事象・疑問・きっかけ | 1〜3文 |
| 本題 | メッセージそのもの。原因 / 仕組み / 手順 | 全体の6割以上 |
| 結論 | メッセージの1文を、読者が使える形で再掲 | 数文 |
| 参考 | 一次情報へのリンク | リンクのみ |

「入り口」で背景を語りすぎない。**本題に一番文字数が割かれていない記事は、構成を間違えている。**

### 型を選ぶ

シートで決めた型に沿う。混ぜない。

| 型 | 見出しの並び | 手本 |
| :--- | :--- | :--- |
| **トラブルシュート** | 前提・環境 → 発生した問題 → 原因 → 解決策 → 参考 | `react-native-reduce.md` |
| **疑問の深掘り** | 不思議に思ったこと → 調べてみた → 注意したい点 | `php-null.md` |
| **道具の紹介** | はじめに → 何ができるか → 使い方 → おわりに | `linux-fg-bg.md` |
| **作業ログ** | 背景と前提 → 工程ごとの見出し → ハマった点 → おわりに | `s3-to-rds.md` |
| **Tips集** | 見出し = Tips 1つ。並列 | `vim-command.md` |
| **書評** | どんな本か → 印象に残った点 → おすすめの読者 | `architecture-textbook.md` |

新しい型が必要になったらこの表に足す。

**Tips集型だけは1記事1メッセージの例外。** ただし道具は1つに固定する（vimならvimだけ）。
道具が混ざったら分割対象。この型では想定読者が「その道具を日常的に使っている人」に固定される。

### 素材の出しかた

- **バージョンと環境を書く。** 「PHP 7.0以降」「MySQL 8.0」のように、読者が自分に当てはまるか判断できる形で
- **一次情報にリンクする。** LLM や二次情報の要約を引くなら、公式ドキュメントへのリンクも必ず併記する（`mysql-index.md` の作法）
- **再現できるものは再現して書く。** 手元で動かせる最小例は、記憶の説明より短くて強い
- **裏が取れなかったことは「推測」と1文で明示するか、落とす**

### 書く順番

1. **見出しだけ並べる。** ここで「メッセージに奉仕していない見出し」を落とす
2. 本題から書く。入り口とおわりには最後に手を付ける

### 分量の目安

既存記事の実測は本文 1,200〜6,200字。

- 本文 **1,500〜4,000字**
- `##` 見出し **3〜6個**
- 1セクション **5〜15行**

**6,000字 / 200行を超えたら分割を検討する。** 作業ログ型だけは工程数ぶん超えてよい。

## フェーズ4: 削る

長い記事には、たいてい以下が混ざっている。書いたあとに上から順に探して消す。

| 削るもの | 具体例 | どうするか |
| :--- | :--- | :--- |
| 想定読者が知っていること | 前提技術の基礎解説 | 消す。シートで線は引けている |
| 前置きの自分語り | 「業務で〜という機会がありまして…」 | 1文に圧縮する |
| 調査過程の実況 | 試して外した案の逐一再現 | 結論に効いたものだけ残す |
| 教科書的な一般解説 | 用語の定義を一から説明する | 公式ドキュメントへのリンクで済ませる |
| 網羅的な例外リスト | 主筋に関係ない条件分岐 | 丸ごと落とす（ぼかさない） |
| コードの全文貼り | 設定ファイル全体 | 差分と要点だけ。10行超えたら疑う |
| 言い換えの段落 | 「つまり」で始まり前段と同義 | 片方を消す |
| まとめでの本文再説明 | おわりに で全部おさらいする | メッセージの1文だけ残す |

### 書き終わったら

- [ ] `description` フロントマターが、メッセージの1文を縮めたものになっている
- [ ] シートの「落とすもの」が本文に紛れ込んでいない
- [ ] **出せない情報が残っていない**（社内の固有名詞、実スキーマ、URL、顧客名）
- [ ] `npm run build` が通る（コードブロックの言語指定漏れはここで出る）

## このブログの作法

### フロントマター

スキーマは `content.config.ts`。**スキーマ外のキーは Zod が黙って捨てるので書かない**（`layout` など）。

```md
---
title: "記事タイトル"
emoji: "🐘"
description: "メッセージの1文を縮めたもの"
published: true
date: 2026-09-01
tags:
  - mysql
  - index
category: blog
---
```

`published: false` で下書きとして置ける。`category` は `blog` / `book`。

### 見出し

- `#` は使わない（`title` が h1）。本文は `##` から
- 見出しに「まとめ」ではなく中身を書く。読者は見出しだけ拾う

### コードブロック

言語指定は `nuxt.config.ts` の `langs` にあるものだけ色がつく。

`js` `ts` `json` `html` `css` `vue` `shell` `sh` `bash` `md` `mdc` `yaml` `vim` `lua` `sql` `php`

これ以外を使いたいときは `nuxt.config.ts` に追加する。

### Callout

Obsidian互換。`> [!TYPE] タイトル` で書く。

```md
> [!WARNING] ハマりどころ
> 本文
```

使えるタイプ: `note` `abstract` `info` `todo` `tip` `success` `question` `warning` `failure` `danger` `bug` `example` `quote`
（`summary` `tldr` `hint` `important` `check` `done` `help` `faq` `caution` `attention` `fail` `missing` `error` `cite` はエイリアス。未知のタイプは `note` になる）

`> [!NOTE]- タイトル` で折りたたみ（`-` は初期状態が閉、`+` は開）。

**多用しない。** 1記事に2〜3個まで。全部が強調されている記事は、何も強調されていない。

### リンク

- 外部の一次情報は本文中か「参考」に置く
- 同じ記事内の見出しへのリンクは `[見出し](#見出しのid)`

## レビューするとき

既存記事や下書きを見るときは、この順で見る。**文章表現は指摘しない。**

1. **本文からメッセージと想定読者を1文ずつ復元できるか。** できないなら、決めずに書いている
2. メッセージが1文で言えるか。言えないなら分割を提案する
3. 本題に6割以上の分量が割かれているか
4. 「削るもの」の表に当てはまる段落がないか
5. **読者が再現できるか。** バージョン・環境・一次情報のリンクが足りているか
6. 分量が目安を超えていないか
