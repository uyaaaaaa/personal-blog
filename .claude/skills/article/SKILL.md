# 記事の書き方

`content/article/` に置く技術記事の進め方。**文章の巧拙は問わない。**
見るのは「伝えたいことが1つに絞れているか」と「それが想定読者に短く届くか」だけ。

記事化の依頼は、たいてい**テーマ**の状態で来る（「ダークテーマの話を記事にして」）。
テーマのまま書き始めると、長いのに何も言っていない記事になる。
**テーマを1つの主張に詰めてから書く**のがこのスキルの本体。

## 進め方

| フェーズ | やること | 終了条件 |
| :--- | :--- | :--- |
| 0. 調べる | コード・Issue・PR・コミットを読む | 残る質問が「本人にしか答えられないこと」だけになった |
| 1. 詰める | 質問して主題を1つに絞る | 取り決めシートが埋まり、承認された |
| 2. 書く | 型に沿って本文を書く | 全部の見出しがメッセージに奉仕している |
| 3. 削る | 冗長を落とす | 分量の目安に収まった |

**フェーズ1を飛ばさない。** 飛ばしてよいのは「[詰めない場合](#詰めない場合)」だけ。

## 優先順位

上が勝つ。迷ったら上を取る。

1. **メッセージが1つに絞れている**
2. **想定読者にとって短い**
3. **網羅的である**

3が一番下なのが要点。網羅性を守るために長くなるくらいなら、範囲を狭めて短く書く。

> [!WARNING] 「短くするために不正確に書く」は禁止
> 3の優先度が低いのは「書ききれない厳密さを**落としてよい**」という意味であって、
> 「**ぼかしてよい**」ではない。曖昧な記述は短くならないうえに誤読を生むので、両取りできない。
> 書けないものは丸ごと消す。消したことを断りたいときだけ「本記事は◯◯の場合に限ります」と1文入れる。
> 未検証の推測は、1文で「推測」と明示するか、書かない。

## フェーズ0: 詰める前に調べる

**本人に聞く前に、リポジトリで分かることは全部調べる。**
調査を省いた質問は、書き手の時間を奪うだけで主題は絞れない。

- 記事の元になった実装を読む（コミット、PR、Issue、該当ファイル）
- 記事の根拠になる事実を集める（実測値、エラーメッセージ、設定の差分、日付）
- `content/article/` に同じ主題の記事がないか確認する

**調べた結果は、質問と一緒に短く提示する。**
「調べたらこうだった。この理解で合っているか」の形にすると、1往復で済む。

## フェーズ1: 詰める

### 確定させる6項目

これが埋まるまで本文を1行も書かない。

| 項目 | 形式 |
| :--- | :--- |
| **メッセージ** | 80字以内の1文。「読んだ人に何を持ち帰ってほしいか」 |
| **想定読者** | 1文。「◯◯していて、△△に困っている人」 |
| **説明しないこと** | 想定読者がすでに知っていること |
| **説明すること** | 想定読者が知らず、かつメッセージに必要なこと |
| **型** | [型の表](#型を選ぶ)から1つ |
| **今回落とすもの** | 書きたいが入らないもの。Issue に回す |

**「説明しないこと」と「説明すること」が、そのまま分量を決める。**
読者を決めていないとこの線が引けないので、結果として全部書くことになる。これが冗長化の最大の原因。

### 質問の型

**上から順に効く。** 1〜2問で崩れたら、それより下は聞かなくていい。

| # | 聞くこと | なぜ効くか |
| :--- | :--- | :--- |
| 1 | **言い切ると何になるか。** 「◯◯について」はテーマ。1文で言い切ると? | テーマのままでは構成が決まらない |
| 2 | **誰が読むか。その人は何を知っているか** | 説明の下限と上限が決まり、分量が決まる |
| 3 | **意外なのはどこか。** 読者が予想しないのはどの部分か | 意外な点がないなら記事にする価値がない。公式ドキュメントで足りる |
| 4 | **主張は1つか。** 2つあるなら、どちらを今回書くか | 1記事1メッセージ。残りは Issue にする |
| 5 | **根拠は何か。** 実測値・コミット・エラー文はあるか | 無いものは「推測」と書くか、落とす |
| 6 | **入らないものに合意できるか** | 先に合意しておくと、フェーズ3で削る抵抗が減る |

補足として効く問い。

- メッセージの1文が「かつ」「また」「ついでに」で繋がったら、**2記事に分ける**
- 想定読者がその技術の初心者まで広がったら、**狭める**。広く狙うと一般解説が膨らんで主題が薄まる
- 想定読者がすでに知っていることをメッセージにしていないか。そうなら記事として成立しない

### 聞き方

- **`AskUserQuestion` で複数まとめて聞く。** 1問ずつ往復しない
- **多くて2ラウンド。** それで絞れないならテーマが大きすぎるので、分割を提案する
- **選択肢の形にする。** 「どう書きたいですか」ではなく「A / B / 両方なら分割」で聞く
- **自分の仮説を先に置く。** 「調べた限り B が主題に見える。合っているか」

### 詰めない場合

以下はフェーズ1を飛ばしてよい。

- 依頼にメッセージと想定読者が既に書かれている
- 既存記事のリライト・短縮（主題は決まっている）
- Tips集型（主題ではなく道具が軸）

### 取り決めシート

6項目を並べて提示し、承認を取ってから書き始める。

```
メッセージ: ダークテーマ導入自体は簡単。その簡単さは直前のトークン一本化が作っている
想定読者　: Nuxt + Tailwind でサイトを持っていて、ダークテーマを後から入れたい人
説明しない: Tailwind の基本、@nuxtjs/color-mode の導入手順
説明する　: トークン一本化だけでは足りず、Tailwind 側も var() 参照にする必要がある理由
型　　　　: 疑問の深掘り
落とすもの: コントラスト比の測定手順（別記事にする）
```

> [!NOTE] シートは本文に書かない
> 「対象読者」という見出しを立てて宣言はしない。想定読者は構成の裏側で効かせる。
> ただし、トラブルシュート型・作業ログ型の「前提条件・環境」は別。
> あれは読者の宣言ではなく**再現条件の事実**なので、必要なら書く。

記事の元ネタが Issue にあるなら、**シートを Issue に書き残す**。
本文に残らないので、書かないとリライト時に前提が失われる。

## フェーズ2: 書く

### 共通の骨格

| ブロック | 役割 | 分量 |
| :--- | :--- | :--- |
| 入り口 | 読者が「自分の話だ」と気づく。事象・疑問・きっかけ | 1〜3文 |
| 本題 | メッセージそのもの。原因 / 仕組み / 手順 | 全体の6割以上 |
| 結論 | メッセージの1文を、読者が使える形で再掲 | 数文 |
| 参考 | 一次情報へのリンク | リンクのみ |

「入り口」で背景を語りすぎない。**本題に一番文字数が割かれていない記事は、構成を間違えている。**

### 型を選ぶ

シートで決めた型に沿う。混ぜない。

| 型 | 見出しの並び | 手本 |
| :--- | :--- | :--- |
| **トラブルシュート** | 前提・環境 → 発生した問題 → 原因 → 解決策 → 参考 | `nuxt-content-cloudflare.md` |
| **疑問の深掘り** | 不思議に思ったこと → 調べてみた → 注意したい点 | `php-null.md` |
| **道具の紹介** | はじめに → 何ができるか → 使い方 → おわりに | `linux-fg-bg.md` |
| **作業ログ** | 背景と前提 → 工程ごとの見出し → ハマった点 → おわりに | `s3-to-rds.md` |
| **Tips集** | 見出し = Tips 1つ。並列 | `vim-command.md` |
| **書評** | どんな本か → 印象に残った点 → おすすめの読者 | `architecture-textbook.md` |

新しい型が必要になったらこの表に足す。

**Tips集型だけは1記事1メッセージの例外。** ただし道具は1つに固定する（vimならvimだけ）。
道具が混ざったら分割対象。この型では想定読者が「その道具を日常的に使っている人」に固定される。

### 書く順番

1. **見出しだけ並べる。** ここで「メッセージに奉仕していない見出し」を落とす
2. 本題から書く。入り口とおわりには最後に手を付ける

### 分量の目安

既存記事の実測は本文 1,200〜6,200字。

- 本文 **1,500〜4,000字**
- `##` 見出し **3〜6個**
- 1セクション **5〜15行**

**6,000字 / 200行を超えたら分割を検討する。** 作業ログ型だけは工程数ぶん超えてよい。

## フェーズ3: 削る

長い記事には、たいてい以下が混ざっている。書いたあとに上から順に探して消す。

| 削るもの | 具体例 | どうするか |
| :--- | :--- | :--- |
| 想定読者が知っていること | 前提技術の基礎解説 | 消す。シートで線は引けている |
| 前置きの自分語り | 「業務で〜という機会がありまして…」 | 1文に圧縮する |
| 調査過程の実況 | 試して外した案の逐一再現 | 結論に効いたものだけ残す |
| 教科書的な一般解説 | 用語の定義を一から説明する | 公式ドキュメントへのリンクで済ませる |
| 網羅的な例外リスト | 主筋に関係ない条件分岐 | 丸ごと落とす（ぼかさない） |
| コードの全文貼り | 設定ファイル全体 | 差分と要点だけ。10行超えたら疑う |
| 言い換えの段落 | 「つまり」で始まり前段と同義 | 片方を消す |
| まとめでの本文再説明 | おわりに で全部おさらいする | メッセージの1文だけ残す |

### 書き終わったら

- [ ] `description` フロントマターが、メッセージの1文を縮めたものになっている
- [ ] シートの「落とすもの」が本文に紛れ込んでいない
- [ ] `npm run build` が通る（コードブロックの言語指定漏れはここで出る）

## このブログの作法

### フロントマター

スキーマは `content.config.ts`。**スキーマ外のキーは Zod が黙って捨てるので書かない**（`layout` など）。

```md
---
title: "記事タイトル"
emoji: "🐘"
description: "メッセージの1文を縮めたもの"
published: true
date: 2026-09-01
tags:
  - nuxt.js
  - cloudflare
category: blog
---
```

`published: false` で下書きとして置ける。`category` は `blog` / `book`。

### 見出し

- `#` は使わない（`title` が h1）。本文は `##` から
- 見出しに「まとめ」ではなく中身を書く。読者は見出しだけ拾う

### コードブロック

言語指定は `nuxt.config.ts` の `langs` にあるものだけ色がつく。

`js` `ts` `json` `html` `css` `vue` `shell` `sh` `bash` `md` `mdc` `yaml` `vim` `lua` `sql` `php`

これ以外を使いたいときは `nuxt.config.ts` に追加する。

### Callout

Obsidian互換。`> [!TYPE] タイトル` で書く。

```md
> [!WARNING] ハマりどころ
> 本文
```

使えるタイプ: `note` `abstract` `info` `todo` `tip` `success` `question` `warning` `failure` `danger` `bug` `example` `quote`
（`summary` `tldr` `hint` `important` `check` `done` `help` `faq` `caution` `attention` `fail` `missing` `error` `cite` はエイリアス。未知のタイプは `note` になる）

`> [!NOTE]- タイトル` で折りたたみ（`-` は初期状態が閉、`+` は開）。

**多用しない。** 1記事に2〜3個まで。全部が強調されている記事は、何も強調されていない。

### リンク

- 外部の一次情報は本文中か「参考」に置く
- 同じ記事内の見出しへのリンクは `[見出し](#見出しのid)`

## レビューするとき

既存記事や下書きを見るときは、この順で見る。**文章表現は指摘しない。**

1. **本文からメッセージと想定読者を1文ずつ復元できるか。** できないなら、決めずに書いている
2. メッセージが1文で言えるか。言えないなら分割を提案する
3. 本題に6割以上の分量が割かれているか
4. 「削るもの」の表に当てはまる段落がないか
5. 分量が目安を超えていないか
