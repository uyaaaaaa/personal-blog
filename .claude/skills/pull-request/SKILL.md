# PR の作り方

実装は終わっていて、**実測が済んでいる**前提。まだ測っていなければ `verify` に戻る。

## PR にしない場合

- スコープが2つ以上に割れている（分ける）
- 依頼が調査・確認だけで、差分が無い

## 1. 出す前

- 最新の `main` から派生。コンフリクトの有無を先に確認
- ブランチ名は `claude/<主題>-<英数字4〜6>`
- 実測用の一時的な細工が残っていないこと

## 2. タイトル

- 何をどう変えたかを1行で言い切る
- issue タイトルの写しにしない（issue は現象、PR は変更）
- 分類の接頭辞は付けない

## 3. 本文

### 原則: 機械が持っているものを写さない

| 写さないもの | どこが持っているか |
| :--- | :--- |
| ファイル名・件数・数値・関数名・クラス名・設定キーの列挙 | 差分 |
| CI が判定した結果 | PR の緑と赤（何を打つかは `.github/workflows/`） |

残すのは、**判断・理由・機械が出さない確認結果**と、**差分からは読み取りにくい変更の形**。前置きは書かない。各節はリストで、体言止めの短い1文にする。

### 節

上から順。不要な節は落とす。

| 節 | 中身 | 落とす条件 |
| :--- | :--- | :--- |
| `Closes #N` | 対応する issue | issue が無い |
| 背景 | なぜ必要か。事象と影響 | やったことだけで自明 |
| やったこと | 変えたことの列挙と、要るときだけ形の図1つ | なし（必須） |
| issue から変えた点 | issue に書かれた手段を採らなかった理由と代替 | issue のとおりに実装した |
| 確認 | CI が打たない実測の、前と後 | 測ったものが CI の範囲に収まる |
| マージの危険 | 戻せるかと、影響の範囲 | なし（必須） |
| このPRでやらないこと | 送り先の issue 番号 | 送るものが無い |

### やったことの節

- **1項目を折り返しのない1行に収める。** 目安は40字。収まらないなら詳細度が高すぎる
- 内訳・件数を書かない。読み手が要るのは差分を読む前の見取り図だけ
- 波及の追従は、範囲を並べずに1行にまとめる

**構造や流れが変わるときだけ、形を最小の図1つで添える。** 散らばった差分からは、組み上がった形が見えないため。

| 変わるもの | 図 |
| :--- | :--- |
| コンポーネントの入れ子 | コンポーネントの木。触った枝だけ |
| 呼び出しや処理の流れ | 呼び出しの木か疑似コード |
| ファイルの置き場 | 浅いファイルの木 |
| 要素どうしのやりとり | Mermaid のシーケンス図 |

- 既にある形に足す・消すだけなら、その図を `diff` で書く（`+` と `-` の行だけで変化が分かる）
- 図には、要点に要る名前・境界・状態だけを残す。図のための名前は、写しの禁止の例外

### 確認の節

**`verify` の報告表から、CI が打つものの行と証跡の列を落とし、前と後を並べて置く。**

- 見た目の変更は、`before-` と後の撮影を並べるのが最も強い
- それ以外は、直す前に落ちて直した後に通る実行結果（テスト・出力）を並べる
- 結果には、証跡から引いた根拠を残す。「問題なし」ではなく、件数・バイト数・観測した行
- 測れなかったものは「未実施」と明記する。空欄にも「問題なし」にもしない
- **残るものが無ければ節ごと落とす**

### マージの危険の節

書き手がマージを決めるための材料。2行で書く。

- **戻せるか。** 取り消しの PR で元に戻るなら「戻せる」。公開 URL・静的生成で配られる HTML の形・消した記事のように、出した後に戻しても外に残るものがあれば「戻せない」と、その理由
- **影響の範囲。** 1語で言い、要るときだけ1文を足す（例: 「全ページのヘッダー」「記事の目次だけ」「エージェントの手順だけ」）

## 4. 出す

- 作成は GitHub MCP の PR 作成ツール。base は `main`
- **`agent` ラベルを必ず付ける。** エージェントが書いたことを表すだけの印で、出来や可否は表さない

### 書き手に返す判断が残っているなら draft で出す

**自分で決めずに書き手へ返す判断があるときは、draft で出す。** ready にするのは判断が返ってから。
draft はラベルと違い、マージを機械的に塞ぐ。ラベルの不在は、付け忘れ・人間の PR と区別が付かない。

- **判断はコメントに書く。** 選択肢とそれぞれで何が変わるかを添え、推奨を先頭に置く
- **その判断に依る箇所は直さない。** 書き手の判断を先取りしない
- **それ以外は draft でも直す。** CI の赤、自明な不具合、レビューの小さな指摘は自分で直す

## 5. 出した後

**`followup` に従う。** 購読・レビュー依頼・CI とレビューへの追従はそちらが持つ。
