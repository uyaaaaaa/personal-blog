# issue 対応の手順

**対象は issue 番号のある依頼だけ。** 症状だけの依頼は `ui-change`、記事は `article`、番号の無い課題は `create-issues`。

**実装の手順はここに無い。** UI は `ui-change`、記事は `article`、実測は `verify`、PR の型は `pr`、出した後は `followup` に従う。ここが持つのは、issue 1本を PR にするまでの進め方。

## 1. 読む

**issue に書かれていることは、すべて仮説として読む。**

- **原因は実装で裏を取る。** 行番号・変数名は書いた時点のもの
- **書かれた解決手段の採用を約束しない。** 判断は実測の後でよい
- **触る範囲の方針を先に読む。** UI は `docs/DESIGN_GUIDELINE.md`、構造は `docs/ARCHITECTURE.md` の該当節
- **再現してから直す。** 実データで条件が揃わないなら、条件を作って再現する

ブランチは最新の `main` から切る。

## 2. 直す

- **issue の範囲から出ない。** 見つけた別の問題は直さず、PR の「このPRでやらないこと」に書く。issue が無ければ `create-issues` で立てる
- **前提が崩れたら手を止める。** 直し方を自分で決めない（→ 2-A）

### A. 解決手段を変えるときだけ確認を取る

原因調査と実装は自走してよい。**確認を取るのは、issue に書かれた解決手段を採らないと判断したときだけ。**

`AskUserQuestion` に2つを揃える。採らない理由（試して壊れたならその出力）と、代案で何が変わるか。

## 3. 実測する

**`verify` に従う。**

## 4. 出す

文書は原則書かない（→ `.claude/rules/docs.md`）。方針に触れたときだけ、該当箇所を直す。

**PR の型は `pr` に従う。** issue 対応で必ず入れるのは3つ。

- `Closes #<番号>`
- 書かれた手段を採らなかったときの「issue から変えた点」
- 実測の表

| 状況 | どうする |
| :--- | :--- |
| セッション内で答えを待てる | 2-A の `AskUserQuestion` |
| 待てない、差分を見せたほうが答えやすい | draft で出してコメントで問う |

`dispatch` から起きたセッションは答えを待てない。下段に倒す。

## 5. 見届ける

**`followup` に従う。** 購読・レビュー依頼・CI とレビューへの追従はそちらが持つ。

issue は書き手のマージで `Closes` が閉じる。
