# issue 対応の手順

**対象は issue 番号のある依頼だけ。** 症状だけの依頼（「表示がおかしい」）は `ui-change`、記事の依頼は `article`、番号の無い課題を issue にする依頼は `create-issues` に行く。

このスキルは issue を1本閉じるまでの**進め方**だけを扱う。**実装の手順は書かない**（UI なら `ui-change`、記事なら `article` に従う）。

## 全体

| フェーズ | やること | 終了条件 |
| :--- | :--- | :--- |
| 1. 読む | issue と実装を突き合わせる | issue が挙げた原因を実装で裏取りできた |
| 2. 直す | 委譲先の手順で実装する | スコープが issue の中に収まっている |
| 3. 実測する | `verify` に従って測る | 直ったことをコマンドの出力で示せた |
| 4. 出す | 記録・コミット・`pr` で PR | PR に実測の表が載った |
| 5. 見届ける | レビューを起こし、CI と指摘に追従する | 緑と判定を報告した |

---

## 1. 読む

**issue に書かれていることは、すべて仮説として読む。**

- **原因は実装で裏を取る。** issue の行番号・変数名は書いた時点のもの。該当ファイルを開いて、いま同じ状態か確認する。
- **書かれた解決手段の採用を約束しない。** 判断は3の後でよい。
- **触る範囲の方針を先に読む。** UI なら `docs/DESIGN_GUIDELINE.md` の該当節、構造なら `docs/ARCHITECTURE.md`。個々の指定の理由は文書に無いので、一見不要に見える指定は消して実測で確かめる（→ 3）。
- **再現できるか確かめる。** 再現しないなら、実データでは条件が揃っていないだけのことがある。**条件を作って再現する**（→ 3）。

ブランチは `claude/issue-<番号>-<英数字4〜6>` を最新の `main` から切る。

## 2. 直す

- **UI に触るなら `ui-change` の手順に従う。**
- **issue の範囲から出ない。** 途中で見つけた別の問題は直さず、PR の「このPRでやらないこと」に番号付きで書く。無ければ `create-issues` で立てる。
- **前提が崩れたら手を止める。** 実装中に前提が壊れたときは、直し方を自分で決めずに 2-A へ。

### A. 解決手段を変えるときだけ確認を取る

原因調査と実装は自走してよい。**確認を取るのは、issue に書かれた解決手段を採らない判断をしたときだけ。**

`AskUserQuestion` で、この3つを揃えて出す。

1. **採らない理由**（試して壊れたなら、その出力）
2. **代案と、それで何が変わるか**
3. **推奨（先頭に置く）**

## 3. 実測する

**`verify` スキルに従う。** 実測の手順はそちらが持つ。ここでは issue 対応に固有のことだけ。

- **直す前に、issue の現象を一度再現する。** 再現していない不具合は、直ったことも確認できない。
- **実データで条件が揃わないものは、条件を作って測る。**
- **issue に書かれた再現条件を全部通す。** 1つ通ったところで止めない。
- 時間のかかる測定は、サブエージェントに委譲してよい。**判断は委譲しない。**

**測っていないことを PR に書かない。** 実測していない項目は「未実施」と書く。

## 4. 出す

原則として文書は書かない（基準は `.claude/rules/docs.md`）。方針に触れたときだけ、該当する文書を**実装と同じコミットで**直す。

### PR

**`pr` スキルに従う。** タイトルと本文の型はそちらが持つ。issue 対応で必ず入れるのは次の3つ。

- `Closes #<番号>`
- 書かれた手段を採らなかったときの「issue から変えた点」
- 実測の表（未実施は「未実施」と明記）

ラベルと draft の判断は `pr` スキルが持つ。issue 対応で決めるのは、2-A との使い分けだけ。

| 状況 | どうする |
| :--- | :--- |
| セッション内で答えを待てる | 2-A の `AskUserQuestion` |
| 待てない、または差分を見せたほうが答えやすい | draft で出してコメントで問う |

## 5. 見届ける

**`pr` スキルの「作成後」に従う。** 購読・CI・レビューへの追従はそちらが持つ。issue 対応で加えるのは、レビューを起こすことと、往復の畳み方と、マージの扱いの3つ。

### レビューは別のセッションに頼む

**PR を出したらすぐ、レビュー用のセッションを1つ起こして依頼する。** 書いたセッションが自分の差分を見ても、直したい形が先に見えていて判定にならない。

- 起こす手段（Claude Code Remote のセッション作成ツール）が無ければ飛ばし、報告に「レビュー未依頼」と書く
- 渡すのは、このリポジトリと PR の URL、`review` スキルの「見届けを頼まれたとき」に従うこと、この3つだけ。実装の意図や、どう見てほしいかは渡さない
- 起こしたら待たない。こちらは CI の追従に戻る

### レビューが付いたら

直すか返すかは `pr` スキルの表に従う。ここで決めるのは往復の回し方。

- **直したら push する。** push が次のレビューの合図で、レビュー側は head が変わったときだけ見る
- **返す判断はコメントに書き、そこで止める。** 設計・複数ファイルに及ぶ指摘は書き手のもの。レビュー側の返事を待たない
- **指摘が尽きるまで繰り返す。** 新しい指摘が来たら同じ扱いで回す。往復の打ち切りはレビュー側が持つ
- **黙って止まらない。** 直さないなら、直さない理由を1行で PR に書く

### 終わり

- **マージしない。** 判定が `Approve` で CI が緑でも、マージは書き手が判断する
- **判定・CI・実測の結果を報告して終える。** issue は書き手のマージで `Closes` が閉じる
- レビュー側が往復を打ち切って書き手に判断を渡したときも、同じ形で報告して終える
