# issue 対応の手順

**対象は issue 番号のある依頼だけ。** 症状だけの依頼は `ui-change`、記事は `article`、番号の無い課題は `create-issues`。

**実装の手順はここに無い。** UI は `ui-change`、記事は `article`、実測は `verify`、PR の型は `pr` に従う。ここが持つのは、issue 1本を閉じるまでの進め方と、PR を出した後の見届け。

## 1. 読む

**issue に書かれていることは、すべて仮説として読む。**

- **原因は実装で裏を取る。** 行番号・変数名は書いた時点のもの
- **書かれた解決手段の採用を約束しない。** 判断は実測の後でよい
- **触る範囲の方針を先に読む。** UI は `docs/DESIGN_GUIDELINE.md`、構造は `docs/ARCHITECTURE.md` の該当節
- **再現してから直す。** 実データで条件が揃わないなら、条件を作って再現する

ブランチは `claude/issue-<番号>-<英数字4〜6>` を最新の `main` から切る。

## 2. 直す

- **issue の範囲から出ない。** 見つけた別の問題は直さず、PR の「このPRでやらないこと」に書く。issue が無ければ `create-issues` で立てる
- **前提が崩れたら手を止める。** 直し方を自分で決めない（→ 2-A）

### A. 解決手段を変えるときだけ確認を取る

原因調査と実装は自走してよい。**確認を取るのは、issue に書かれた解決手段を採らないと判断したときだけ。**

`AskUserQuestion` に3つを揃える。推奨を先頭に、採らない理由（試して壊れたならその出力）、代案で何が変わるか。

## 3. 実測する

**`verify` に従う。** issue 対応で足すのは2つ。

- **直す前に、issue の現象を一度再現する。** 再現していない不具合は、直ったことも確認できない
- **issue に書かれた再現条件を全部通す。** 1つ通ったところで止めない

## 4. 出す

文書は原則書かない（→ `.claude/rules/docs.md`）。方針に触れたときだけ、該当箇所を**実装と同じコミットで**直す。

**PR の型は `pr` に従う。** issue 対応で必ず入れるのは3つ。

- `Closes #<番号>`
- 書かれた手段を採らなかったときの「issue から変えた点」
- 実測の表

| 状況 | どうする |
| :--- | :--- |
| セッション内で答えを待てる | 2-A の `AskUserQuestion` |
| 待てない、差分を見せたほうが答えやすい | draft で出してコメントで問う |

## 5. 見届ける

**出したセッションが最後まで見る。** 出したら、購読とレビュー依頼を先に済ませてから CI に戻る。

- **PR のイベント（CI・レビュー・コメント）を購読する**
- **セッション名を `PR #N` に変える。** 一覧からどの PR を見ているセッションか辿れるようにする
- **レビュー用のセッションを1つ起こす。** 渡すのは、このリポジトリと PR の URL、`review` の「見届けを頼まれたとき」に従うこと、この3つだけ。**書いた側が自分の差分を見ても、直したい形が先に見えていて判定にならない**ので、実装の意図やどう見てほしいかは渡さない
- **起こしたら待たない。** 起こす手段が無ければ飛ばし、報告に「レビュー未依頼」と書く

### CI とレビューに追従する

| 来たもの | どうする |
| :--- | :--- |
| CI の赤、lint、自明な不具合 | 直して push。理由は PR に1行 |
| 小さく閉じた指摘（改名、テストの追加、1関数の整理） | 直して push |
| 設計の指摘、複数ファイルに及ぶ変更 | 直さず、返答をコメントに書く。判断は書き手 |
| コンフリクト | `main` をマージして解消。rebase と force push はしない |

- **小さいか判断が付かないなら、大きい側に倒す**
- **直したら push する。** push が次のレビューの合図で、レビュー側は head が変わったときだけ見る
- **指摘が尽きるまで繰り返す。** 往復の打ち切りはレビュー側が持つ
- **黙って止まらない。** 直さないなら、直さない理由を1行書く

### 終わり

- **マージしない。** CI が緑で `Approve` でも、マージは書き手が判断する
- **判定・CI・実測を報告して終える。** issue は書き手のマージで `Closes` が閉じる

### 見届けられないとき

購読の手段が無いか、セッションが続かないなら**待たない。** そのときの CI とレビューの状態を報告して終える。
**「後で確認します」と書かない。** 見ないものを見ると書くと、誰も見ていない PR が残る。
