# UI 変更の手順

コーディングの制約は `.claude/rules/` が自動で読み込まれる。このスキルは**手順**だけを扱う。

## 1. 読む

実装が正なので、まず触るコンポーネントの `.vue` を読む。個々の指定の理由は文書に無いので、**一見不要に見える指定は、消して lint / build / 目視で確かめる**（→ §4）。

方針に触れる変更は、先に `docs/DESIGN_GUIDELINE.md` の該当節を読む。

| 変更の対象 | 先に読む節 |
| :--- | :--- |
| 色・フォント・角丸・余白・モーション | 2、`theme/tokens.ts` |
| TOP・一覧・記事詳細のレイアウト | 3 |
| 本文の見た目・Callout・脚注 | 4 |
| ナビ・ページャ・ダークモードなど機能の要件 | 5 |

## 2. 実装する

- 既存の同種コンポーネントの書き方に揃える（Tailwind のクラスを基本にし、複雑な状態やアニメーションだけ scoped CSS）。
- 新しい色・サイズが要るときは、先に `theme/tokens.ts` に足す（DESIGN_GUIDELINE 2-A）。
- コメントは書かない（`.claude/rules/comment.md`）。

## 3. 方針を直す

- 原則として文書は書かない。コンポーネント内の設計や「消したら壊れる指定」の理由は残さない（基準は `.claude/rules/docs.md`）。
- DESIGN_GUIDELINE の方針（トークン、レイアウト原則、UX 要件）を覆したら、同じ変更でそちらを直す。
- 覆した方針が ADR の基準（思想が反映され、簡単には変えられない）に当たるなら、`docs/adr/` に1ファイル足し、`docs/DECISIONS.md` の索引にも行を足す。既存の ADR を覆したなら、その ADR を直すか消す。

## 4. 実測する

**`verify` スキルに従う。** テストがあるのは `app/utils/` の純粋関数だけで、UI そのものは測らないと分からない。根拠になるのは実際に打ったコマンドの出力だけ。**読んで判断したものは未確認として扱う。**

UI 変更で必ず測るもの。

- `npm test`（`app/utils/` の純粋関数。UI の見た目は見ていない）
- `npm run lint`（コンポーネントの import 忘れと、循環・依存方向。build は通ってしまう）と `npm run build`
- `npm run dev` での目視を SP 375px / PC 1280px × ライト / ダークの4通り
- 横スクロールが出ていないか、着地位置がヘッダーに潜り込んでいないか

測っていないものを「確認した」と書かない。

## 5. コミットする

日本語の言い切りで、何をどう変えたかを1行に書く（例: `ヘッダーメニューの先読みをホバー/フォーカスまで遅らせる`）。
ドキュメントの更新は実装と同じコミットに含める。
commit のたびに pre-commit フックが §4 と同じ lint を回すので、通らなければ先に直す。
