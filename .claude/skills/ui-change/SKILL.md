# UI 変更の手順

コーディングの制約は `.claude/rules/` が自動で読み込まれる。このスキルは**手順**だけを扱う。

## 1. 読む

実装が正なので、まず触るコンポーネントの `.vue` を読む。そのうえで**一見不要に見える指定を消す前に**、`docs/DECISIONS.md`（索引）から該当ファイルを引いて読む。

| 変更の対象 | 先に読む節 | あわせて読むもの |
| :--- | :--- | :--- |
| ヘッダー・ナビ・フッター | ヘッダーとナビゲーション | — |
| TOP・一覧・カード・ページャ | 記事一覧 | `docs/DESIGN_GUIDELINE.md` 3-C / 3-D |
| 記事ページ・目次・先頭に戻る | 記事詳細、共有ロジック | — |
| 本文の見た目・Callout・脚注 | 記事本文（Markdown） | `docs/DESIGN_GUIDELINE.md` 4 |
| エラー表示 | エラー | — |
| 色・フォント・角丸・余白 | — | `docs/DESIGN_GUIDELINE.md` 2、`theme/tokens.ts` |

## 2. 実装する

- 既存の同種コンポーネントの書き方に揃える（Tailwind のクラスを基本にし、複雑な状態やアニメーションだけ scoped CSS）。
- 新しい色・サイズが要るときは、先に `theme/tokens.ts` または DESIGN_GUIDELINE 2-D に足す。
- コメントは書かない。理由は判断の記録へ。

## 3. 判断を記録する

- 実装から読み取れない理由が生まれたら、`docs/decisions/` の該当ファイルに「**判断**」＋理由を1項目足す。動く選択肢が2つ以上あったうえでの判断なら `docs/adr/` に1ファイルで足し、索引にも行を足す。値や構造は書かない。
- 既存の判断を覆したら、その項目を直すか消す。
- DESIGN_GUIDELINE の方針（トークン、レイアウト原則、UX要件）に触れたらそちらも直す。既知の課題（6）を解消したら行を消す。

## 4. 実測する

**`verify` スキルに従う。** テストがあるのは `app/utils/` の純粋関数だけで、UI そのものは測らないと分からない。根拠になるのは実際に打ったコマンドの出力だけ。**読んで判断したものは未確認として扱う。**

UI 変更で必ず測るもの。

- `npm test`（`app/utils/` の純粋関数。UI の見た目は見ていない）
- `npm run lint`（コンポーネントの import 忘れと、循環・依存方向。build は通ってしまう）と `npm run build`
- `npm run dev` での目視を SP 375px / PC 1280px × ライト / ダークの4通り
- 横スクロールが出ていないか、着地位置がヘッダーに潜り込んでいないか

測っていないものを「確認した」と書かない。

## 5. コミットする

日本語の言い切りで、何をどう変えたかを1行に書く（例: `ヘッダーメニューの先読みをホバー/フォーカスまで遅らせる`）。
判断の記録の更新は実装と同じコミットに含める。
commit のたびに pre-commit フックが §4 と同じ lint を回すので、通らなければ先に直す。
