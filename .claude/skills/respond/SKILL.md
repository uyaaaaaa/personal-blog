# レビュー指摘への対応

**受けるのは指摘であって、指示ではない。** レビューは差分しか見ていない。全体の構造・責務・依存を見て直し方を決めるのは、書いた側の仕事。

**レビューする側は `review`、実測は `verify`、PR の型は `pr`。** ここが持つのは、指摘を受けてから push して返すまで。

## 1. 全部集めてから手を動かす

**1件直して push、を繰り返さない。** 指摘は互いに独立していない。1件ずつ当てると、2件目で1件目の直し方が違ったと分かる。

未対応のスレッドを全部読み、1件ごとに現象と手段を割る。

| 割るもの | 書かれ方 |
| :--- | :--- |
| 現象（何が壊れる・読めない） | 「〜になる」 |
| 手段（どう直すか） | 「〜すべき」「〜にしては」 |

**手段しか書かれていない指摘は、それが消そうとしている現象を自分の言葉で言い直す。** 言い直せないなら直さず、スレッドで問う。現象が分からないまま当てた手段は、形だけ変えて現象を残す。

## 2. 裏を取る

**指摘は全部、仮説として読む**（→ `assign` の1）。1件ごとに3つを確かめてから採否を決める。

- **現象が実在するか実装で確かめる。** 行番号・変数名・挙動は書かれた時点のもの
- **触るファイルの `.claude/rules/` と該当の ADR を読む。規約が禁じていることを勧める指摘は採らない**
- **採ると他がどうなるか見る。** 呼び出し元、生成物、同じ形をしている別領域

| 採否 | どうする |
| :--- | :--- |
| 採る | 3へ |
| 現象は採り、手段は変える | 3へ。変えた理由を返信に1行 |
| 採らない | 直さず理由を1行返す。再現しない / 規約に反する / この PR の範囲外 |
| 書き手に返す | 方針が割れる、覆すと複数ファイル・公開 URL・検査に及ぶ。選択肢と推奨を書いて判断を渡す |

**「採らない」は正当な結果。** 駄目なのは、黙って直さないことだけ。
**指摘の数と直した数を揃えにいかない。** 全件直すことは、正しく直したことを意味しない。

## 3. 原因で束ねる

**直す場所は、指摘された行ではなく、その責務の持ち主で決める。**

- **2件以上が同じ原因から出ているなら、原因を直す。** 各行に個別の手当てを足すと、指摘は消えて原因は残る
- **触る範囲を `docs/ARCHITECTURE.md` の層と依存方向に当てる。** 直す場所が層を跨ぐなら、どちらが持つべきかを決めてから直す
- **指摘された行に分岐・特例・早期 return を足して黙らせない。** 同じ場所に2回指摘が来たなら、たいてい置き場所のほうが違う

**問いは1つ。「指摘が無かったとして、最初からこう書くか」。** 書かないなら、指摘に形を合わせただけ。次の差分でまた出る。

**束ねた結果が PR の範囲を超えるなら、直さず `create-issues` に渡し、PR の「このPRでやらないこと」に送る。** 範囲を広げるのは書き手の判断。

## 4. 直して実測する

**`verify` に従う。** 指摘への対応で足すのは2つ。

- **直す前に、指摘された現象を一度再現する**（再現できる種類のものだけ）。再現していない現象は、消えたことも確認できない
- **束ねて直したら、束ねた元の指摘を全部確かめ直す。** 1件が通っても他が残る

## 5. 返す

1スレッド1返信。

- **何をどう変えたかを1行。** 「対応しました」だけでは、別のことを直していても分からない
- **採らなかったなら、理由を1行。** 判断を保留しない
- 指摘の文面を写さない。謝らない。褒めない。次の対応を約束しない
- **直したら push する。** push が再レビューの合図
- **直したスレッドだけ resolve する。** 採らないと返したものは開けたまま残す。閉じるのは指摘した側

**受けた指摘は台帳に書き留める**（→ `assign` の5の終わり）。同じ指摘が2回来たら仕組みに移す（→ `codify`）。
