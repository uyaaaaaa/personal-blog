# コンテキストの棚卸し

**やることの半分は「消す」。** 今のモデルは周囲の文脈から判断できる。旧世代向けに積んだ禁止・手順の全文・例示の列挙は、判断の邪魔になるか、互いに矛盾する。

## 読まれ方で分ける

| 種類 | 読まれるタイミング | 置いてよいもの |
| :--- | :--- | :--- |
| `CLAUDE.md`、`paths` の無い rule、`paths: "**"` の rule | 毎セッション | 毎回効く事実だけ。落とすと同じ間違いを繰り返すもの |
| `paths` 付きの rule | 該当ファイルを開いたとき | そのファイル種別に閉じた判断 |
| skill | 依頼が該当したとき | 手順。フェーズごとに参照する文書はさらに別ファイルに分ける |

## 手順

1. 各ファイルの行数と読まれ方を出す（`wc -l`、frontmatter の `paths`）
2. 毎セッション読まれる行を1行ずつ見て、**「消すと Claude が間違えるか」**を問う。間違えないなら消す
3. 実装・設定・Git 履歴・ツールの説明を読めば分かることを消す（コマンド一覧、ディレクトリ構成、検査の一覧、ハーネスが既に指示していること）
4. 機械が守っているものを消す（lint・フック・CI が落とすもの）。守らせたいのに守れていないものは、文書ではなくフックか lint に足す
5. 同じ指示が2箇所にあれば、効く場所1つに寄せる（スキルの使い分けは description に、コーディングの判断は rule に）
6. 実装と食い違っている記述を直す（テストの範囲、ファイルの所在、文書の節番号）
7. 例示の列挙は判断基準1つに置き換える。残す例は、基準を最短で伝える1〜2個

## 消さないもの

- 取り消せない操作の確認（本番反映・削除・外部送信・課金）
- リポジトリ固有の落とし穴で、実装を読んでも辿り着けないもの
- 標準と違う規約と、その理由

## 終わり方

変更前後の行数を、毎セッション読まれる分と合計に分けて報告する。振る舞いが変わったかは次のセッションで見る。
