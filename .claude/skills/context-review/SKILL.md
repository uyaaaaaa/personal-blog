# 渡す散文を減らす

**やることの半分は「消す」。** 今のモデルは周囲の文脈から判断できる。旧世代向けに積んだ禁止・手順の全文・例示の列挙は、判断の邪魔になるか、互いに矛盾する。

**対象はコードの周りに人が置いた文章すべて。** 実装は正なので触らない。

**ここで直す。** 消すのは1行の削除で、issue と PR を経由するには軽すぎる。ただし**判断を含むものは消さずに挙げる**（規約そのものの是非、`.claude/rules/docs.md` の ADR 基準に当たるもの、消すと判断の理由が失われるもの）。決めるのは書き手。

## 読まれ方で分ける

コストは読まれる頻度に比例する。上の層の1行は、下の層の1行より重い。

| 種類 | 読まれるタイミング | 置いてよいもの |
| :--- | :--- | :--- |
| `CLAUDE.md`、`paths` の無い rule、`paths: "**"` の rule、全 skill と agent の description | 毎セッション | 毎回効く事実だけ。落とすと同じ間違いを繰り返すもの |
| `paths` 付きの rule | 該当ファイルを開いたとき | そのファイル種別に閉じた判断 |
| コード内のコメント | 該当ファイルを開いたとき | 判定は `.claude/rules/comment.md` が持つ。ここでは基準を書き直さない |
| skill の本体 | 依頼が該当したとき | 手順。フェーズごとに参照する文書はさらに別ファイルに分ける |
| agent の本体 | 投げられたとき | 投げた先で完結する手順。判断はメインに残す |
| `docs/` と ADR | 参照されたとき | 基準は `.claude/rules/docs.md` が持つ |

## 範囲

**1回に1層。** 上から順に、まだ見ていない層を1つ選ぶ。依頼が範囲を名指ししていればそれに従う。全域を一度に触ると差分がレビューできず、消しすぎたことに次のセッションまで気付けない。

**コメントの層はディレクトリ単位に割る。** `app/composables/`、`app/components/layout/` のように、1回で読み切れる単位にする。

## 手順

選んだ層について、次を順に見る。

1. 1行ずつ、**「消すと Claude が間違えるか」**を問う。間違えないなら消す
2. 実装・設定・Git 履歴・ツールの説明を読めば分かることを消す（コマンド一覧、ディレクトリ構成、検査の一覧、ハーネスが既に指示していること）
3. 機械が守っているものを消す（lint・フック・CI が落とすもの）。守らせたいのに守れていないものは、文書ではなくフックか lint に足す（→ `enforce`）
4. 同じ指示が2箇所にあれば、効く場所1つに寄せる（スキルの使い分けは description に、コーディングの判断は rule に、検査の置き場は `docs/ARCHITECTURE.md` に）
5. 実装と食い違っている記述を直す（テストの範囲、ファイルの所在、文書の節番号、切れた相互参照）
6. 例示の列挙は判断基準1つに置き換える。残す例は、基準を最短で伝える1〜2個

description の層を見るときは、**発火条件が他のスキルと重なっていないか**も見る。重なると、依頼のたびに違うスキルが立つ。

## 消さないもの

- リポジトリ固有の落とし穴で、実装を読んでも辿り着けないもの
- 同じ指摘を2回以上受けて入った行（→ `codify`）。消すと同じ指摘がまた出る
- 標準と違う規約と、その理由
- 外部の仕様やライブラリの都合を書いたコメント（`.claude/rules/comment.md` の「残してよいもの」）

## 終わり方

**消した項目と、消した理由を1件1行。** 行数は報告しない。量を指標にすると、消すこと自体が目的になり、正当なコメントまで刷る。

**1件も消せなければ報告しない。** 消せるものが無いのは正常な結果で、この層は既に絞れているというだけ。
