# issue 対応の手順

**対象は issue 番号のある依頼だけ。** 症状だけの依頼（「表示がおかしい」）は `ui-change`、記事の依頼は `article` に行く。

コーディングの制約は `.claude/rules/` が自動で読み込まれる。**実装の手順は書かない**（UI なら `ui-change`、記事なら `article` に従う）。このスキルは issue を1本閉じるまでの**進め方**だけを扱う。

## 全体

| フェーズ | やること | 終了条件 |
| :--- | :--- | :--- |
| 1. 読む | issue と実装を突き合わせる | issue の「原因」が実装で裏取りできた |
| 2. 直す | 委譲先の手順で実装する | スコープが issue の中に収まっている |
| 3. 実測する | `verify` に従って測る | 直ったことをコマンドの出力で示せた |
| 4. 出す | 記録・コミット・PR | PR に確認結果が書けた |
| 5. 見届ける | Cloudflare Pages のチェック | 緑になった |

---

## 1. 読む

issue 本文は **現象 / 原因 / 対応案** の3節で書かれている。3つとも**仮説として読む**。

- **「原因」は実装で裏を取る。** issue に書かれた行番号・変数名は書いた時点のもの。該当ファイルを開いて、いま同じ状態か確認する。
- **「対応案」は採用を約束しない。** 採用しない判断は普通に起きる（#98 → PR #104、#108 → PR #112）。判断は3の後でよい。
- **触る範囲の `docs/DECISIONS.md` を先に読む。** 一見不要に見える指定は、たいてい理由がある。
- **再現できるか確かめる。** 再現しないなら、実データでは条件が揃っていないだけのことがある（#108 は5〜6件のカテゴリが無かった）。**条件を作って再現する**（→ 3）。

ブランチは `claude/issue-<番号>-<英数字4〜6>` を最新の `main` から切る。

## 2. 直す

- **UI に触るなら `ui-change` の手順に従う。** ここで重複して書かない。
- **issue の範囲から出ない。** 途中で見つけた別の問題は直さず、PR の「このPRでやらないこと」に番号付きで書く。無ければ issue を立てる。
- **前提が崩れたら手を止める。** 対応案どおりに実装して壊れたときは、直し方を自分で決めずに4-Aへ。

### A. 対応案を変えるときだけ確認を取る

原因調査と実装は自走してよい。**確認を取るのは、issue の対応案を採らない判断をしたときだけ。**

`AskUserQuestion` で、この3つを揃えて出す。

1. **採らない理由**（試して壊れたなら、その出力）
2. **代案と、それで何が変わるか**
3. **推奨（先頭に置く）**

例: #98 は `autoImport: false` を実際に設定して `/` が 500 になることを確認したうえで `scan: false` に替えた。**確認したことを添えると1往復で済む。**

## 3. 実測する

**`verify` スキルに従う。** 実測の手順はそちらが持つ。ここでは issue 対応に固有のことだけ。

- **直す前に、issue の現象を一度再現する。** 再現していない不具合は、直ったことも確認できない。
- **実データで条件が揃わないものは、条件を作って測る。** #108 は5〜6件のカテゴリが実在しなかったので、データを細工して `generate` し `dist/` を検査した（細工は revert）。
- **issue に書かれた再現条件を全部通す。** 1つ通ったところで止めない。
- 時間のかかる測定は、サブエージェントに委譲してよい（`verify` の「サブエージェントに委譲する」）。**判断は委譲しない。**

**測っていないことを PR に書かない。** 実測していない項目は「未実施」と書く。

## 4. 出す

**記録は実装と同じコミットに入れる。**

| 変えたもの | 直すドキュメント |
| :--- | :--- |
| 実装から読み取れない理由が生まれた | `docs/DECISIONS.md` の該当節 |
| 動く選択肢が2つ以上あって選んだ | `docs/DECISIONS.md` の「構造に関わる判断」（検討した案 / 対価 / 戻す条件） |
| トークン・レイアウト原則・UX要件 | `docs/DESIGN_GUIDELINE.md`。既知の課題が消えたら行ごと消す |
| ディレクトリ・依存方向・lint の範囲 | `docs/ARCHITECTURE.md` |

コミットメッセージは日本語の言い切りで1行。何をどう変えたかを書く（`View Allの判定をその幅で実際に見えている件数に合わせる`）。

### PR の型

```md
Closes #<番号>

## 背景
issue の現象を、実装のどこがどうずれているかまで落として書く。
再現条件が実データと違うなら、いつ顕在化するかも書く。

## 変更内容
差分の要点。長い引用はしない。

## issue から変えた点（対応案を変えたときだけ）
採らなかった理由と、代わりに何をしたか。

## 確認
`verify` の報告の型をそのまま置く。実測したこと / コマンド / 結果の表。
測っていない項目は「未実施」と書く。

## このPRでやらないこと（あれば）
別 issue の番号を添えて書く。
```

**確認の節に、実測していないものを書かない。** 「何を打って、何が出たから直ったと言っているか」だけを残す。

## 5. 見届ける

PR を作ると Cloudflare Pages のプレビューが自動で走る（`.github/workflows/` は無い。リポジトリ側の設定も不要）。

- **`Cloudflare Pages` チェックが緑になるまで見る。** 落ちたら PR に理由を書いてから直す。
- ボットがコメントするプレビュー URL（`https://<ブランチ名>.tech-blog-efb.pages.dev`、`/` は `-` になる）で、**本番と同じ静的生成の出力**を確認できる。生成結果に関わる変更はここまで見る。
- **コンフリクトは `main` をマージして解消する。** rebase や force push はしない。
- **マージはしない。** 緑になったことと確認結果を報告して終わり。マージと issue クローズは書き手が判断する。
