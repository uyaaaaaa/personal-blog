# PR の作り方

実装は終わっていて、**実測が済んでいる**前提。まだ測っていなければ `verify` に戻る。

## 1. 出す前

- ブランチが `main` でないこと
- ブランチ名は `claude/<主題>-<英数字4〜6>`
- 最新の `main` から派生。コンフリクトの有無を先に確認
- `git status --short` が空
- 実測用の一時的な細工が残っていないこと
- 実測の結果が手元にあること
- コミットは日本語の言い切りで1行
- ドキュメントの更新は実装と同じコミットに含まれていること

## 2. タイトル

- 何をどう変えたかを1行で言い切る
- issue タイトルの写しにしない（issue は現象、PR は変更）
- 分類の接頭辞は付けない

## 3. 本文

### 書き方

- **ソースコードレベルの情報（関数名・クラス名・変数名・設定キー）は原則書かない**
- 例外は、書かないと説明が成り立たない場合のみ
- 各セクションはリストで列挙
- 体言止めを使い、1文を最小限に
- 差分を読めば分かることを写さない
- 残すのは、判断・理由・確認結果の3つ

### 節

上から順。不要な節は落とす。

| 節 | 中身 | 落とす条件 |
| :--- | :--- | :--- |
| `Closes #N` | 対応する issue | issue が無い |
| 背景 | なぜ必要か。事象と影響 | 変更内容だけで自明 |
| 変更内容 | 変えたものの列挙 | なし（必須） |
| issue から変えた点 | 対応案を採らなかった理由と代替 | 対応案どおりに実装した |
| 確認 | 実測の表 | なし（必須） |
| このPRでやらないこと | 送り先の issue 番号 | 送るものが無い |

### 確認の節

- `verify` の報告表をそのまま置く
- 未実施の項目は「未実施」と明記
- 実測していない項目を書かない

## 4. 出す

- 作成は GitHub MCP の PR 作成ツール（`gh` は使えない）
- PR テンプレートはリポジトリに無い
- base は `main`
- コミットのフッターは `Co-Authored-By`
- PR 本文のフッターは `🤖 Generated with Claude Code`

## 5. 作成後

- CI が green になるまで見る
- 落ちたら、理由を PR のコメントに残す。1行で言い切る。
- コンフリクトは `main` をマージして解消。rebase と force push はしない
- レビューコメントへの追従は、このスキルの範囲外

## PR にしない場合

- 実測が済んでいない
- スコープが2つ以上に割れている（分ける）
- 依頼が調査・確認だけで、差分が無い
