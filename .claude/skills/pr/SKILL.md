# PR の作り方

実装は終わっていて、**実測が済んでいる**前提。まだ測っていなければ `verify` に戻る。

## PR にしない場合

- 実測が済んでいない
- スコープが2つ以上に割れている（分ける）
- 依頼が調査・確認だけで、差分が無い

## 1. 出す前

- 最新の `main` から派生。コンフリクトの有無を先に確認
- `git status --short` が空
- 実測用の一時的な細工が残っていないこと
- 実測の証跡が `.verify/` に残っていること
- **CI が打つものは、出す前に自分で通す。** 本文には書かない（→ 3）

## 2. タイトル

- 何をどう変えたかを1行で言い切る
- issue タイトルの写しにしない（issue は現象、PR は変更）
- 分類の接頭辞は付けない

## 3. 本文

### 原則: 機械が持っているものを写さない

| 写さないもの | どこが持っているか |
| :--- | :--- |
| ファイル名・件数・数値・関数名・クラス名・設定キー | 差分 |
| CI が判定した結果 | PR の緑と赤（何を打つかは `.github/workflows/`） |

残すのは、**判断・理由・機械が出さない確認結果**の3つ。ソースコードレベルの情報は、書かないと説明が成り立たないときだけ。
各セクションはリストで列挙。体言止めで1文を最小限に。

### 節

上から順。不要な節は落とす。

| 節 | 中身 | 落とす条件 |
| :--- | :--- | :--- |
| `Closes #N` | 対応する issue | issue が無い |
| 背景 | なぜ必要か。事象と影響 | やったことだけで自明 |
| やったこと | 変えたことの列挙 | なし（必須） |
| issue から変えた点 | issue に書かれた手段を採らなかった理由と代替 | issue のとおりに実装した |
| 確認 | CI が打たない実測の結果 | 測ったものが CI の範囲に収まる |
| このPRでやらないこと | 送り先の issue 番号 | 送るものが無い |

### やったことの節

- **1項目を折り返しのない1行に収める。** 目安は40字。収まらないなら詳細度が高すぎる
- 内訳・件数・ファイル名・数値を書かない。読み手が要るのは差分を読む前の見取り図だけ
- 波及の追従は、範囲を並べずに1行にまとめる

### 確認の節

**CI が打つものは書かない。** 書くのは、`verify` の実測メニューのうち CI が打たないものだけ。

- `verify` の報告表から証跡の列を落として置く
- 結果には、証跡から引いた根拠を残す。「問題なし」ではなく、件数・バイト数・観測した行
- 測れなかったものは「未実施」と明記する。空欄にも「問題なし」にもしない
- **残るものが無ければ節ごと落とす**

## 4. 出す

- 作成は GitHub MCP の PR 作成ツール。base は `main`
- **`agent` ラベルを必ず付ける。** エージェントが書いたことを表すだけの印で、出来や可否は表さない

### 書き手に返す判断が残っているなら draft で出す

**自分で決めずに書き手へ返す判断があるときは、draft で出す。** ready にするのは判断が返ってから。
draft はラベルと違い、マージを機械的に塞ぐ。ラベルの不在は、付け忘れ・人間の PR と区別が付かない。

- **判断はコメントに書く。** 選択肢とそれぞれで何が変わるかを添え、推奨を先頭に置く
- **その判断に依る箇所は直さない。** 書き手の判断を先取りしない
- **それ以外は draft でも直す。** CI の赤、自明な不具合、レビューの小さな指摘は自分で直す

## 5. 出した後

**`assign` の「5. 見届ける」に従う。** 購読・レビュー依頼・CI とレビューへの追従はそちらが持つ。
