# コメントのルール

**原則としてコメントは書きません。** コードを読めば分かることは、コメントではなくコードで表現します。

コメントは実装と一緒には更新されず、必ず実装から乖離します。乖離したコメントは無いより有害なため、
「無くても困らないコメント」は最初から書かない、という方針を取ります。

対象は `app/`・`theme/`・`remark/` 配下のコードと各種設定ファイル（`.ts` / `.vue` / `.mjs` / CSS）です。
記事本文（`content/`）と設計ドキュメント（`docs/`）は対象外です。

---

## 1. 書かないもの

| 種類 | 削除例 | 理由 |
| :--- | :--- | :--- |
| コードの言い換え | `// Fetch articles from 'article' content directory` | 直下の `queryCollection('article')` が同じことを言っている |
| セクションラベル | `<!-- Hero Section -->` `<!-- Title -->` `<!-- Mobile Navigation -->` | 直後のコンポーネント名・タグ・クラス名で分かる |
| 型やシグネチャで分かること | `@param id ターゲット要素のID`<br>`/** ページ固有のタイトル */ title?: ...` | 型定義が正。二重管理になる |
| 推測できる背景 | `/* 固定ヘッダー64px + 余白24px */`（`scroll-margin-top: 88px` に対して）<br>`// iOSのラバーバンドスクロールで負値になるためクランプする` | 実装を追えば辿り着ける。値の内訳を残したいなら定数に切り出す |
| 他ファイルの場所案内 | `// 着地位置のオフセットは [_slug].vue で一元管理している` | grep で分かる。参照先が動いた瞬間に嘘になる |
| 処理ブロックの要約 | `// 目次を開いた時、現在読んでいる見出しが見える位置までドロップダウン内をスクロールする` | 関数・変数の命名で表現する |
| コメントアウトされたコード | `// { label: 'About', path: '/about' },` | Git 履歴が持っている |
| ツール由来の定型コメント | `// https://nuxt.com/docs/api/configuration/nuxt-config` | scaffold の残骸 |
| キー名と重複する用途説明 | `theme/tokens.ts` の各トークンの `/** ページ背景 */` 等 | `bg` `border` `accent` というキー名が用途そのもの |

## 2. 残してよいもの

以下に当てはまる場合**のみ**書きます。判断に迷うものは書かない側に倒します。

### 2.1 外部の仕様・ライブラリの都合

リポジトリ内を全部読んでも分からず、外部の知識が要るもの。`docs/` に同じ記述があっても、コード側に残します。

```ts
// app/components/content/Callout.vue
// Obsidianデフォルトテーマの色（RGB）とlucideアイコン
const CALLOUT_CONFIG = { ... }
```

```js
// remark/obsidian-callout.mjs
// remark-mdcが `[!note]` から生成する属性なしspanノードか判定し、タイプ名を返す
```

```css
/* app/components/content/Callout.vue */
/* prose由来の余白をcallout内で詰める */
```

### 2.2 一見不要に見えるコードが、必要な理由

消してよさそうに見える行を、次の人が消さないためのもの。

```ts
// app/composables/useScrollTo.ts
// ターゲットが既に表示位置にありスクロールが一切発生しないケースの保険
settle()
```

### 2.3 意図的に「書いていない」こと

コードに現れないため、コメントでしか表現できないもの。

```css
/* app/components/layout/HeaderNavigation.vue */
/* 表示・非表示の切り替えはTailwindの md: に統一しているため、displayはここで指定しない */
```

### 2.4 名前から意味が読み取れない値

```ts
// app/components/content/Callout.vue
// '-' は初期状態が閉、'+' は初期状態が開の折りたたみcallout
fold?: string
```

```ts
// app/utils/tag.ts
// 例: "github action" -> "github-action", "@nuxt/content" -> "nuxt-content", "S3" -> "s3"
```

### 2.5 機能を持つディレクティブ

`@ts-expect-error` `eslint-disable` などはコメントの形をしたコードなので、この規約の対象外です。

```ts
// nuxt.config.ts
// @ts-expect-error 型定義のないローカルESMモジュール
```

## 3. 書くときの書き方

- **「何を」ではなく「なぜ」を書く。** ただし §1 のとおり、リポジトリ内を読めば分かる「なぜ」は書かない。書くのは外部要因だけ。
- **1〜2行に収める。** それ以上の説明が必要なら、コードコメントではなく `docs/` に書く。
- **実装を変えたらコメントも直すか消す。** 残す価値が無くなったら消す。

## 4. 判定手順

1. そのコメントを消して、コードだけで意味が変わるか？ → 変わらないなら**消す**
2. リポジトリ内を読めば分かる内容か？ → 分かるなら**消す**
3. 命名の変更・定数の抽出・関数の分割で表現できるか？ → できるなら**そうする**
4. 外部（ライブラリ仕様、外部ツールとの互換、運用上の決定）を知らないと分からないか？ → §2 に当てはまるなら**残す**
