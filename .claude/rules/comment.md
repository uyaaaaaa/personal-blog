# コメントのルール

**原則としてコメントは書かない。** コードを読めば分かることは、コメントではなくコードで表現する。
コメントは実装と一緒には更新されず必ず乖離し、乖離したコメントは無いより有害。

対象は `app/`・`theme/`・`remark/` と設定ファイル。記事本文（`content/`）と `docs/` は対象外。

## 残してよいもの

リポジトリ内を全部読んでも分からず、理由がコードの外にあるものだけ。迷ったら書かない。

- **外部の仕様・ライブラリの都合。** 例: Obsidian テーマの色に合わせた定数、remark-mdc が生成するノードの形
- **一見不要なコードが必要な理由。** 次の人が消さないためのもの。例: スクロールが一切発生しないケースの保険
- **意図的に書いていないこと。** 例: `display` は Tailwind の `md:` に統一しているのでここで指定しない
- **名前から意味が読み取れない値。** 例: `'-'` は初期状態が閉、`'+'` は開
- `@ts-expect-error` `eslint-disable` などの機能を持つディレクティブはコードなので、この規約の対象外

書くときは「なぜ」を1〜2行。それ以上要るなら、命名や構造で表現し直す。実装を変えたらコメントも直すか消す。

## 判定

1. 消してもコードだけで意味が変わらないなら、消す
2. リポジトリ内を読めば分かるなら、消す（コードの言い換え、セクションラベル、型で分かること、他ファイルの場所案内、処理の要約、コメントアウトしたコード、scaffold の定型、キー名と重複する説明）
3. 命名の変更・定数の抽出・関数の分割で表現できるなら、そうする
4. 外部を知らないと分からないものだけ、残す
