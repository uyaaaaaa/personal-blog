# ドキュメントのルール

**原則としてドキュメントは書かない。実装が正で、実装を読めば分かることは書かない。**

ドキュメントは実装と一緒には更新されず、必ず実装から乖離する。乖離した文書は無いより有害なため、
残すのは「思想が反映されていて、簡単には変えられないもの」だけに絞る。それ以外は実装・lint・Git 履歴が持つ。

## 1. 書かないもの

| 種類 | 例 | 理由 |
| :--- | :--- | :--- |
| 実装の写し | 値、構造、props、ページ構成、ディレクトリツリー | 実装が正。写しは遅れたコピーにしかならない |
| コンポーネント内の設計 | 状態の持ち方、表示の出し分け、要素の分割 | 影響がそのコンポーネントに閉じる。直すのも速い |
| 関数の設計、共通関数の切り出し | composable の分け方、引数の取り方 | 同上。呼び出し側を読めば分かる |
| 機械的に縛れるもの | import の書き方、任意値、依存方向、循環 | lint / build / テストが落とす。縛りたければ文書ではなく lint に足す |
| 機械が守っている旨の説明 | 「〜は lint が落とす」「フックが形式を検査する」、強制手段の一覧 | 破れば止まる。書かなくても効く（→ [ADR 11](../../docs/adr/11-no-enforcement-inventory.md)） |
| 変更の規模が小さく、すぐ直せるもの | 設定ファイルの1キー、CI の1ジョブ | 壊れたら直せばよい |
| 「一見不要に見える指定」が必要な理由 | 消すと崩れるクラス、ブラウザの都合 | 消して壊れたら lint / build / 目視で分かる。それで受ける |
| 既知の課題、TODO、issue の一覧 | 未実装の機能の表 | GitHub の issue が持つ |
| 「最終更新」のような日付 | | Git が持つ |

## 2. 書くもの

| 何を | どこに |
| :--- | :--- |
| 思想が反映され、簡単には変えられない判断（下記） | `docs/adr/NN-<英語スラッグ>.md` に1判断1ファイル。索引は `docs/DECISIONS.md` |
| デザインの大方針とガードレール（コンセプト、トークンの原則、UX 要件） | `docs/DESIGN_GUIDELINE.md` |
| 構造、依存方向、検査の置き場 | `docs/ARCHITECTURE.md`。効いている検査の一覧は持たない（→ [ADR 11](../../docs/adr/11-no-enforcement-inventory.md)） |
| favicon / OGP の仕様と生成手順 | `docs/ICON_GUIDELINE.md` |

実装を変えて方針が変わったら、同じ変更で該当箇所を直すか消す。理由が失効した項目は消す。

## 3. ADR の基準

次の**両方**を満たすときだけ書く。片方しか満たさないものは書かない。

1. **思想が反映される。** アーキテクチャ設計、アーキテクチャ規約、テスト設計、デザインの大方針やガードレールのどれかに当たる。
2. **簡単には変えられない。** 覆すと複数ファイル・公開 URL・ビルド設定・テストの走らせ方が変わる。または一度出すと戻せない（公開 URL など）。

既存の方針を覆した「方針転換」は必ず書く。初回の採用も、上の2つを満たすなら書く。
迷ったら書かない側に倒す。あとで方針転換になったときに書けばよい。

## 4. ADR の書き方

- 1判断1ファイル。見出しは判断を言い切る1行。
- 「判断」＋「検討した案」「対価」「戻す条件」の3つを必ず持つ。
- 検討した案が2つ以上あるときは、案ごとに1行の入れ子の箇条書きにする。行頭は案の名前を太字にし、採用した案には `（採用）` を付ける。対価が3つ以上に分かれるときも同じにする。
- 番号は連番で、消したら詰め直す（残りのファイル名と参照も同じ変更で振り直す）。索引の行も同じ変更で足す・消す。

```md
- **検討した案**
  - **クエリ（`?page=2`）**: 静的生成では2ページ目以降が生成されない。
  - **パス（`/article/page/2`、採用）**: `crawlLinks` がページャを辿って全ページを生成する。
- **対価**: …
- **戻す条件**: …
```
