# コミットのルール

**件名は日本語の言い切りで1行。分類の接頭辞は付けない。**

`feat:` `fix:` のような接頭辞は付けません（理由は §5）。件名に入れるのは「何を」「どう変えたか」の2つだけです。

## 1. 形

```
<何をどう変えたか。1行>

<なぜそうしたか。任意>

Co-Authored-By: ...
```

| 何 | 決まり |
| :--- | :--- |
| 件名の長さ | 12〜50字。目安は30字 |
| 言語 | 日本語。`update` のような英語1語は何も伝えない |
| 語尾 | 言い切り（「〜する」「〜に替える」）。体言止め（「〜対応」「〜の修正」）にしない |
| 句点 | 件名には付けない |
| 2行目 | 本文を書くなら空行を1つ挟む |
| 本文 | 任意。書くのは「なぜ」だけ。「何を」は件名と差分が持つ |

## 2. 件名に書くこと

**「何を」と「どう変えたか」を両方入れる。** 片方だけだと、差分を開くまで何が起きたか分かりません。

| 書く | 書かない | 足りないもの |
| :--- | :--- | :--- |
| `View Allの判定をその幅で実際に見えている件数に合わせる` | `View Allを修正` | どう変えたか |
| `ページングの判定を utils の純粋関数に出してテストで守る` | `リファクタリング` | 何を・どう |
| `タグのスラッグが一意になることをlintで検査する` | `update` | 両方 |

- **ファイル名・件数・数値を書かない。** 差分が持っています
- **issue の文面を写さない。** issue は現象、コミットは変更です
- 50字に収まらないときは、1つのコミットに2つの変更が入っています。分けてください

## 3. 1コミットの範囲

- **ドキュメントの更新は実装と同じコミットに入れる。** 方針が変わった記録を実装から切り離すと、理由が失われます
- **整形だけのコミットは分ける。** 分けたらハッシュを `.git-blame-ignore-revs` に足します
- **実測用の一時的な細工はコミットに含めない**（→ `verify` スキル）

## 4. 機械が見ないもの

§1 の形は機械で落とせますが、**§2 と §3 は判定できません。** このファイルが持ちます。

## 5. 分類の接頭辞を付けない理由

Conventional Commits が挙げる利点は、CHANGELOG の自動生成・semver の自動決定・公開のトリガー・変更の周知・貢献のしやすさです。
このリポジトリは CHANGELOG も version も持たず、Cloudflare Pages は `main` への push を型で分岐せず全部ビルドし、書き手は1人です。**回収先がありません。**

一方で対価は残ります。実装とドキュメントを同じコミットに入れる規定（§3）と、1コミット1つの型は毎回衝突します。
接頭辞を付けても「型を選ぶ手間」と「過去の履歴と揃わない混在」だけが残るため、採りません。PR タイトルに接頭辞を付けないのも同じ理由です（→ `pr` スキル）。

**戻すとしたら**、CHANGELOG かバージョンを持ったとき、または型で公開の分岐を変えたくなったときです。
